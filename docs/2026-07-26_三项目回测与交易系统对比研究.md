### 1.3 值得 VERA 学习的地方

1. **QP:exit_rules 单模块三端复用**(回测/模拟盘/实盘调同一份 `exit_rules.py`)。VERA 建交易系统时,卖出规则引擎必须从一开始就是独立包,回测和实盘 import 同一份代码,杜绝"回测一套、实盘一套"的口径分裂。QP 自审 C6(优化器与生产引擎退出语义不一致)正是反例。
2. **QP:成本配置单一真相源**(`get_cost_cfg()` 统一从 settings 读,含最低佣金)。VERA 补最低佣金模型,且交易系统的成本配置必须与回测共用同一份定义。
3. **MQ:1m 级撮合精度 + 信号时刻对齐**(日信号映射到日内 14:50 bar)。VERA 的 5m degrade 已有雏形,可借鉴其 `signal_bar_instant` 统一时刻语义。
4. **MQ:回测进程隔离**(独立子进程跑回测,mp.Queue 传进度,崩溃有 sentinel 兜底)。VERA 的 web 服务长跑场景下值得引入。
5. **三家共同教训——双实现必漂移**:MQ 的 Python/Numba 双引擎、QP 的优化器/生产双路径,都出了口径问题。VERA 的 `test_loop_parity.py` 字节级 parity 守卫正是正确答案,交易系统的任何"第二实现"都必须有 parity 测试。

### 1.4 VERA 不应学的地方

- MQ:无滑点的成本模型、无测试的正确性裸奔。
- QP:AI 优化器全样本报收益(统计自欺);同 bar 默认止盈优先的乐观假设;iterrows 级性能。
- 两家共同点:**回测核心恰恰是最没测试的部分**。VERA 要守住自己的优势。

### 2.2 四个关键问题的结论

#### 问题一:持仓/交易记录同步,以 QMT 为准还是本地为准?

**结论:以 QMT(柜台)为准,本地账本只做缓存+策略视图+成本修正。这是业界一致答案。**

- vnpy:connect 成功后立刻全量查询券商侧,运行中信任推送,本地不维护权威账本(官方文档)。
- LEAN:Brokerage 抽象基类强制实现 `GetOpenOrders/GetAccountHoldings/GetCashBalance`,启动对账是强制步骤。
- freqtrade:本地 SQLite 是操作账本,但与交易所不一致时以交易所为准做 best-effort 恢复。
- QP 是正确范式:A(QMT 实时) vs B(本地持仓) vs C(成交还原)三方比对,偏差超门限→写 audit+kill switch,**对账结果不回写本地、不自动改账**——自动改账会把对账 bug 变成资损。
- MQ 的弱对账(双数据源合并查询+每日备份)够用但有资损窗口,不要学。

本地账本真正不可替代的价值只有一个:**QMT 不告诉你的事**——策略归属(哪个策略开的仓)、成本口径(本地未闭合交易周期均价)、卖出规则状态(阶梯已卖到第几档)。这些存本地,其余以 QMT 为准。

#### 问题二:锁控制是否有必要?

**结论:业务层的并发锁不必要(用单线程事件循环消灭多写者);但"业务逻辑锁"(防重入)必要;跨边界处锁不可避免。**

- 行业主流是"串行化优先,锁为兜底":vnpy EventEngine 单线程消费队列,策略代码零锁;LMAX Single Writer Principle——每个数据结构只有一个写者就不需要锁;xtquant 官方回调也是单队列串行(这正是回调里调同步查询会死锁的原因)。
- 因此交易系统核心:**所有 xtquant 回调只 put 进 queue,单一消费者线程串行处理** → 账户状态天然无竞争,不需要互斥锁。
- 但 MQ/QP 的"清仓锁"不是并发锁,是**业务状态锁**:解决"撤固卖单→下轮又挂回"和"止损自我重入"两个真实 race。事件循环解决的是并发,解决不了跨事件的业务重入,这个锁值得保留(粒度 (env,account,code),TTL 300s 兜底,order_id 反查)。
- 真正需要锁的地方只剩两处:① 队列本身(用标准库 queue.Queue,不用自研);② DB 连接(QP 实测 DuckDB 多线程 1.5 秒段错误,教训是单连接+一把锁全量串行化)。

#### 问题三:盘中监控,订阅推送还是轮询?

**结论:不是二选一,是"订阅为主+轮询对账+心跳降级"三层结构,各司其职。**

| 层 | 机制 | 用途 |
|---|---|---|
| 行情 | xtdata 订阅推送 | 低延迟驱动监控逻辑 |
| 行情健康 | 软心跳(开盘时段 N 秒无 tick 即告警/降级轮询) | 订阅丢失是无信号的,必须主动探活 |
| 委托/成交 | on_stock_order/on_stock_trade 回调 | 驱动订单状态机 |
| 持仓对账 | 低频轮询 query_stock_positions(QP 每日 4 次定时+启动必对账) | 全量快照天然自愈,纠正回调丢失 |

依据:freqtrade WS 失败自动回退 REST 轮询;迅投社区已确认 xtquant 回调会丢(on_stock_trade 时有时无、开盘时段 tick 静默);轮询的缺点是流控与延迟,但对账场景不需要高频。QP 的双驱动(tick 订阅+15s 无 tick 降级+60s 调度兜底)是可直接照抄的成熟方案。

**xtquant 三个已验证的坑,设计时必须规避:**
1. 回调里调同步查询(query_stock_*)会死锁卡死(官方文档明示)→ 回调只做入队;
2. connect() 断开后不自动重连(官方)→ 需自研 on_disconnected+指数退避重连+重连后重新 subscribe+全量对账(参考 xqshare 的 1s→16s 退避实现);
3. 回调单线程串行,重活必须丢给自己的工作线程(QP 的 db_executor 有界线程池是正确做法)。

#### 问题四:还有什么值得提高的?

1. **幂等单号**:每笔委托生成策略侧唯一编号编码进 `order_remark`(≤24 字符),盘后 `query_stock_orders` 按 remark 对账。MQ/QP 都没做,是超出两者的改进点。
2. **原始回报 append-only 落盘**:每条 on_stock_order/on_stock_trade 原始对象先 JSONL 落盘再处理——低成本的事件溯源等价物,崩溃可重放。QP 的 WAL 已是这个思路,VERA 可简化为单文件 JSONL。
3. **kill switch 三重态**(QP):内存/DB/文件任一生效即停,必须人工解除。这是 QP 最值得完整照搬的设计。
4. **断线守护要覆盖"行情静默但连接未断"**:`on_disconnected` 在该场景未必触发(社区未验证),软心跳不可省。
5. **非交易日/非交易时段自动拒单**(QP kill switch 已含),加上配置热加载(QP 用 mtime 每秒 stat,解决双进程配置漂移的实际事故)。

## 第三部分:VERA 交易系统建议架构

目标:专业、简洁、清晰、高鲁棒,**不要复杂**。建议刻意砍掉 MQ 的微服务拆分(x-tdxqmt/x-miniqmt/x-server/x-admin 四个进程三种语言)和 QP 的过度防御层数。

### 3.1 推荐形态:单进程、四模块、一条事件总线

```
vera_trade/
├── gateway.py        # xtquant 适配层(唯一 import xtquant 的地方,含 Fake SDK 供测试)
├── event_engine.py   # 单线程事件总线(仿 vnpy,queue.Queue+单消费者线程)
├── book.py           # 本地账本:持仓视图/策略归属/成本口径/卖出规则状态
├── order_fsm.py      # 订单状态机(48→50→56/57 官方枚举,终态不可逆)
├── reconciler.py     # 三方对账(QMT vs 本地 vs 成交还原),只告警+熔断,不回写
├── risk_gate.py      # 事前风控闸门(照搬 QP 的 10 闸门,可裁剪为 6 闸门起步)
├── exit_monitor.py   # 离场监控——必须 import VERA 回测侧同一份退出规则(铁律)
├── store.py          # SQLite 持久化 + WAL/JSONL 回报落盘 + 启动恢复
└── kill_switch.py    # 三重态 kill switch(照搬 QP)
```

- 进程模型:FastAPI 服务内嵌 event_engine 线程;回调只入队;DB 写走单连接+单锁。
- 监控:行情订阅+软心跳+定时对账轮询(09:35/11:30/14:55/15:05 每日 4 次起步)。
- 前端:复用 VERA 现有 web 栈(vanilla JS+自托管 ECharts,守"本地部署优先"铁律),加交易页即可。不要引入 Vue/构建链,不要学 MQ 的 3123 行单文件——按现有 web/js/ 模块划分拆 3-4 个模块。
- 成本配置与卖出规则:与回测共用同一份定义(QP 教训 C6:口径分裂是过拟合之外最大的自欺)。

### 3.2 起步即铁律(写入 CLAUDE.md)

1. QMT 是持仓/成交的唯一真相源;对账只告警+熔断,永不自动改账。
2. 任何回调线程里禁止调用 xtquant 同步接口、禁止直接写 DB。
3. 实盘/回测共用同一份 exit_rules 与成本配置,并有 parity 测试锁定。
4. 所有下单先过 risk_gate,kill switch 三重态任一生效即全面拒单。
5. 原始回报先落盘(JSONL append-only)再处理;重启先全量对账再恢复交易。
6. 交易系统代码测试覆盖率不得低于回测侧现状(MQ=2 分、QP=5 分的教训:交易恰恰是最需要测试的部分)。

### 3.3 待实测验证项(构建前做 spike)

- miniQMT 查询接口流控上限(决定对账轮询频率);
- 回调丢失的真实频率与触发条件(模拟盘 vs 实盘行为差异社区有报告);
- `on_disconnected` 在"行情静默但连接未断"场景是否触发;
- order_remark 在 query_stock_orders 返回中是否完整回传(幂等单号方案的前提)。
