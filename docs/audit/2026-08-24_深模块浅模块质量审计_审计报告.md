# 深模块 / 浅模块质量审计报告

- 日期: 2026-08-24
- 对象: VERA 全项目（重点: backtest / pipeline / core / trade / server）
- 方法: John Ousterhout《A Philosophy of Software Design》的深模块/浅模块框架
- 审计人: 架构审计（WorkBuddy）

---

## 一、结论先行

**能用吗? 能用。整体接口质量中等偏上（7/10）。**

VERA 的模块设计呈"**两头尖、中间平**"：

- **最深处在核心回测子包** `backtest/loop/` —— 对象图分解得干净利落（深模块典范）。
- **最浅处在引擎与数据层的公共入口** —— 参数被摊平成 41 个、17 个、11 个的长列表（浅模块重灾区）。
- **trade/ 与 server 层**存在"上帝对象 + 依赖注入失控"两类问题，但不影响运行，是工程债。

**最值得动手的只有一件事**: 把 `stop_config` 从裸 dict 升级成强类型载体。就这一刀，能同时消掉 3 个长参数函数的肥接口（`build_backtest_loop` 41 参、`_resolve_stop_and_build_loop` 17 参、`get_kline` 11 参里的一半），性价比最高。

## 二、先说人话: 什么叫"深模块 / 浅模块"

这是一把衡量"接口划得好不好"的尺子，两个维度:

1. **接口（面）** = 调用方要懂多少、要传多少东西。越小越好。
2. **实现（里）** = 模块内部藏了多少复杂度。越深越好。

**深模块 = 接口小、实现深**。比喻: 自动挡汽车。你只操作油门/刹车/方向盘 3 样，发动机舱里上千个零件你一个都不用管。**好设计**。

**浅模块 = 接口大、实现浅**。两种坏味道:

- **传话筒（pass-through）**: 函数自己不干活，就是把参数原封不动转给下一个函数。像秘书只负责递话，不帮你处理任何事。
- **操纵杆外露**: 每个内部零件都伸一根杆到驾驶座，你开个车要同时操作 40 根杆。参数列表越长、越接近内部实现，越浅。

一句话: **深模块把复杂度藏起来，浅模块把复杂度漏给调用方。**

## 三、深模块典范（正面，保持现状）

### 3.1 `core/progress.py` —— 全项目最漂亮的深模块

- 对外接口只有 3 个函数: `reset()` / `report()` / `snapshot()`，见 [core/progress.py:58]、[core/progress.py:66]、[core/progress.py:98]。
- 内部藏了: 全局状态机、速率法 ETA 估算、8 个阶段到全局百分比的 ANCHORS 映射、线程锁、单调性。
- 调用方只需要喊一句"我在 formula 阶段，进度 0.3，批到 23/51"，剩下全不用管。连"有没有人读"这个复杂度都封装了（无人读时 ~1µs no-op）。
- **这是 Ousterhout 书里的标准答案**：把"进度怎么算、ETA 怎么估、锁怎么加"全部关进盒子里，只留一个窄门。

### 3.2 `pipeline.Pipeline.run()` —— 深模块的编排范本

- 对外 3 个参数: `export_tdx / progress_callback / close_on_finish`，见 [pipeline/pipeline.py:240]。
- 内部编排了 10 步: 连 TDX → 选股 → 因子过滤 → 政策标签 → 概念标签 → 回测 → 基准 → 报告 → 导出 → 清理，全部在盒子里消化。
- 两个加分细节: 进度回调失败被吞（不中断管线）、政策/概念标签失败降级为 None（松耦合）。**把"失败怎么处理"也封装了**，调用方零负担。

### 3.3 `backtest/loop/` 子包 —— 对象图分解清晰

- `BacktestParams`（参数数据类）、`ExitDispatcher`（策略分发）、7 个 `Strategy`（cost_stop/trailing/ladder_tp/time_stop 等各一个文件）各司其职。
- 每个 Strategy 接口小（比如 `TrailingStrategy` 只管 activation/drawdown/gap_protection/confirm），实现内聚。
- 这是从当年 39 参的 `_simulate_core_v3` 一步步拆出来的成果，方向完全正确。

### 3.4 `core/dividend_type.py` —— 窄接口消除歧义

- 用 `to_tdx_str` / `to_formula_int` 把 int/str 复权口径统一归一化，允许调用方混传。接口极小，内部消化了所有映射分支。

## 四、浅模块反模式（负面，带证据）

> 所有 `[file.py:line]` 引用均经 AST 脚本 + Read 实际代码验证，非肉眼引用。

### 反模式 1: 接口摊平 —— `build_backtest_loop` 41 个参数

这是全项目最刺眼的浅模块，定义在 [backtest/loop/builder.py:31]。

**实测数字**: 41 个参数，20 个必填 + 21 个带默认值，**全部是位置参数，连 `*` 强制关键字分隔都没有**。

它的"前身"是那个被反复批判的 39 参 `_simulate_core_v3`（CLAUDE.md 有记载）。重构后非但没瘦身，反而**多了 2 个**。

**为什么说它是浅模块而不是深模块**: 它内部实现其实是深的（做能力门控、参数归一化、构建对象图），但接口面把 41 个原子值全部摊开，等于把引擎的每一个旋钮都伸到了调用方面前。调用方 [backtest/engine.py:395] 必须把这 41 个值**按顺序**一个个摆好，摆错一个就是静默 bug。

**最讽刺的地方**: 函数内部**已经有** `BacktestParams` 这个数据类在收拢参数（[backtest/loop/builder.py:77] 把 15 个资金/仓位参数打包进去），但函数签名却没跟上——**内部已经抽象好了，对外却还在裸奔**。这是典型的"接口没追上实现"。

### 反模式 2: 接口摊平（续）—— `_resolve_stop_and_build_loop` 17 个参数

定义在 [backtest/engine.py:318]。17 个参数，一半是 numpy 矩阵（close/high/low/open/tradable/last_tradable_idx），一半是阶梯止盈数组（ladder_profits/ladder_ratios/n_ladder）。

公允地说，它不是纯传话筒——内部真消化了复杂度（优先级校验、移动止盈缺省、时间 ×bpday 缩放、ATR 计算、构建循环、执行循环）。但它把 `stop` 字典**拆散成 17 个原子参数**，这就是"信息泄漏": 调用方必须知道 `stop` 字典里到底有哪些 key、哪些要提前取出来传。正确的做法是直接把 `stop` 字典传进去，让函数自己解析。

### 反模式 3: 透传开关 —— `get_kline` 11 个参数

定义在 [core/data_fetcher.py:43]。函数体只有 9 行，本质是个 if/else 路由:

```python
if use_cache:
    return cls._get_kline_via_cache(...)
return cls._get_kline_from_tdx(...)
```

见 [core/data_fetcher.py:69]。

**这是标准的"传话筒"浅模块**: 11 个参数进来，不做任何加工，原样分发给两个私有方法。尤其 `use_cache` 这个布尔开关，强迫调用方理解"缓存还是直拉"这个**本该内聚的实现细节**。调用方想拉数据，不该关心数据是缓存来的还是现拉的。

### 反模式 4: 依赖注入失控 —— `__init__` 14 参 / 13 参

- `trade/executor.py:162` 的 `__init__` **14 个参数**。
- `trade/reconciler.py:69` 的 `__init__` **13 个参数**。

构造函数参数爆炸，通常是"上帝对象"的前兆: 一个类要依赖十几个协作者，说明它要么职责太杂，要么没把协作者打包成更高层的抽象。

### 反模式 5: 方法参数爆炸 —— `apply_trade` 9 参

- `trade/book.py:127` 的 `apply_order_update` 9 个参数。
- `trade/book.py:159` 的 `apply_trade` 9 个参数。

账本写入方法要传 9 个原子字段，说明"一笔成交"这个概念还没有被建模成一个对象，而是散成 9 个裸值在方法间流转。

## 五、上帝对象（超大文件，职责混杂）

"上帝对象"是浅模块的近亲——一个模块塞了太多职责，接口面必然臃肿。

| 文件 | 行数 | 问题 |
|---|---|---|
| `trade/rotation.py` | 802 | 轮动策略，职责边界待查 |
| `trade/api.py` | 791 | 自述"薄层"，但 20+ 端点堆在一起 |
| `trade/config.py` | 740 | 配置模型 + 校验 + 存取混杂 |
| `brain/data_tools.py` | 720 | 工具集，疑似杂物抽屉 |
| `server.py` | 622 | 已拆 lab/research/data_cache 后仍 600+ 行，30+ 端点 |

需要说明: `server.py` 和 `trade/api.py` 的"大"有一定合理性——它们本质是 API 契约面，端点数 = 接口数。但 `trade/config.py`（740 行配置模型）和 `brain/data_tools.py`（720 行工具集）值得警惕，可能是"杂物抽屉"。

## 六、核心洞察: `stop_config` 裸 dict 的信息泄漏

这是本次审计最想点的一个**系统性根因**，它同时喂养了反模式 1、2、3。

`backtest/stop_config.py` 目前只提供 `load_stop_config()` 返回**裸 dict**（见 [backtest/stop_config.py:39]）。于是 `cost_stop` / `trailing_stop` / `ladder_tp` / `time_stop` / `cond_time_stop` / `first_day` / `atr_stop` / `capabilities` 这些 key，在 **pipeline → engine → builder** 三层之间靠字符串 `.get()` 反复解析:

- [pipeline/pipeline.py:140] 取 `self.config.get("stop_loss", {})`
- [backtest/engine.py:353] 起，`_resolve_stop_and_build_loop` 里 `stop.get("cost_stop", {})`、`stop.get("trailing_stop", {})`…… 逐个抠
- [backtest/engine.py:784] `run_cached` 里再抠一遍 `caps.get("formula_exit", True)`

**危害**: dict 的 key 结构成了"隐式接口"，任何一层拼错 key（比如 `cond_time_stop` 写成 `cond_time`）都是**运行时才炸**，IDE 无法提示、测试难覆盖。这正是浅模块的本质——**把内部结构的细节漏给了每一个调用方**。

**解法方向**: 引入一个 `StopConfig` 强类型（dataclass 或 pydantic），`load_stop_config` 返回它而不是 dict，下游 `.cost_stop.enabled` 替代 `.get("cost_stop", {}).get("enabled")`。一次性消除三层之间的字符串耦合。

## 七、重构建议（按性价比排序）

### P0（强烈建议，一次手术三处受益）

1. **`stop_config` 强类型化**: `load_stop_config()` 返回 `StopConfig` dataclass。
   - 顺带把 `_resolve_stop_and_build_loop` 的 17 参收窄为「`stop: StopConfig` + 矩阵 + ladder 数组」约 6-7 参。
   - 把 `build_backtest_loop` 的 41 参收窄为「`params: BacktestParams` + `stop: StopConfig` + 能力矩阵」约 3-5 参。
   - 风险: 需同步改 `builder.py` 的签名契约，`tests/test_engine_run_path.py` 有签名守卫，改完必跑全量测试。

2. **`build_backtest_loop` 签名收口**: 它内部已经在用 `BacktestParams` 打包（[backtest/loop/builder.py:77]），把签名里那 15 个资金/仓位参数收进 `BacktestParams`，签名立刻砍掉三分之一。

### P1（建议，独立小手术）

3. **`get_kline` 拆掉 `use_cache` 分支**: 缓存逻辑已经内聚在 `KlineCache`，可以让 `get_kline` 默认走缓存（内部 miss 时自动回源），或拆成两个明确命名的入口 `get_kline`（直拉）/ `get_kline_cached`（走缓存），不再用布尔开关分流。

4. **`executor.__init__` / `reconciler.__init__` 打包协作者**: 把十几个依赖收进一个 `Deps` 或 `Context` 结构体，构造函数参数压到 5 个以内。

### P2（可选，工程债）

5. **`book.apply_trade` 引入 `Trade` 值对象**: 9 个散参 → 1 个 `Trade` 对象，账本接口立刻变浅。

### 不建议动的

- `backtest/loop/` 子包本身: 分解已经很好，别为了"更浅"去过度抽象（违反 CLAUDE.md 铁律 8「如无必要勿增实体」）。
- `server.py` / `trade/api.py`: 端点多是契约面，不是深/浅问题，强行拆只会加转发层。

## 八、风险与边界

1. **本报告不评判业务正确性**: 深/浅模块是"接口质量"尺子，不是"功能对不对"尺子。41 参函数可能运行得完全正确，只是难维护、易错位。
2. **长参数列表 ≠ 一定坏**: `_resolve_stop_and_build_loop` 是"接口偏肥的深模块"，它内部真消化了复杂度。真正的病根是"内部已有 `BacktestParams` / `StopConfig` 却没用在签名上"这个错位。
3. **重构必须配测试**: `build_backtest_loop` 签名被 `tests/test_engine_run_path.py` 守卫锁定，动签名前先看清测试断言。
4. **trade/ 铁律约束**: CLAUDE.md 铁律 8 明确 gateway/store 两模块"契约面即接口面"例外，本文的反模式 4、5 若落在这些例外模块，需单独评估是否真有必要改。
