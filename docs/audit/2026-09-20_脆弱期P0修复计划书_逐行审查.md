## 3. 发现的问题

### P1 —— 实施前必须补进计划书

**P1-1 「CI 的 Test 步骤是史上首跑」要写进风险节**
- 实测证据：run #25 的 job 步骤为 Lint=failure / **Test=skipped**（GitHub API）。历次红全是 lint 短路，CI 里的 pytest 从未真正执行过。
- 影响：item 7 修绿 lint 后，CI 第一次跑 3166 个用例，几乎必然暴露 ubuntu/py3.11 特有的新失败（编码、路径分隔符、依赖缺失如 xtquant）。
- 计划书现状：§3.4 诚实边界只写了"pytest 步骤以 CI 实跑为准"，**不够显眼**。
- 修法：在 §5 风险表加一行："lint 修绿 ≠ CI 绿；Test 步骤史上首跑，预留一轮 CI 修红预算"。

**P1-2 看门狗判定必须处理 `monitor_healthy` 的三态 None**
- 实测：`monitor.is_healthy()` 在非连续竞价返回 **None**（monitor.py:228-230），JSON 里是 `null`。
- 当前安全只是因为 `TRADING_HOURS`（brain/sentiment_pipeline.py:33）与 `trading_session` 的 continuous 窗口（trade/monitor.py:66-89）**恰好同值** —— 两套独立定义，改一边就静默错位。
- 修法：`evaluate_watchdog` 显式约定 `monitor_healthy is None → 跳过健康判定（不误报）`；计划书 §3.2 补一条耦合依赖说明。

**P1-3 看门狗的失败计数 / 冷却状态存放位置没写**
- "连续 2 次失败才告警"需要一个跨调用计数器。计划书未指定存哪。
- 修法：写明用 `scheduler/__main__.py` 模块级变量（如 `_WATCHDOG_STATE = {"fails": 0, "last_alert_key": "", "last_alert_ts": 0.0}`）。进程重启重新计数 = 首次失败重新起算，行为可接受；测试可直接注入该 dict。

**P1-4 8080 探测端点未在计划书点名**
- 计划书只说"探 8080"。已验证可用端点是 `GET /api/status`（server.py:242）。
- 修法：计划书写明 `http://127.0.0.1:8080/api/status`（200 即活），与 8081 一样 timeout=3。

### P2 —— 建议（不阻塞开工）

1. **§1 背景表"工作区 50 条"与 §4"59 条"时间点不同**：建议 §1 加注"（审计开始时）"，§4 的 59 已含并发改动 + 计划书本身。不构成错误，但读者会困惑。
2. **item 5 的 `max_mb=50` 与 scheduler 先例不一致**：scheduler/__main__.py:381-382 用 `attach_file_logger` 默认 max_mb=100。建议要么统一 100，要么注释"trade 日志更密取 50"。
3. **item 9 需处理未跟踪目录展开**：`git status --porcelain` 对全未跟踪目录只报 `dir/`，拷贝 `new_files/` 时要递归展开目录；同时大文件（如图/数据）建议设上限并记 manifest 而不是硬拷。计划书写成实施注意点即可。
4. **item 4b 的 TradeApp property 读 `monitor._last_tick_ts` 是跨类访问私有成员**：组合根访问成员的私有字段在本项目有先例，可接受；建议在 property 上加一行注释说明"只读出口，monitor 不加公开方法守铁律 8"。

### P3 —— 观察（不改计划书）

1. `EVENT_QUOTE_SNAPSHOT` 是**无生产者的预留事件类型**（grep 全仓仅定义/列表/接线 3 处，无 put 点）。与本次无关，建议将来删除或接线。
2. 看门狗用 `stopped_on_purpose()` 整轮跳过，会**继承**该机制的既有边界：停止标记无 TTL、且 `status()` 里标记优先于心跳（health.py:72）。手工起 scheduler + 遗留标记的场景下看门狗会静默。接受，但值得知道。
3. 基线 2 红（test_policy_sources.py × 2）归因并发编辑半成品（news_search._FETCHERS 被改没了）。**并发侧收尾后必须复跑全量**，否则验收标准 2 无法判定。
