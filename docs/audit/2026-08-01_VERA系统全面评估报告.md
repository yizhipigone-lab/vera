# 🔍 VERA 系统全面评估报告

> **评估时间**: 2026-08-01
> **评估范围**: 全项目 293 个 Python 文件（~51,500 行）+ 前端 JS/HTML + 辅助模块
> **评估维度**: 功能完整性、代码冗余性、流程合理性、回测准确性、架构合理性、模块深浅性
> **评估方法**: 5 个并行 agent 独立探索 + 亲自阅读 30+ 关键文件

---

## 一、总体画像

VERA 是一个**个人量化交易系统**，分三大子系统：

| 子系统 | 核心模块 | 规模 | 状态 |
|---|---|---|---|
| **回测流水线** | `backtest/` + `pipeline/` + `selection/` + `core/` | ~13,000 行 | 核心成熟，正在收敛 |
| **实盘交易** | `trade/` + `trade_main.py` | ~5,200 行 | 生产级，架构优秀 |
| **Web 前端** | `server.py` + `web/`（单页应用） | ~1,700 行 Python + ~170KB JS | 功能完整，正在长肉 |
| **工具和实验** | `tools/`（65 个脚本） + `brain/` + `scheduler/` 等 | ~12,000 行 | 大量一次性脚本，冗余高 |

**测试**: 115 个测试文件，约 1,260 个测试函数，测试代码占总量 41%（~21,200 行）——对于个人项目来说覆盖度很高。

## 三、六维评估

### 3.1 功能完整性 ⭐⭐⭐⭐（8/10）

**已完成的**：
- 回测引擎：多周期（1d/5m/1m）、8 种止盈止损策略、因子过滤、基准对比、报告生成
- 选股系统：TDX 公式选股、多级缓存（L0/L1/L2 三层）、因子过滤、信号规则
- 实盘交易：订单生命周期、预埋单、动态止损、三方对账、急停开关、飞书通知
- Web UI：回测配置面板、体检页面、交易页签、研究页（政策+Brain）
- 管线：选股→回测→基准→报告全自动串联

**功能缺口**：

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| F1 | 实盘 Monitor 的持有天数未接入——时间止损/首日/条件时间止损在实盘端**永不触发** | [trade_main.py](trade_main.py) 实例化 Monitor 时未注入 `hold_days` | 🔴 实盘止损静默失效 |
| F2 | 预埋单交易日判定硬编码为 `True`——周末/节假日也尝试下单 | [trade_main.py:961-966](trade_main.py#L961) | 🔴 可能异常下单 |
| F3 | 板块缓存无 TTL | [core/data_cache.py](core/data_cache.py) 永久缓存 | server 不重启就看不到新股/退市 |
| F4 | 节假日日历未接入 | [trade/monitor.py:32](trade/monitor.py#L32) `trading_session` | 只判断周末+时刻 |
| F5 | 税费未计入实盘 | [trade/book.py:103](trade/book.py#L103) | P2 标记 |

**评价**: 核心功能完整，实盘端有几个已标记但未修的功能缺口，不算严重但放在实盘里有隐患。

### 3.2 代码冗余性 ⭐⭐⭐（6/10）

**最大的问题区域是 `tools/` 目录**——65 个脚本，大量重叠。

| 类型 | 严重度 | 具体表现 |
|---|---|---|
| **L0 缓存与 L2 缓存重复** | HIGH | `selection/selection_cache.py`（v1 整段缓存）和 `selection/signal_day_cache.py`（v2 按日缓存）存的是**同一份数据**，v1 被 v2 技术上替代但仍在管线中活跃使用 |
| **4 个缓存模块各自实现同一套样板** | HIGH | `selection_cache`/`signal_day_cache`/`universe_cache`/`matrix_cache` 各自实现 `blake2b` 哈希键 + `tmp+os.replace` 原子写重试 + mtime 排序 LRU 清理——每个文件约 40% 是重复样板 |
| **gs_* 脚本族 ~16 个重叠** | MEDIUM | `gs_5m_sweep.py` / `quantqq_5m_sweep.py` / `gs_1d_sweep.py` / `gs_top10_*` 等，无共享核心 |
| **`_deep_merge` 写了两遍** | MEDIUM | [utils/config_loader.py](utils/config_loader.py) 和 [trade/api.py](trade/api.py) |
| **涨停幅度规则写了两遍** | MEDIUM | [trade/executor.py](trade/executor.py) `limit_ratio` vs [backtest/engine.py](backtest/engine.py) `_limit_ratio_vector`（标记 TODO P2） |
| **`engine.py` 的 `run()` / `run_cached()` ~20 行重复** | MEDIUM | 止损配置解析 + `build_backtest_loop` 调用几乎一样 |
| **死代码** | MEDIUM | [selection/deduplicator.py](selection/deduplicator.py) (`pipeline.py` 引用了但从不调用)、[pipeline/state_manager.py](pipeline/state_manager.py)（从未实例化）、[preprocessor.py](preprocessor.py)（222 行，完全孤立） |
| **7 个缓存机制并存** | LOW | `data_cache`(内存) + `kline_cache`(磁盘) + `universe_cache`(L1) + `signal_day_cache`(L2) + `selection_cache`(L0) + `matrix_cache`(回测准备) + `formula_exit`(24h 盘) |

**评价**: 核心模块（backtest/trade）冗余控制得不差，但辅助模块（tools/ + 缓存层）冗余较高，积累的主要是"v1 做了一版，v2 没删 v1"的版本迭代债。

### 3.3 流程合理性 ⭐⭐⭐⭐（7.5/10）

**做得好的**：
- **缓存分层清晰**（即使有冗余）：数据层 (kline_cache) → 池层 (universe_cache/L1) → 信号层 (signal_day_cache/L2) → 回测准备层 (matrix_cache)，每层独立且失效策略不同
- **Pipeline 的 4 步串联干净**：选股→回测→基准→报告，每步独立异常边界
- **实盘事件流设计优秀**：单消费者线程 = 唯一写者，回调只做入队，零锁
- **trade/ 依赖注入纯粹**：模块间不互 import 单例，所有协作对象走构造函数注入
- **进度反馈双轨融合**：粗粒度 callback 与细粒度 `core/progress` 在 `/api/status` 做 max 融合、单调不回退

**可以改进的**：

| 问题 | 影响 |
|---|---|
| `trade_main.py`（1,039 行）超载——组合根 + 消费者线程控制器 + 重连状态机 + 自动买入功能 | 组合根被业务逻辑撑爆 |
| `server.py`（767 行）混合了路由定义 + 配置序列化/反序列化 + 管线编排 | 三件不同的事塞在一起 |
| `tools/` 不是 package（无 `__init__.py`） | 测试和工具脚本需要 `sys.path.insert` hack |
| `result_writer → server.py` 循环依赖 | 通过函数内 lazy import 破解，脆弱 |
| 因子过滤直接读 kline parquet 文件（绕过 `KlineCache` API） | kline 格式变了就静默炸 |
| WIP 提交 `64d4b86` 混了 engine/config/kline/web 四个不相关模块 | 历史脏提交 |

### 3.4 回测准确性 ⭐⭐⭐⭐（7.5/10）

**准确性保障**：

| 保障机制 | 位置 |
|---|---|
| **parity 测试锁死** | [tests/test_loop_parity.py](tests/test_loop_parity.py)（22 个测试）保证 loop 重构前后数字字节级一致；[tests/trade/test_exit_parity.py](tests/trade/test_exit_parity.py) 保证回测与实盘卖出规则一致 |

| **买入价铁律代码锁死** | [backtest/loop/entry.py](backtest/loop/entry.py) 显式声明 `ENTRY_PATH = EntryPath.BACKTEST_T_CLOSE` |
| **非标准 bar 过滤** | 过滤盘中临停导致异常 bar（48/240 根不变量守卫，1m 防踩坑保护） |
| **退市检测** | 基于原始未 ffill 的 close 自建 `tradable_np` |
| **扫描深度修复** | `_adaptive_scan_count` 回退到硬编码 3000（修复了 2026-07-23 引入的"历史回测丢前段信号"bug） |

**已知局限**：
- `engine.py` 文档自述："回测绝对值不可全信（方向系统性乐观），相对排序在同口径、含停牌/ST 少的策略里尚可参考"
- 系统综合评分 2026-07-13 为 7.5/10，后续多轮修复提升但**成交价乐观偏差、前视偏差等根本性乐观倾向仍存在**
- 浮点阈值比较**有意不用 epsilon**——设计决策而非 bug

**评价**: 在同口径相对排序层面可信度较高。绝对值不可全信——这是 VERA 的已知约束，不是意外发现。代码层面的保护（parity 测试 + 铁律锁死 + 退市检测）做得很扎实。

### 3.5 架构合理性 ⭐⭐⭐⭐（8/10）

**最强的部分 — `trade/` 实盘模块**：

这可能是整个项目里架构最漂亮的子系统：
- **真正的组合根模式**：`trade_main.py` 是唯一知道所有协作对象的地方
- **book.py 作为词汇表中枢**：xtquant 常量 + 订单状态机 + ETF 判定——6 个模块引用它但只读取常量
- **8 个深模块**：gateway / executor / reconciler / risk / monitor / store / signals / notifier
- **依赖注入极致**：每个模块的构造函数接受 callable 而非具体类
- **事件引擎简单干净**：`queue.Queue` + 单消费者线程，仅 136 行

**backtest/loop/ 拆解得也不错**：
- 8 种策略各自独立文件（Strategy 模式），`builder.py` 按 capability gating 过滤
- `TriggerPreFilter` 跳过 84.7% 的不可能触发持仓
- `ExitDispatcher` 做优先级排序，loop 只负责执行

**需要改进的**：

| 问题 | 影响 |
|---|---|
| `backtest/engine.py`（1,149 行）仍是最大单体——核心循环已抽出但自身仍是 god-orchestrator | 两个并行入口 `run()`/`run_cached()` 有配置解析漂移风险 |
| `_simulate_core_v3`（53 行兼容壳）只为 7 个测试活着 | 已有删除计划未执行 |
| `_entry_basis.py` 的 `LiveBiasEstimate` / `LIVE_T_PLUS_1_OPEN` 为不存在的 sim_trader 准备 | 纯脚手架 |
| `ENGINE_VERSION` 含义冲突：两处同名常量 | [backtest/engine.py](backtest/engine.py) vs [pipeline/result_writer.py](pipeline/result_writer.py) |
| `trade_main.py` 正在从"浅组合根"退化为"胖控制器" | 1,039 行中 ~230 行是自动买入业务逻辑 |
