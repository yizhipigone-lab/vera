# 2026-09-19 VERA 代码库架构审查报告

> 方法：4 个独立子代理分片深读（trade/ 实盘交易、backtest/+selection/+core/ 引擎侧、server+API+web 前端、scheduler/brain/notes_gen+存储横切面）+ 主会话 AST 全仓依赖扫描 + 定量摸底。所有结论均带文件:行号证据，未凭印象下判断。
> 规模基线：生产 Python 314 个文件 / 2.9MB（tests 另计）；前端 `index.html` 143KB + 14 个外部 JS；`tools/` 130 个脚本占 949KB。

## 〇、一句话总评（大白话）

VERA 像一栋**地基钢筋很好、但房间在不断加建**的房子：地基 —— 铁律用 AST 测试锁死、原子写统一原语、交易单写者、失败方向全单向 —— 是制度化的、机器在守，不靠自觉；问题出在**加建速度超过治理速度**：三个 80~111KB 的上帝文件、`tools/` 里 63% 的一次性脚本、以及多处"新机制上线了、旧写法没收编"的并存态。没有架构方向性错误，全是工程卫生与收口问题。

## 一、整体结构评价

### 1.1 依赖方向：健康（AST 全仓扫描实证）

- **红线全守住**：`core/market_*` 与 `core/market_dashboard_runner` 零 import trade；`trade/` 与 `trade_main.py` 零 import notes_gen；`brain/` 全包零 import trade/backtest（唯一接触是 `brain/sgpjbg_radar.py:87` 以 `mode=ro` 只读 trade.db）。
- trade/ 内部分层干净无循环：L0 内核（book/events/config）→ L1 基础设施（store/risk/gateway）→ L2 执行（executor/monitor/shadow）→ L3 特性（rotation/auto_buy/reconciler/analysis）→ L4 接口（api/decision_api）→ L5 组合根（trade_main.py）。
- engine/loop/pipeline 三层划分清楚：pipeline=编排+校验、engine=数据准备+能力拼装、loop=纯数值核心。

### 1.2 层级倒挂：4 处具体破口

| 破口 | 证据 | 性质 |
|---|---|---|
| 纯日历工具住在调度器包里，被 3 层 9 个文件"向上 import" | `scheduler/trading_calendar.py` 被 core 3 处（`kline_cache_maintenance.py:67`、`market_dashboard_runner.py:184/592`）、trade 6 处（`gateway.py:93`、`rotation.py:57`、`store.py:21`、`monitor.py:17`、`decision_api.py:26`、`decision_backfill.py:58`）引用 | **最该搬**：它是通用工具，应在 `utils/` 或 `core/` |
| IO 层横跨引擎层与工具层 | `core/market_position_runner.py:990` import `backtest.engine`、`:1331` import `backtest.metrics`、`:2068` import `tools.send_report_feishu` | 前两个是"不写第二份成本口径"的刻意取舍（可辩护），推送属投递职责越界 |
| 生产层反向依赖工具层 | `selection/factor_filter.py:20/84/109/118` import `tools.factor_ic_screen` | 工具被当成了库 |
| 编排层依赖工具层投递 | `notes_gen/daily.py:752`、`notes_gen/morning.py:242` import `tools.send_report_feishu` | 同上一类 |

### 1.3 进程拓扑与数据落盘

- 4 进程：server.py(8080) / trade_main.py(8081, EventEngine 单写者) / scheduler(12+1 个 job) / 外部 QMT。进程间几乎不直接通信：共享 sqlite 只读（`mode=ro`，WAL 下不互堵）+ 共享文件 + 前端跨端口 HTTP，出方向统一飞书 webhook。**协作机制少而清晰，这是优点**。
- 落盘：sqlite ×5（trade.db 14 表 / brain_dsh_runs / news_seen / sgpjbg_radar / kg graph.db 76MB）+ parquet 约 1.6 万文件 + jsonl 群。每份的写者/读者已普查，**唯一写者纪律大体成立**，例外见风险清单 P0-5/P0-6。

## 二、五个跨切片共性主题（本报告最重要的部分）

### 主题 A：「改造进行到一半」并存综合征

每个子系统都至少有一处"新机制已上线、旧写法没收编"：

- Web 层：`api.js:121` 的统一 `createTradeClient` 工厂写好了没人用，而 8081 地址在 5 处各自硬编码（`trade.js:19`、`analysis.js:8-9`（拼两次）、`decision.js:42`、`decision_util.mjs:268`、`mobile.html:215`）—— 9 月 19 日"404 被报成 8081 不可达"事故的同源温床。
- fetch 封装三套并存：`api.js` 统一 request()（只覆盖 module 页）、`trade.js:22-64` 自带副本、`mobile.html:271-276` 第三份；`esc()` 重复定义 7 处。
- 引擎侧：run/run_cached 双入口漂移大头已治（`_resolve_stop_and_build_loop`，engine.py:354-368），但残留 5 处"有意的不对称"靠人工纪律维持（formula_sell 取数只 run()、capabilities 三开关只 run_cached()、degrade_5m 只 run()、entry_price_mode 处理路径不同、ladder 排序口径不同）。
- API 错误响应四种形状并存（`success:False` dict / `JSONResponse(400)` lab_api.py:48 / `HTTPException` farm_api.py:30 / market_position_api.py:96 混用），无全局 exception handler。

**并存不是错误，但每个并存都是已爆过或会再爆的事故点。**

### 主题 B：铁律 8 管住了"接口面"，没管住"体积"

三个最大的文件都是"公开接口数合规、内部体量失控"：

| 文件 | 体量 | 职责数 | 接口合规性 |
|---|---|---|---|
| `core/market_position_runner.py` | 111KB / 2087 行 | **8 种**（采集落盘/ERP/牛熊区间/指标体检/影子回放/照镜子+分桶/体温表文案 `thermometer_md:1458` 单函数约 470 行/飞书推送） | 公开接口 8 个，正好顶格 |
| `trade/rotation.py` | 89KB / 1655 行 | **7 种**全混在 `RotationFeature` 一个类（39 个私有方法）：动量择腿+三份错峰簿记+在途买卖双台账+逐份止损+影子记录+迁移+取数降级链 | 公开 6 个，字面合规精神不合 |
| `trade_main.py` | 82KB | 组合根+15 事件 handler 合理，但约 200 行报告逻辑（`_notify_daily:1153-1253`）应下沉 `daily_report.py`（仅 128 行） | TradeApp 13 个公开方法 |

另有 6 个以上 trade/ 模块公开名超 8（executor 21、book 19、config 17、monitor 12、channel_manager 12、analysis 10）——**规矩与实现已脱节，像 2026-07-26 M7 裁决那样修文档口径或真拆，别留双轨**。

### 主题 C：单源纪律的残余破洞

"同一口径不写第二份"是全仓最强的一条纪律，且大多有测试锁，但仍有：

1. **4 个 sweep 工具复刻 engine 私有准备段**（`gs_5m_sweep.py:161-187`、`quantqq_1m_sweep.py:177-193`、`quantqq_5m_sweep.py:188-206`、`quantqq_5m_sweep_2010.py:256-272`）—— 同一段"取数→`_ensure_index`→`_drop_nonstandard`→`_build_entry_signals`→ffill→`_build_tradable_from_raw`"调用链写了 4 份，engine 准备段一改这 4 份**静默漂移**。这是最严重的一份重复。
2. 交易日历双源：`trade/analysis.py:217-226` 直读 kline_cache 的 parquet 日历，与全仓统一的 `scheduler.trading_calendar` 并存。
3. 涨停价表达式三处复制（`executor.py:379` / `auto_buy.py:352` / `closing_auction.py:41`）；`round_price` 双 import 路径（`auto_buy.py:39` 从 executor 进口，而 `executor.py:79` 只是 re-export book 的）。
4. `attr_gp1014.py:93-95` 运行时 monkeypatch `BacktestEngine._filter_limit_up`。
5. 缓存层 `_DEFAULT_TRUE_KEYS={"exclude_quit"}`（`selection_cache.py:53`）是手工维护名单，selector 再加同类键，7 月 27 日投毒事故的 P0-1 即复发；`universe_cache.py:53` 跨模块 import 私有名 `_normalize_universe`。

### 主题 D：跨进程/跨天协调靠"注释约定"

- **开机顺序**：`start_vera.bat`（行 36/41/45）同时拉起三进程，仅 rem 注释提醒"交易进程需要 miniQMT 已登录运行"—— 9 月 2 日冷启动 rc=-1 事故的根因未被脚本消化，**必复发**。
- **调度顺序**：15:45 缓存补尾段是后台线程+子进程 fire-and-forget（`scheduler/__main__.py:89-94` 自述"不阻塞调度循环"），15:50 采集**并不等它完成** —— "排在之后"只是注释约定 + 回归锁断言时刻，代码不强制完成关系。
- **重启纪律**（改 core/ 必须重启 server.py、模块级 HAS_AK 判定、trade_main 重启必须 ≥15:05）全部靠 CLAUDE.md 文字约定，无机器检查。

### 主题 E：事故驱动治理有效，但全是后置的

项目的测试锁几乎每把都是事故后加的（投毒→conftest 隔离、404 误报→契约测试、幽灵行→过滤代码）。锁的质量很高（`test_decision_wiring.mjs` 对修复前代码真红 9 项），但**前置防护**缺两块最值钱的：mobile/PC 双前端零契约测试（字段漂移防护为 0）、8081 写端点零鉴权。

## 四、值得肯定的设计（制度化的优点，别在整改中破坏）

1. **铁律用 AST 测试锁死**，不靠口头约定（`tests/test_market_position.py:476-484` 等）—— 本次扫描证实红线全守住。
2. **原子写公共原语**统一收编（`utils/parquet_cache`：pid+uuid 独立 tmp + atomic_replace + 统一 blake2b_key），三处缓存复用，双进程并发写不踩踏。
3. **失败方向全单向**：KillSwitch 读异常按激活（`risk.py:40-42`）、日亏基准缺失按亏（`risk.py:158`）、轮动台账"账本≥真实"、采集"宁可不写不可瞎写"—— fail-closed 哲学全仓一致。
4. **事故→范式→测试锁闭环**：决策台账三件套、`test_tab_wiring` 把页签接线变机器判据、缓存 SCHEMA_VERSION 显式失效不静默读旧。
5. **EventEngine**：有界队列+关键事件分级超时+丢弃留痕+handler 异常不死写者（`events.py:82-155`）。
6. **brain/ 隔离干净**：server 对 brain 全部请求内惰性 import + 异常兜底 + 子进程超时（`research_api.py:72-91`、`claude_cli.py:202-205`），大脑挂了不拖垮其他页签。
7. **调度状态持久化 + monthly 补发窗**，双发/断档两类事故都有实测修复闭环。
