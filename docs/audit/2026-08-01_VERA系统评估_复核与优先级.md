## 二、六维详评

### 2.1 功能完整性 7.5/10

核心链路 (选股→回测→基准→报告、订单生命周期/预埋/对账/急停/飞书) 完整且过了实盘验证。扣分集中在**实盘功能哑火**, 四条全是实测:

1. **三条时间类卖出规则实盘永不触发** (上轮 P0-1, 本会话已验证): `trade_main.py` 全文件无 `hold_days`, `monitor.py:72` 默认 `lambda: 0`; time_stop(≥20天)/cond_time(≥5天)/first_day(==1天) 全部为死规则。接线材料现成 (`trade/api.py:170` 的 `_hold_days` + 交易日历)。
2. **尾盘自动买入对三个板块定价失效** (07-31 实盘实测, 上轮报告没有): 创业板/科创板挂涨停价超 2% 价格笼子被交易主机暂存, 两天 **0/12** 零成交 (状态 50 不废单, 无任何告警); 沪主板"对手最优"市价单在收盘竞价被拒, 当天 **6/6 废单**——代码注释"沪市连续竞价到 15:00"的假设错误 (沪市 2018 年起收盘也是集合竞价)。深主板正常 (12/12)。
3. 次要缺口: `is_trading_day=True` 硬编码 (仅用于卖出闸, 暴露面小, 上轮定 🔴 偏重); 税费未计 (P2 标记); 节假日日历未接; `exclude_new_listings_days` 配置了但被静默忽略 (selector.py:143-146); StateManager 断点续跑全模块死代码。

### 2.2 代码冗余性 5/10 (最弱维)

核验后比上轮说的更重:

- **回测双入口重复 ~55 行** (stop 解析 24 + ATR 13 + build_loop 调用 20, engine.py:363-386/690-711 等), 已发生过一次漂移事故 (run() 缺 priority 校验)。
- **四个缓存模块同三套样板** (blake2b 键/tmp+os.replace 原子写/mtime LRU), 逐行级复制 ~150 行, 连 Windows 退避注释措辞都一致。
- **1d 场景 L0/L2 双写同一份 selections** (实测磁盘 472K+11M 并存)。修正上轮说法: 不是"v1 该删未删"——L2 只在 1d 生效, 5m/1m 只有 L0; 正确解是 L0 收缩为 period≠1d。
- **tools/ 研究垃圾场**: gs_* 族 16 个一次性灌入零迭代, 编排层互相克隆 (prep_all/prep_parallel 成对矛盾); 但"无共享核心"不准确 (gs_5m_sweep 等都 import quantqq_5m_sweep)。
- 死代码 ~15 处清单两报告一致 (preprocessor.py 222 行孤立、_fetch_prices、StateManager、Deduplicator、5 个零引用函数等)。
- 涨停幅度规则两处实现**口径已漂移** (回测用 TDX IsSTGP 真实标记, 实盘靠外部传 bool)。

### 2.3 流程合理性 7.5/10

强项实测成立: pipeline 每层异常回退实算不中断; 缓存接缝位置正确 (L2 在 selector 内, 调用方自动受益); 实盘事件流单写者零锁; 进度双轨融合单调不回退。

扣分: `trade_main.py` (1039 行) 组合根被 auto_buy (~230 行) + 重连状态机撑成胖控制器; `server.py` (767 行) 五件事一个文件; **事件队列满时关键事件与 tick 同等被丢** (07-31 实测: 丢 reconcile 1 + sync_reports 31 + timer_scan 548); 撤单 ack 2s 阈值实测 87% 超时; tools prep 串/并行矛盾版并存; pipeline 日志编号 "[Step n/5]" 与实际 6 步不符。

### 2.4 回测准确性 7/10

保护机制密集且真实 (76 项相关测试全过): 信号日数据缺失丢弃不顺延、formula 卖出 lag 1 bar、停牌 NaN 暴露、分钟级非标准 bar 过滤、佣金/滑点/印花税全开、degrade_5m 多重守卫+影响量化披露、matrix 缓存指纹失效保守正确。

**两项扣分都是本轮新信息**:
1. **回归保护网退化**: legacy 甲骨文 07-23 删除后, test_loop_parity 从"字节级一致"退化为形状断言 (注释四处 "legacy removed"), docs 建议的"删前转快照 parity"未执行——目前无基线快照对比, 重构回归保护有洞。
2. ST 口径漂移 (见 2.2 末条)。
已知系统性乐观 (信号日 T 收盘成交、止损按线价成交) 是明示的设计决策, 不扣分但不可忘; `LiveBiasEstimate` 补偿工具存在未接线。

### 2.5 架构合理性 8/10 (最强维, 与上轮持平)

实测成立的教科书级: trade/ 组合根 + 全构造函数注入 (callable 而非具体类); trade/api.py 独立 8081 薄层 app 与 server.py 完全解耦, 职责划分干净; backtest/loop/ Strategy 模式拆解; 辅助模块 (brain/kg/scheduler 等) 与主干单方向松耦合 (6 条边多为 lazy import)。

扣分: server.py god-file; trade_main 胖化; **server.py:137 sys.path 注入 tools/ 再 import lab_runner**——生产 web 服务反向依赖研究脚本目录, 是明确的架构破口; result_writer→server 循环依赖靠函数内 lazy import 兜底。

### 2.6 模块深浅性 7.5/10

深模块意识真实且普遍: signals.py (65 行藏 TDX 全链路)、四个缓存文件 (小接口藏原子写/退避/LRU)、matrix_cache 指纹失效、degrade_5m 纯函数、loop/strategies 每文件 28-61 行单一职责、events.py 136 行。

与上轮的分歧:
- 上轮深浅表"公开方法数"系统性失实 (store 写 3 实际 22 def/15+ 公开; executor 写 3 实际 9+; gateway 写 10 实际 11)——store/gateway 本就超铁律 8 红线 (上轮审计 M7 记录在案的例外)。深浅意识值得 8 分, 但用假数字撑到 8.5 不行。
- `core/data_cache.py` 63 行纯 getter/setter 浅封装 (接口与实现同宽); evolution/notes_gen/llm/concept_kb 4 个"package"各包一个浅文件, 目录开销大于收益。

## 三、对上轮报告的核验结论 (摘要)

8 条抽样指控 **6 条属实、2 条部分失实、若干数字不准**:
- 失实①: "parity 字节级锁死"——已退化 (见 2.4)。
- 失实②: "gs_* 无共享核心"——存在非正规共享 (import quantqq_5m_sweep)。
- 数字修正: run/run_cached 重复 ~55 行 (非 20); server.py 未使用 import 6 个 (非 8); trade/ 13 个文件 (方法说明写 14)。
- 判断修正: P0-2 (is_trading_day) 定 🔴 偏重, 实际 M; L0/L2 是"1d 双写"而非"v1 该删未删"。
- 上轮 P0-1 (hold_days) 与 P0-3 (webhook 明文) **经本会话独立验证属实, 且 P0-1 比上轮写的更重**——它是回测-实盘 parity 的静默大洞。

## 五、结论

与上轮"局部很漂亮、整体在收敛"的判断一致, 但修正两点: ①回测回归保护网没有上轮说的那么牢 (parity 已退化); ②实盘的问题不在架构在**功能哑火**——三条卖出规则从没活过、尾盘买入对三个板块基本无效, 这些只有跑实盘数据才看得见, 静态评估发现不了。

P0 六项全部是实测/已验证的小改, 无架构障碍; 建议按 P0 → P1 顺序执行, P0-1/2/6 与 H1/H4 可一个批次做完。
