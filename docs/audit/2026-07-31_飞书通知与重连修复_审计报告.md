## 一、审计对象

本次改动两块功能：
1. **飞书 webhook 通知**：成交提醒（买/卖）+ 盘后日报，互动卡片，URL 走环境变量，设置面板开关。
2. **重连死锁修复（方案C）**：`_on_connection_lost` 的 `while True` 改成 `_try_reconnect` + `_on_scan` 接力，消除消费者线程死锁。
3. **飞书补记路径**：成交回调丢失走 sync_reports 补记时也发飞书。

涉及文件：`trade/notifier.py`(新)、`trade/config.py`、`trade/executor.py`、`trade_main.py`、`trade/reconciler.py`、`web/index.html`、`web/js/trade.js`、`tests/trade/test_notifier.py`(新)、`tests/trade/test_e2e_trade.py`、`tests/trade/test_reconciler.py`。

## 四、HIGH 级发现

### H1【功能·已交叉验证】清仓卖出丢失"盈亏%"

- **证据**：
  - `trade/book.py:188-189`：`apply_trade` 卖出后 `if pos.volume == 0: pos.avg_cost = 0.0` —— 清仓即清零成本。
  - `trade_main.py:518-520`：`_notify_fill` 在 `apply_trade` **之后**取 `avg_cost = pos.avg_cost`，清仓时 =0.0 → `if avg_cost > 0` 为假 → `pnl_pct = None`。
  - `notifier.py:155-157`：`pnl_pct is None` 时卡片跳过盈亏行。
- **后果**：所有清仓类卖出（硬止损一刀砍光、时间止损清仓、阶梯清仓档 ratio≥1.0、移动止盈清空小仓、人工全卖）——恰恰是用户最在乎盈亏的场景——飞书卡片独独缺盈亏%。违背明文要求 #1。
- **现有测试盲区**：`test_notifier.py:83`（_build_fill_card sell）和 `:230`（E2E 阶梯）都用部分卖（ratio 0.33，余 700），**没覆盖 volume→0**，故全绿却漏 bug。
- **修复方向**：`_on_trade` 在 `apply_trade` **之前**快照 `avg_cost`，传给 `_notify_fill`（而非 apply 后再取）。补一条清仓卖出 E2E 测试断言含盈亏%。

### H2【测试】_on_scan 接力重连"成功"分支零覆盖

- **证据**：方案C 的核心恢复通道是 `_on_scan`（trade_main.py:540-542）检测 `_reconnect_pending` 后调 `_try_reconnect`。现有测：①立即成功（test_e2e_trade.py:201/284，FakeGateway connect 立即成功，**绕过接力**）；②持续失败不卡死（:333-351，bomb 永远 raise，**接力分支被执行但永不到成功**）。
- **漏掉的真实剧本**：connect 失败 N 次 → 第 N+1 次 `_on_scan` 接力 → 成功 → 重新订阅+对账。这是 QMT 实际"断线几分钟后恢复"的主路径，**无任何测试**。
- **风险**：若有人改坏接力（_reconnect_pending 失败后未保持 True、backoff 永不 reset、_on_scan 早 return），现有测全绿但生产会永久卡死——0731 event_dropped 重演。
- **修复方向**：补一个测——connect 先失败 1 次 → 恢复 connect → _put_scan → 断言 connected=True + reconnect audit。

## 五、MEDIUM 级发现

### 架构
- **M-架1**：`reconciler.py:77,95-96` 的 `fill_reason` 参数是**死代码**（_adopt 改用 pop_fill_context+reason_from_ctx 后无人调 _fill_reason），注释"兼容保留"误导维护者以为有 fallback。建议删除或改注释。

### 功能
- **M-功1**：15:05 后重启走补偿 EOD（trade_main.py:352-360）会发一份"零盈亏"日报（baseline 刚用当前 total_asset 设，差值≈0），是启动噪声。
- **M-功2**：notifier docstring 承诺"URL 缺失启动告警一次"，实际 `_warn_no_url_once`（notifier.py:105-109）只在 notify_fill/notify_daily 调，`start()` 不调 → 用户忘设 URL 时要到当天首笔成交才告警。建议 start() 主动 warn。
- **M-功3**：部成第二笔 pop 不到 ctx（pop 取即删）→ trades.reason 空 + 卡片 label 回退。成交记录页同一委托两笔第一笔有原因第二笔空，体验割裂。
- **M-功4**：`_day_baseline`（trade_main.py:309）是"启动时点"总资产，盘中重启会吃掉上午盈亏。语义上"当日盈亏"应锚昨日收盘。

### 测试
- **M-测1**：买入实时通知 E2E 漏测（_on_trade 买入路径 + _notify_fill is_buy 分支只单测直调，未端到端；现有 E2E 全是卖出）。
- **M-测2**：手工单（order_id 不在本地订单簿）补记通知漏测（test_e2e_backfill_adoption_notifies 注入的是系统单 order_id）。
- **M-测3**：`FeishuConfig`/`_coerce_feishu`（config.py:383-394）**零测试覆盖**，其余配置段都有 _coerce_* 测试唯独 feishu 缺。
- **M-测4**：EOD 日报 E2E 只断言"字段存在"，不断言盈亏数值/市值（test_notifier.py:258-275）。
- **M-测5**：配置热更新 feishu.enabled 运行中切换漏测（test_disabled_is_noop 用静态 lambda，没测 True→False 热切换）。

## 六、LOW 级发现（汇总，建议打磨期处理）

- 架构 L1：`notifier.py:35` DIRECTION_BUY=23 硬编码（应 lazy import book 或加 assert）。
- 架构 L2：_try_reconnect 单次最坏 5s 阻塞消费者（方案C 有意权衡，可接受）。
- 架构 L3：主线程 reconcile 读 book 与消费者并发（既有模式，本次未放大）。
- 功能 L1：日报无基准（day_pnl is None）显示红色，应中性色（notifier.py:242）。
- 功能 L2：monitor 兜底阶梯（未预埋路径）只挂 label 不带 tier/比例，卡片文案与预埋路径不统一。
- 功能 L3：_build_fill_card 重复兜底算 amount（无害冗余）。
- 测试 L1：notifier.stop drain 语义无测。L2：触达 _engine._queue 私有属性（轻度脆性）。L3：test_adopt_backfill 用 stub lambda 锁不了真实 _reason_from_ctx。L4：register/pop_fill_context 容量上限（_FILL_CONTEXT_CAP=1000 丢最老）无测。L5：no_url 测用固定 sleep 非 _wait。

## 七、额外隐患（主动反思）

1. **并行会话改动叠加风险**：审计期间 trade_main.py/executor.py/test_notifier.py 又被并行改（加了 `_detail_from_reason` 自然语言全文 + 对应测试）。两路改动同处 `_on_trade`/`_reason_from_ctx` 区域，若并行会话也动 `_notify_fill` 的 avg_cost 取数时序，可能与 H1 修复撞车。建议 H1 修复前先 `git status` 对齐基线。
2. **回调丢失是常态，补记通知成主路径**：今天 09:30/09:38/10:38 三笔成交回调 100% 丢失。这意味着飞书成交提醒**实际主要靠补记路径**（3 分钟延迟）。用户感知的"实时"其实是"≤3 分钟"。可接受但应在文档明示。
3. **webhook URL 半密钥落在系统环境变量**：用户选了系统环境变量（不进 git，正确），但意味着换机/重装要重设，且进程继承依赖启动方式。建议在 CLAUDE.md 或运维清单记录这个依赖。

## 八、通过项（明确肯定）

- **四条铁律全部保住**（架构审计逐条取证）：QMT 唯一真相源/回调只入队/单写者/如无必要勿增实体。
- notifier 线程模型严谨：生产侧 put_nowait 零阻塞、worker 异常隔离、队列满/无URL/禁用三重 fail-soft、start 幂等不起双 worker、stop 有上限不死等。
- 重连方案C 真正消除死锁（0731 event_dropped 实证驱动），不碰 kill_switch（铁律7），靠 connected+reconciled 挡交易，恢复后自动对账。
- 可回滚性完整：DB schema ALTER 幂等、INSERT 双向兼容、无文件覆盖/迁移。
- 配置开关前后端往返一致，热生效（lambda 闭包读 self._cfg）。
- label 映射穷举锁定，覆盖 monitor 全部 6 个 reason 前缀 + manual。
- 端到端测高质量：阶梯卖出卡（档位/剩余 700 内容级断言）、worker 三连失败仍消费空、补记路径 ctx 端到端流到卡片。
