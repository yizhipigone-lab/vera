## 三、建议尽快修的两条

### 1（高）补下载后不复检新鲜度 → 这次修复只修了一半

- 现象：重取一次之后，代码只判断「有没有数据」`[trade/gateway.py:473-476]`、`[trade/gateway.py:626-628]`。
  如果补下载失败、或者数据源当天就是没给当日那根，返回值仍是**陈旧序列**，而且**不给调用方任何标记**。
- 为什么危险：下游 `[trade/rotation.py:122-125]` 算动量时**只数根数、不看日期**——最后一根还停在
  9月14日的序列，照样被当成新鲜数据算动量参照点（动量参照点 = 算动量时用来对比的那根历史收盘价）。
  于是「静默污染」这件事并没有被彻底堵死，只是概率变小了，而这次的改动说明文字会让人以为已经修好。
- 建议改法（最小）：补下载之后把 `_should_download_history` **再算一次**；若仍然是「需要下载」，
  记一条 WARN 并在返回值上带「仍陈旧」标记，由调用方决策（轮动侧可以据此降级数据源或 fail-closed）。

### 2（中高）防抖时间戳写在下载之前，一次失败压住 600 秒

- 现象：`[trade/gateway.py:440]` 在**返回「要下载」的同一刻**就把时间戳写进 `_refresh_ts`
  （该字典只在 `[trade/gateway.py:243]` 声明、`[trade/gateway.py:437]` 读取、`:440` 写入，无第二处回滚），
  而真正的下载发生在调用方 `[trade/gateway.py:465]`，失败只打一条日志 `[trade/gateway.py:467-468]`。
- 后果：一次下载失败 = 这个代码 600 秒内不再尝试；如果轮动当天只跑一次，等于**当天就不补了**，
  继续用陈旧序列（叠加第 1 条，就是「补不动 + 不校验」）。
- 建议改法（最小）：把 `self._refresh_ts[code] = now_ts` 从判定函数里挪到**调用方下载成功之后**；
  失败路径不写戳，下次调用可以立刻重试。

## 六、机器校验的局限（本次实例）

`[docs/audit/_verify_references.py:100]` 的校验只做两件事：**文件存在** + **行号在文件行数范围内**，
它**查不出**「行号落在范围内、但语义张冠李戴」。本次 B2 就是活例子：子智能体引用
`[trade/gateway.py:793]` 说「区间查询恒返回空」，而 793 行其实是 `query_daily_closes`
（区间查询在 `[trade/gateway.py:799-803]`）——行号在范围内，机器校验会判 PASS。
**所以机器校验是兜底，逐条 read 原文仍是最后一道。**

## 附：本次实验数据（并行 vs 串行派发，仅供方法参考）

同一批提示词、同一台机器、同一个模型通道，先跑并行臂、再跑串行臂（这样提示词缓存与连接预热的
便宜都归给后跑的串行臂，属于对并行不利的保守设计）：

| 项目 | 数值 |
|---|---|
| 并行臂墙钟时间 | 73.9 秒 |
| 串行臂墙钟时间 | 117.6 秒 |
| 加速比 | 约 1.59 倍（理论最优 3 倍） |
| 三个助手耗时（并行） | 34.8 / 52.4 / 73.9 秒（三段时间区间确实互相重叠） |
| 三个助手耗时（串行） | 55.8 / 35.3 / 26.5 秒（越跑越快 = 吃到了缓存与预热） |
| 三个助手耗时之和（并行臂） | 161.1 秒（总计算量）；墙钟只等于最慢的那一个 |

**读法**: 并行省的是墙钟时间，不省计算量；加速比由**最慢的那个任务**决定（木桶效应）。
任务之间有先后依赖时，并行收益为 0。
