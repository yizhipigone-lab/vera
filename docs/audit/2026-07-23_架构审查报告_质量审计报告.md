## 🏛️ 架构分析师发现

### HIGH-1: 候选 3（删除 legacy shell）严重低估影响范围

**证据**: `grep "_simulate_core_v3" --include="*.py" -rl` 返回 25+ 文件。

`_simulate_core_v3` 的直接调用方：
- **生产路径**: `BacktestEngine.run()` (engine.py:1054) + `BacktestEngine.run_cached()` (engine.py:1289) — 各传 ~30 个位置参数
- **工具脚本**: `tools/bench_engine_speed.py` + `tools/benchmark_perf.py` — 直接 `from backtest.engine import _simulate_core_v3`
- **测试文件**: ~15 个测试文件直接导入/调用/ monkeypatch 它（test_loop_parity, test_priority_switch, test_end_to_end_formula_sell, test_dual_trigger, test_gap_and_delist_nan, test_loop_perf, test_prefilter, test_run_cached_parity, test_real_parity, test_degrade_5m, test_engine_5m_window, test_matrix_cache, test_window_end_clip, test_engine_run_path）

报告中写 "Delete ~540 lines" **完全没有提及**需要同步修改 15+ 测试文件和 2 个工具脚本。这不是简单删除，是需要迁移计划的跨模块重构。

**严重级别**: HIGH（报告建议不完整，可能导致读者低估工作量）

### HIGH-2: 报告缺少任何候选的风险分析

所有 5 个候选都没有讨论实施风险。例如：
- 候选 1（拆分前端）：项目没有 JS 构建系统，拆分后如何加载模块？需要引入 ES modules 还是 bundler？
- 候选 3（删除 legacy）：见 HIGH-1
- 候选 4（tools common）：引入共享模块会耦合独立子进程，与 TDX 连接隔离的设计意图冲突

**严重级别**: HIGH（架构建议不完整，缺少 trade-off 分析）

### MEDIUM-1: 候选 4 "43 scripts" 与候选 5 的评估基于不完整信息

候选 4 建议 `tools/common/`，但未讨论 tools 层的子进程隔离设计意图。`formula_lab.py` 用 `subprocess.run()` 隔离 TDX 连接是刻意的架构选择——共享模块可能无意间破坏这个隔离。

候选 5 的 "duplicated connector seam" 实际上已被测试覆盖（`test_data_fetcher_connector.py` 测 DataFetcher，`test_pipeline_mock_integration.py` 两个都测，`conftest.py` 两处 reset），"Speculative" 标签合理但论据可以更强。

### MEDIUM-2: `_simulate_core_v3` 壳描述不精确

报告 Candidate 3 里写 "entire body is one delegate call to build_backtest_loop"。实际壳体做了：
1. `from backtest.loop import build_backtest_loop` (import)
2. `loop = build_backtest_loop(...)` (构造)
3. `_LAST_LOOP = loop` (赋值给模块级变量，供 `run()` 读期末未平仓)
4. `return loop.run(...)` (运行 + 返回)

这是两次函数调用 + 一次副作用赋值。虽不影响核心论据（壳确实是浅模块），但表述应精确。

## 🤔 穷举"我额外想到的隐患"

### 隐患 1: 候选 1 实施后 vera-ui.js 变成多文件但没有构建系统
VERA 前端目前是纯 HTML + 单 JS 文件，零构建步骤。拆成 4+ 个 .js 文件后，需要 `<script type="module">` 或手动拼接加载顺序。引入构建系统（Vite/esbuild）是另一项工程决策，报告没提这个隐含成本。

### 隐患 2: 候选 3 删除 legacy 后 `_LAST_LOOP` 全局变量仍需处理
`_LAST_LOOP` (engine.py:45) 是模块级可变全局变量，供 `run()` 路径读 `loop.final_positions`。如果删除壳（壳里写 `_LAST_LOOP = loop`），这个全局变量需要在新的引擎接口里重新安置，不能直接丢掉——否则期末未平仓功能会静默断掉。

### 隐患 3: 候选 2（server 拆分）可能引入循环 import
将路由拆成独立模块后，`config_router.py` 需要引用 `StrategyConfig` 和 `_config_to_yaml_dict`，`backtest_router.py` 需要引用 `pipeline_status` 和 `_run_lock`，`lab_router.py` 需要引用 `lab_status`。如果这些模块之间互相 import，可能引入循环依赖。报告没提这个风险。

### 隐患 4: 报告没讨论"哪些候选人可以并行做、哪些必须串行"
候选 2（server 拆分）和候选 1（前端拆分）基本独立，可以并行。候选 3（删除 legacy）会影响候选 4（tools common）里的 bench_engine_speed 和 benchmark_perf，需要先做候选 3。但报告没有给实施顺序建议。

### 隐患 5: 报告在 temp 目录，用户未必能持久访问
Windows temp 目录（`%TEMP%`）的文件可能被系统清理。报告没有存一份到项目 `docs/` 下作为审计记录。
