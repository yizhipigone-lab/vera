# VERA 实盘交易系统计划书

> 版本:v1.0 · 2026-07-26
> 依据:`docs/2026-07-26_三项目回测与交易系统对比研究.md` 及后续四轮专题深挖(MQ 预埋单机制、QP 卖出执行路径、模块深浅、条件单设计)
> 设计原则:**简洁、专业、准确。如无必要,勿增实体。**

---

## 一、目标与边界

**目标**:一个单进程 Python 实盘交易系统,对接 QMT(miniQMT/xtquant),实现"信号/持仓 → 自动卖出管理 → 半自动买入"的闭环,与 VERA 回测共用同一份卖出规则与铁律口径。

**MVP 明确不做**(每一条都有理由):

| 不做 | 理由 |
|---|---|
| 税费/手续费计算 | 用户决定:MVP 先通,成交原始数据落盘,事后可回溯补算 |
| 微服务/多进程 | MQ 的 4 进程 3 语言是最大的复杂度税;单进程后回调即函数调用 |
| Redis/消息中间件 | SQLite 官方选型树三条全不满足(无网络隔离/无多写者/无 TB 数据) |
| DI 框架 | 手写 composition root + 构造函数注入(vnpy/freqtrade 均如此) |
| LLM 参与交易链路 | 延迟、不可复现、不可回测;研究侧用途另行评估 |
| 模拟盘与实盘共用回报链(dry-run) | QP 教训:每条资金路径多一个分支,性价比最差的复杂度。注意区分:Fake SDK 是仅存在于 tests/ 的测试替身,生产代码零分支,不是 dry-run |
| 信号驱动全自动买入 | P2 再做;MVP 买入走"人工确认 + 风控闸门" |

## 二、架构总览

```
┌──────────────────────────── 单进程 ───────────────────────────┐
│                                                                │
│  xtquant 回调线程 ──put──┐                                     │
│  行情订阅回调线程 ──put──┤                                     │
│  定时器线程 ────────put──┼──► EventEngine(queue + 单消费者线程)│
│  Web/CLI 命令 ──────put──┘         │  唯一写者                  │
│                                    ▼                           │
│        ┌──────┬──────┬────────┬───────────┬─────────┐         │
│        │ book │ fsm  │executor│reconciler │ risk/kill│         │
│        └──┬───┴──────┴────────┴───────────┴─────────┘         │
│           │ 读                              写                 │
│        FastAPI/Web(只读快照 + 发命令)      store(SQLite+JSONL) │
│                                                                │
│  gateway.py = 唯一 import xtquant 的地方(含 Fake SDK)          │
└────────────────────────────────────────────────────────────────┘
```

**线程模型(核心决策)**:所有交易状态只有一个写者——EventEngine 的消费者线程。QMT 同步调用在该线程内直接调(带超时),不需要 asyncio,不需要业务锁。Web 侧用 SQLite WAL 的只读连接读快照,命令一律 put 进队列。这是 vnpy EventEngine 模式,比 QP 的 asyncio+多线程池简单一整档,且从结构上消灭了 QP 踩过的 DB 并发段错误、事件循环阻塞两类事故。

## 三、模块划分(深模块优先,每个模块藏住一个设计决策)

新包 `trade/`,9 个模块。接口方法数即封装质量的晴雨表:超过 ~8 个公开方法就是设计警报(QP store.py 44 方法的教训)。**例外(2026-07-26 审计 M7 裁决)**:gateway/store 两个基础设施模块不受此限——gateway 的抽象方法就是柜台契约本身,store 的方法是持久化契约,拆成多个类只会加转发层(浅模块),其余模块仍守 ≤8。

| 模块 | 藏住的设计决策 | 公开接口 | 设计来源 |
|---|---|---|---|
| `gateway.py` | xtquant 协议、回调注册、重连、Fake SDK | connect/order/cancel/query_* ≈6 | MQ sdk_adapter 接缝 + vnpy BaseGateway。**Fake SDK 第一天就建**,无 QMT 环境可跑全量测试 |
| `events.py` | 线程模型(单消费者串行) | put/start/stop | vnpy EventEngine;事件类型常量集中此文件;**启动时一次性静态接线,无运行时注册/注销**(订阅者集合翻一个文件即知,杜绝"忘订阅静默失败");订阅侧不得回发事件(防事件链) |
| `book.py` | 本地账本:持仓视图、策略归属、成本口径、档位状态;订单状态机(48→50→56/57,终态不可逆,纯函数) | snapshot/apply_fill/tier_state/transition 等 ≈7 | QMT 为唯一真相源,本地只存 QMT 不知道的事;状态机用 xtquant 官方枚举,纯函数易测 |
| `executor.py` | 预埋单管理、撤单流水线、价格阶梯 | place_ladder/execute_exit/cancel_all ≈5 | MQ prepareSellAction + QP 追价重挂(见 §5) |
| `monitor.py` | 行情订阅+心跳+轮询降级、动态规则评估 | start/stop | QP 双驱动(但我们是真接线)+ 共享规则核心(见 §6) |
| `reconciler.py` | 三方对账规则 | reconcile() **1 个方法** | QP reconciler:QMT 实时 vs 本地账本 vs 成交还原;只告警+熔断,**永不自动改账** |
| `risk.py` | 事前风控闸门 + 急停(三重态:内存/DB/文件任一生效,只许人工解除) | check(intent)/activate/deactivate/is_active | QP risk_gate(加闸门不改签名)+ kill_switch;4 道闸 + 买入 sizing 校验(见 §7,2026-07-26 裁决②砍集中度) |
| `store.py` | SQLite(WAL 模式)+ 原始回报 JSONL 先落盘 | save_*/load_* ≈6 | freqtrade SQLite 实践;替代 QP 的自研 WAL 叠 DuckDB(过度设计) |
| `api.py` | HTTP/WS 协议转换(刻意的薄层) | FastAPI 路由 | 读快照+发命令,零业务逻辑;传话层在这里是**正确**的。2026-07-26 增设面板:`GET/PUT /api/trade/config`(校验复用 load_trade_config 同一份逻辑,深合并语义防面板误清账号,消费者线程热替换) |

**组装**:入口 `trade_main.py` 是唯一 composition root——所有依赖关系看 `__init__` 签名即知,禁止模块互 import 单例,禁止 `_state` 式全局注册表(QP 的弯路)。

**反模式红线**(写进 CLAUDE.md):不按"开盘/盘中/收盘"切模块(temporal decomposition);不加 Manager/Facade 转发层;不出现 `utils.py`/`helpers.py`;规则、成本、状态码映射全项目各只有一份。

## 四、每日生命周期(一条时间线看懂系统)

```
盘前  连接QMT → 启动对账(全量:持仓/资产/在途单)→ 一致才放行
09:15-09:20  挂预埋单(全档位限价,见 §5.1)
09:20-09:25  不挂不撤(交易所不收撤单)
盘中  订阅驱动监控 + 心跳 + 定时对账(09:35/11:30/14:55)
14:57 未成交的必卖单 → 对手最优(逃生通道)
15:05 收盘对账 → 预埋单标记过期 → EOD 归档
任何时刻  kill switch 三重态任一生效 → 全面拒单;断线 → 指数退避重连 → 重新订阅 → 全量对账
```

## 五、核心机制设计

### 5.1 条件单 = 预埋单 + 监控腿,各管一段

静态价位规则(阶梯止盈,成本×固定比例)→ **预埋限价单**;动态状态规则(移动止盈、成本止损、时间止损、条件时间止盈、首日规则)→ **监控腿**。依据:交易所只支持限价/市价申报,无原生条件单;预埋单有排队时间优先权、零监控延迟、程序崩溃照常在券商端成交。

**规则复刻裁决(2026-07-26 用户裁决①)**:实盘止盈止损**复刻回测完整内容**——参数结构与 `config/default.yaml` 的 `stop_loss` 同形(priority/cost_stop/trailing_stop 含 activation/ladder_tp/time_stop/cond_time_stop/first_day),语义逐条对齐 `backtest/loop/strategies/`,`tests/trade/test_exit_parity.py` 锁死(六规则 + priority 调度,对齐口径见测试头注)。监控腿的 ladder 评估只对**未预埋档**兜底(超涨停跳过/风控拒的档),已预埋档由券商端成交,防双卖;trailing_first 双触发的部分卖由预埋单承担。formula_sell 留 P2(实盘盘中跑公式引擎,重)。

**预埋单规则**(融合讨论结论):
- 9:15–9:20 依据盘前对账后的持仓,**全档位一次性挂出**(档位间无依赖,消灭 MQ 的"成交推进"逻辑);
- 档位价 > 当日涨停价 → 今日跳过该档(不可能成交,挂了只会废单;涨停幅度按板块:主板 10/科创创业 20/北交所 30/ST 5%,复用 VERA 回测的涨停映射);
- 价格 = 成本 × (1+比例),0.01 对齐;
- 日终自动过期,本地标记,次日重挂。

**监控腿触发后执行**(撤单流水线 + 两级价格阶梯):

```
触发 → 清仓锁(env,account,code,TTL 300s,order_id 反查)
     → 撤该股全部预埋单 → 等 ack(2s 告警重试,正常 <1s)
     → 限价=买一价 卖出(立即成交+价格地板,锚定最新买一,天然避开 2% 价格笼子)
     → 5s 未成交 或 ≥14:57:对手最优(逃生通道)
```

**逃生通道市场感知(2026-07-27 实测, 审计 V5 勾销)**:深市 14:57–15:00 收盘集合竞价**只收限价单**(当日五张深市"对手最优"市价单全废单);沪市连续竞价到 15:00 可市价单。故 ≥14:57 的升级:深市**买挂涨停价/卖挂跌停价**(收盘竞价单一价格撮合,挂极限价=最大成交优先权,成交价仍是收盘价,不吃亏),沪市维持对手最优。尾盘自动买入的定价分支同口径(卖一价限价 → SZ 涨停价限价 / SH 对手最优)。

追价多级阶梯(让 1 跳再追)移到 P3:等真实成交数据证明滑点值得再补,不猜。

- 占券空窗无双卖风险:预埋单冻结可用数量,重复卖单会被券商拒收(天然保险);
- 跳空低开:预埋单处理不了,由止损腿接管,文档明示,不假装全能;
- 行情故障 → fail-closed:本轮不动作+告警,宁可不卖,不可瞎卖(QP 教训:不返回空持仓冒充"无命中")。

### 5.2 行情:订阅为主、心跳探活、轮询兜底

xtdata 订阅推送(回调只 put 队列)→ 开盘时段 15s 无 tick 判定不健康 → 降级 QMT 轮询。对账用低频全量轮询(每日 4 时点),天然自愈推送丢失。腾讯行情兜底移到 P3:QMT 行情断时交易大概率同断(QMT 行情与交易同客户端),救命窗口窄,MVP 不为此多维护一个协议。

**时段感知(2026-07-27 ETF 误卖事件裁决①②)**:自动规则(监控腿评估/未成交升级/心跳与断线检测)**仅在连续竞价时段**(09:30–11:30 ∪ 13:00–15:00)执行,其余时段静默;**人工命令任何时段放行**(人工单一买一价无时间戳/陈旧不拦,与自动规则口径刻意不同)。心跳健康三态(True/False/None 不适用),status API 输出 `session` 与人话 `monitor_reason`,页面不再笼统红色"降级"。tick 缺时间戳字段时 ts=None(不再兜底本地时刻),monitor 视为陈旧 fail-closed。

### 5.3 对账(reconciler)

三方比对:A=QMT 实时、B=本地账本、C=成交记录还原。偏差门限 max(100 股, 市值×0.5%),扣除对账时点间的在途成交。处置分级:CRITICAL → kill switch;只写 audit,**永不回写**。时机:启动、重连后、每日 4 时点、收盘。

**手工成交认领(2026-07-27 裁决④)**:A≠B 出现差异时,CRITICAL 之前先用当日成交记录认领——本地没见过的成交按 QMT 记录补记进账本(strategy 标"手工")+落库+audit(kind=manual_adopt),能解释则不拉闸,仍超门限照旧 CRITICAL。分寸:认领是把券商已证明的事实补记(QMT→本地单向),不是按差异改账,不违反"永不回写"铁律。幂等:traded_id 判重(store 当日成交 + book 幂等集合双保险)。

### 5.4 幂等与持久化

- 每笔委托生成策略侧单号编码进 `order_remark`(≤24 字符,格式 `V{mmdd}-{seq}{规则码}`),盘后按 remark 对账;
- 原始回报 JSONL append-only **先落盘再处理**(审计/复盘留痕;恢复 = QMT 全量对账 + 当日成交回填幂等集合,不做 replay——审计 M10 定位改写);
- SQLite WAL 模式;档位状态落库(QP 的乐观标记法:下单提交成功即标记,防废单重复卖);
- 崩溃恢复:重启 → 读 JSONL/SQLite → 全量对账 → 模糊状态(如下单中途崩)**宁可中止也绝不自动重发**。

### 5.5 断线守护

行情软心跳(**主触发源**)+ `on_disconnected`(辅助触发)→ 指数退避重连(1s→2s→…→60s 上限)→ 重连成功才关旧连接 → 重新 subscribe → 全量对账。(xtquant 官方 connect 不自动重连,必须自研;回调线程内禁止调任何 xtquant 同步查询——官方死锁坑。)

**P0-③ 实测结论(2026-07-26, 关闭 miniQMT 客户端实验)**:
1. `on_disconnected` 在"关闭客户端"场景**不触发**(9 分钟窗口零事件)——回调触发链不可靠,故改为:连续 2 次周期扫描行情心跳不健康(且曾收到过 tick、当前视为已连接)即触发同一重连路径,`on_disconnected` 保留为辅助触发;
2. 断线后 `query_positions` **不抛异常,静默返回空列表**——空返回 ≠ 持仓清零:本地有持仓而查询连续 3 次(间隔 1s)返回空,对账结论记 UNKNOWN(不急停、不动 reconciled),查询空结果一律按"查询不可用"处理。

## 七、风控闸门(2026-07-26 裁决② 做减法:4 道 + 买入 sizing 校验)

1. kill switch 检查(三重态);2. 启动对账通过(只拦买单,卖出放行——卖出是降风险动作);3. 日亏软熔断(基准缺失走 fail-safe 禁买);4. T+1 可卖双校验(可用数量+交易日历)。**单票集中度闸已砍**(与回测 position_sizing 职责重复),其买入侧职责由 sizing 校验接替:人工买入按回测 `position_sizing` 口径校验(min/max 金额、lot_size 整手、max_positions 持仓数上限),参数进 TradeConfig。每道拒绝写 audit。买入侧涨跌停拒买随 P2 自动买入一起上。**ETF 排除规则(2026-07-27 裁决③)**:ETF(沪 51/56/58、深 15/16/18 前缀,`exclude_etf` 配置)不纳入自动管理——不挂预埋单、不做规则评估,但持仓**照常对账**,页面灰化明示。

## 九、阶段计划

**P0 · Spike(1–2 天,不写生产代码)**
实测验证 4 个假设:① miniQMT 查询接口流控上限(定对账频率);② `order_remark` 是否完整回传(幂等方案前提);③ `on_disconnected` 在"行情静默但连接未断"时是否触发;④ 9:15–9:20 预埋单在集合竞价的成交行为。产出:验证记录,任何一项不成立则回改本文档对应章节。

## 十、铁律(进 CLAUDE.md)

1. QMT 是持仓/资产/成交的唯一真相源;对账只告警+熔断,永不自动改账、绝不自动重发。
2. 回调线程只做入队;禁止在回调线程调 xtquant 同步接口、写 DB。
3. 交易状态唯一写者 = EventEngine 消费者线程;业务代码零锁(队列/DB 连接内部锁除外);清仓锁是业务防重入锁,保留。
4. 回测与实盘共用同一份卖出规则与参数定义,parity 测试锁定。
5. 原始回报先落盘再处理;重启先对账再交易;行情故障 fail-closed。
6. 预埋单报价锚定最新买一,不超涨停价、不撞 2% 笼子。
7. kill switch 三重态任一生效即全面拒单,只许人工解除。
8. 如无必要勿增实体:不加进程、不加中间件、不加转发层、不写第二份规则。接口数口径(审计 M7 裁决):以"能一口气读完"为准,gateway/store 两个基础设施模块例外(契约面即接口面),其余模块 ≤8。
