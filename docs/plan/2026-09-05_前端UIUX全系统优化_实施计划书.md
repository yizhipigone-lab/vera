### W1-1 暗色模式声明 color-scheme + theme-color

**问题**: 暗色主题下浏览器不知道页面是暗色,原生控件(select 展开的选项列表、滚动条、日期控件)仍按亮色渲染,暗底页面弹出白晃晃的下拉。

**改动**:
| 文件:行 | 现状 | 改为 |
|---|---|---|
| index.html:18(:root 块内) | 无 color-scheme | `color-scheme: light;` |
| index.html:41([data-theme="dark"] 块内) | 无 | `color-scheme: dark;` |
| index.html:3-11(meta 区) | 无 theme-color | 亮/暗各一条 `<meta name="theme-color">`(用 media 属性区分:`media="(prefers-color-scheme: light)"` 与 `dark`) |
| mobile.html:12(:root) | 无 | `color-scheme: dark;`(该页固定暗色) |

**验证**: 暗色下打开任一 select(如股票池下拉),展开列表应为深底;滚动条变深。
**风险**: 极低。唯一注意点: 声明后原生控件会跟随主题,个别控件边框观感变化属预期。

### W2-1 交易页轮询脏检查(数据没变不重绘)

**问题**: trade.js:542 的 1 秒轮询每秒全量 innerHTML 重建持仓表(:252)与委托表(:326): 选中持仓行文字 1 秒内被清选、悬停高亮每秒闪烁、被禁用的按钮 1 秒内被换成全新可用按钮。(第 1 轮核验更正: 当日/历史委托表无委托号列,原"复制委托号"举例不成立,换成持仓行选中场景;核心问题不变)

**改动**(trade.js):
1. 模块级加 `const lastPayload = {};`
2. refresh() 内每个接口的响应在渲染前做比较:
```js
function changed(key, data) {
  const s = JSON.stringify(data);
  if (lastPayload[key] === s) return false;
  lastPayload[key] = s;
  return true;
}
```
3. status/positions/orders/auto_buy/rotation/asset 六路: `changed()` 为 false 时跳过对应表格/KPI 的 innerHTML 重建。**比较键必须按各 render 函数实际消费的字段构造,不要 stringify 整个响应**——第 1 轮核验结论: 六个接口前端消费的字段(status 的 connected/reconciled/monitor_healthy/kill_active 等、positions 的持仓与盈亏、orders 的委托状态)均无每秒必变的服务器时间戳,盘中 last/pnl 随 tick 变化属"数据真的变了,本该刷";但若响应体含前端未消费的 server_time/now 类字段,整包比较会让脏检查每秒失效白干,所以只比较消费字段。实施时用 DevTools 抓一次六个响应实样确认
4. 命令发送成功后(`cmd()` 的 onAccepted 或 watchCmdResult 首次轮询前)清 `lastPayload` 全部 key,强制下次全量刷新,保证回执尽快上屏;**tdsSaveBtn 保存成功后也调 refresh()(trade.js:1002),保存会改 auto_buy/rotation 的 config 显示,保存成功回调里同样清对应 key**(第 1 轮审阅增补)

**验证**: 开着交易页静置 10 秒,选中持仓行文字不被清掉;Elements 面板观察表格 DOM 节点不再每秒重建(可用 DOM 断点或 Performance 面板佐证);后端不可达时仍走既有离线灰化逻辑。**无 QMT 环境替代法**(第 2 轮审读增补): 用 DevTools 的 Local Overrides/拦截改写六路接口响应,先回一份 A 数据、再回一份有差异的 B 数据,验证"B 到达才重绘、重复回 A 不重绘"。
**风险**: 中。比较键构造不当会导致"该刷新不刷新"或"白干"——消费字段清单以六个 render 函数源码为准逐一列出后再写;回归点是无 QMT 环境的离线分支不受影响。
