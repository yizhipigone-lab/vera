# 2026-09-10 停机日资产补算 计划书

> 触发事件: 用户问「为何 9/9 那格显示『无成交』没有盈亏比例? 日历今日卡片说亏 3366,
> 切到交易页 513100 却是 3606, 是不是昨天没开程序?」

## 一、事实与证据 (全部可复验)

### 1. 9/9 那格为什么没有盈亏

`daily_asset` 表**根本没有 2026-09-09 这一行**(全表 26 行, 缺 8/31、9/1、9/9 三个交易日)。
前端 `web/js/analysis.js:225` 的取法是:

```js
const tradeInfo = pnl ? ('买'+n+' 卖'+m) : isTrading ? '无成交' : '休市';
```

`pnl` 为 null 时(该日无资产行)一律显示「无成交」——**把「没采到数据」当成了「当天没成交」**,
同时该格 `pnl_rate` 显示「—」、也点不开盘后日报。

### 2. 为什么没有这一行 (不是"忘了开"这么简单)

| 证据源 | 9/9 的记录 |
|---|---|
| `audit` 表 | 9/8 15:05 有 `eod` 归档 → 下一条已是 9/10 15:52 `eod_catchup`; 9/9 全天零行 |
| `reconcile_log` | 只有 06:57:37 / 06:57:53 / 07:29:35 三次启动对账, 之后到 9/10 15:52 无 |
| `raw_reports.jsonl` | 最后一条原始回报停在 **2026-09-08 15:30:57** |
| `output/logs/scheduler.log` | 最后一行 9/9 07:29:34 |
| Windows 系统事件 41/6008 | 9/9: 06:55:06 起 → 07:28:49 挂; 07:28:49 起 → **11:19:53 意外断电** → **19:28:44 才恢复** |

即: 9/9 一早程序起来过三次(每次先对账), 但机器在 11:19:53 意外断电, 一直到晚上 19:28 才恢复,
**15:05 的收盘归档 (EOD) 没跑成**, 于是 daily_asset 缺 9/9 一行。当晚 19:29 还有一次
Windows 计划内升级重启。

### 3. 为什么日历 -3366 而交易页 -3606

`trade/analysis_api.py` 的逐日盈亏是「本行 − **上一行**」, 不认交易日缺口:

```python
prev = rows[i - 1] if i > 0 else prev_month_row
```

9/9 缺行 → 9/10 的基准被静默换成了 **9/8** 的行, 于是那一格挂的是**两天合计**却标成单日:

| 项 | 数字 | 口径 |
|---|---|---|
| 9/8 实测 | 1,064,797.72 (现金 527,984.52 + 240,400 股 × 2.233) | QMT 日终 |
| 9/9 掉的那格 | 527,984.52 + 240,400 × **2.234** = 1,065,038.12 → **+240.40** | 推算 (本计划书要落地的东西) |
| 9/10 实测 | 1,061,432.12 (240,400 × 2.219 + 现金) | QMT 日终 |
| 日历 9/10 显示 | **-3,365.60** | 1,061,432.12 − 1,064,797.72 (含 9/9) |
| 交易页 513100 显示 | **-3,606.00** | (2.219 − 2.234) × 240,400, 单日真值 |

校验: `-3,606.00 + 240.40 = -3,365.60`, 分毫不差 —— 两个数都对, 差的就是被吞掉的 9/9。
**两个数都是亏, 不是一赚一亏。**

### 4. 两天/三天没开机怎么办 (拿 8/31–9/1 那两天真实验算)

同样缺行的 8/31、9/1 推出来是 1,062,413.72 / 1,064,799.72, 但推到 9/2 就**差 1,847.20 对不上**:
那两天里有一笔 **200 股 518880(黄金ETF, 约 9.236 元/股 = 1,847.20)** 的买入没进 VERA 的账
(持仓是重启后从 QMT 读回来的, 成交表里没有这一笔, 现金却真实少了)。
结论: **N 天停机是同一个算法, 但必须两端夹逼自校验, 对不上就按阈值处置并报差, 绝不闷头写数。**

## 二、目标

VERA 没开机(没归档)的交易日 → 用「最近实测锚点 + 缺口内成交回放 + 每日收盘价计价」补出资产行,
标 `source='derived'`, 界面标「推算」; 两端夹逼差额小于阈值(默认 0.5%)才写入并把差额标注出来,
超阈值拒写并报警。**结论: 日历不再缺格、不再把多日涨跌伪装成单日。**

## 三、算法

```
每天资产 = 现金 + Σ(持仓股数 × 当日不复权收盘价)
```

- **锚点(左端)**: 缺口前面最后一个实测行 (`source='eod'`) 的 `available`(现金) + 由
  「最新已知持仓 − 缺口后的成交」反推出来的当日持仓。
- **缺口内**: 逐交易日回放当日成交(买 → 现金减少/股数增加, 卖反之), 用**当日不复权收盘价**
  逐日计价。前复权与实盘成本/市值不可比, 一律 `dividend_type=none`。
- **右端夹逼**: 用缺口后第一个实测行校验 —— 从推算出的最后一天接着推进右端当天的成交与价格,
  得到「右端预测值」, 与右端实测值的差 = 残差:
  - 残差 = 0 → 完美(9/9 就是 0.00);
  - |残差| ≤ 0.5% × 左端资产 → 写入, 并把残差**按日均摊**并入各日现金(标注"未记录资金调整"),
    这样右端那格的单日涨跌仍然是干净的真值(否则误差会全砸在右端, 就是今天这个 bug 的翻版);
  - |残差| > 0.5% → **拒写**, audit 留痕, 界面显示「未归档·差¥X」。
- **左端诊断**: 反推出的持仓 × 左端当日收盘 vs 左端实测市值, 差多少一起报出来(它解释了残差的来源)。
- **缺收盘价 / 无右端实测日(尾部缺口) / 账户首月无锚点** → 该缺口不写, 如实报原因(fail-closed, 不猜)。

## 四、边界与失败模式

| 情况 | 行为 |
|---|---|
| 缺口内有未记录的手工成交 | 残差检出 (实证 8/31–9/1 的 1,847.20), 报出来 |
| 某代码缺当日收盘价 | 该缺口不写 (宁可不写, 不写错数) |
| 尾部缺口 (最后一行到昨天, 今天还没归档) | 不写, 提示"等今日归档后再补" |
| 账户首月无左端锚点 | 不补 |
| 周末/节假日 | 交易日历过滤, 只补交易日 |
| 重跑 | 幂等: 只重算并覆盖 `source='derived'` 的行, **绝不覆盖实测行** |
| QMT/TDX 取数失败 | 全链路 fail-soft, 交易链零影响 |

## 五、接口与接线

- 新深模块 `trade/asset_gapfill.py`: `plan_gaps()`(纯函数, 全部数学, 可用 dict 单测) +
  `fill_gaps()`(编排: 读库/写行/留痕) + `make_close_source()`(取价降级链)。
- `daily_asset` 加列 `source TEXT NOT NULL DEFAULT 'eod'` (`'eod'`=实测 / `'derived'`=推算),
  ALTER 幂等迁移, 默认值保证零行为变化。
- `gateway.query_daily_closes_range(code, start, end)` → `{日期: 收盘价}`: QMT 主源(持仓估值同源),
  TDX 兜底(需要日期对齐, 故新开一个不取最新 N 根的接口)。
- 自动: `trade_main._startup_catchup` 在 15:05 补偿归档之后补一轮 (此时今天的实测行已存在 →
  缺口变成"两端都有实测"的可校验缺口)。
- 手工: `POST /api/trade/analysis/gapfill?dry_run=1|0` 入队命令 →
  消费者线程执行(非连续竞价守护) → 结果落 `audit(kind='gapfill')`;
  `GET /api/trade/analysis/gapfill_last` 读回最近一次结果供界面展示。
- 界面: 日历格分「实测/推算/未归档(带差额)/待归档(今天)」四态; 月汇总标注"含 N 天推算";
  推算日点开日报面板显示"该日为推算值, 无盘后日报"; 日历头部加「补算停机日」按钮 + 预览。
