## 0. 【前置更正】验证的时刻变了：从「次日 09:05」改为「当天 15:55」

**2026年9月17日用户指出**：体温表 15:50 就采集完了，**次日早上 09:05 推的是同一份数据、
一个新数字都没有**。我实测确认（跑 `expected_last_trading_day` 对照三个时刻）：

| 什么时候跑 | 「应有数据的交易日」 |
|---|---|
| 交易日 T 的 15:50 | T |
| **次日 T+1 的 09:05** | **还是 T**（没到 15:00，函数返回上一交易日） |

→ **两次算出来的记录逐字段相同**，早上那张卡与前一天下午能发的完全一样。所以：

- **原 09:05 的推送 job 要取消**；体温表推送挪到**当天 15:55**，与复盘报告合成一条消息
  （详见 `2026-09-17_大盘位置与趋势研判_计划书.md` §17）。
- **本计划书正文里出现的「09:05」一律按「15:55」理解。** 下面保留原文只为记录推演过程，
  涉及时刻处**以本节为准**。
- 顺带一个好消息：**这两个 job 一次都没跑过**（用户尚未重启 scheduler），改动零风险。

## 1. 为什么必须先手动验

大盘位置子系统的推送链路是 2026-09-17 新建的，**从来没有真发过一张卡片**。
它现在挂在调度器上每交易日 09:05 自动跑——如果格式不对，用户会在接下来每个交易日
早上收到一张烂卡片，而且**推送是单向的，没有回执**，不看就不会发现。

对比参照：项目里飞书推送踩过坑（`tools/send_report_feishu.py` 的注释记着
「飞书自定义机器人卡片只支持 lark_md，**无表格、无图片、无 HTML**」）。而大盘体温表
**含 4 张 Markdown 表格**，是全项目结构最复杂的待推内容之一。风险实在。

## 2. 现状核实（已实测，不是推测）

| 项 | 实测结果 |
|---|---|
| `.env` 里有 `FEISHU_WEBHOOK_URL` 吗 | **有**（只核了键名，没有打印值） |
| 推送器可用吗 | `tools/send_report_feishu.py` 提供 `load_webhook` / `md_to_lark` / `chunk_sections` / `send_card` |
| 体温表多大 | 实测 **2032 字符 / 3580 UTF-8 字节**，18 个表格行，3 个章节 |
| 会被拆成几张卡 | `chunk_sections` 单卡上限 8000 字节 → **预计 1 张卡**（远低于阈值） |
| 入口 | `python tools/market_position_collect.py --push`（采集后推）或 `--push-only`（不采集直接推最新一条） |
| 失败会不会炸 | 不会。`core/market_position_runner.push_thermometer` 全程 fail-soft，webhook 缺失/推送失败都只返 `{"ok": false, "reason": ...}` |

## 3. 要验的 7 项（逐项给判据）

| # | 验什么 | 判据（看到才算过） |
|---|---|---|
| **V1** | 能不能发出去 | `--push` 输出 `飞书推送: {'ok': True, 'cards': 1, 'codes': [0]}`，`code` 必须是 `0` |
| **V2** | **4 张表格有没有被 lark_md 打散** | 位置表 3 行（三大指数）、照镜子表 5 行、影子规则表 4 行（3 规则 + 买入持有对照），每行读起来是「沪深300(000300.SH) ｜ 4450.00 ｜ 73.0% …」而不是一堆竖线乱码 |
| **V3** | 「数据滞后」抬头是否显眼 | 抬头应出现「**数据滞后**: 最新有效交易日 2026-09-15, 应有 2026-09-16」——这是**当前真实现状**（个股日线最新只到 9月15日），正好顺带验了这条分支 |
| **V4** | 一句话摘要读得通 | 全A成交额应显示「16,037亿元」，站上20日均线「21.2%」（**不带正号**——占比写 `+21.2%` 会误导，这是专门改过的格式） |
| **V5** | 照镜子的警告在不在 | 卡片里必须有「样本只有 5 个……「历史相似」不是预测」整句。**这句是硬要求**（`MIRROR_WARNING` 常量），丢了就等于把参照系当预测发出去 |
| **V6** | 三条已知偏差在不在 | 卡片末尾必须有 ST 漏计 / 生存者偏差 / 百分位窗口不足十年 三条 |
| **V7** | 铁律提示在不在 | 末尾有「只读参考，不联入任何仓位调度（业务铁律 1）」 |

**V2 是本计划的核心**——其余六项都是内容有无，只有 V2 是"格式会不会坏"，
而格式坏掉是最可能的失败模式。

## 4. 可能踩的坑与处置（预判，先备好药）

| 坑 | 症状 | 处置 |
|---|---|---|
| 表格被挤成一坨 | 8 列的中文行超宽，手机上要左右拉 | 把位置表**减列**（去掉「偏离年线」「年化波动20日」，保留收盘/十年百分位/距十年最高/近一年/牛熊），或改成多行文本而非表格 |
| 长句被截断 | 飞书单条文本有长度限制 | `chunk_sections` 已按 8000 字节拆卡；若某段本身就是超长单段，需在 `md_to_lark` 之外**手工在体温表里就断段**（改 `thermometer_md` 的组装，不是改推送器） |
| 卡片太密看不清重点 | 三类信息（位置/照镜子/影子规则）平铺 | 若可读性差，**照镜子与影子规则各拆成第 2、3 张卡**（用 `## ` 分节让 `chunk_sections` 自然拆） |
| 早上 9:05 收到"数据滞后"卡片 | 若某天缓存没刷上 | 这是**正确行为**（不能拿旧数据冒充新鲜）。若频繁发生，说明 15:45 的缓存补尾段有问题，那是另一个问题，**不在本计划修** |

## 5. 顺带补一个开关（建议，请用户点头）

现在 09:05 那个 job **写死了每天必推**，用户想关掉只能改代码。建议照项目既有惯例补开关：

- 参照物：舆情扫描读 `config/sentiment.yaml`（`brain/alert_rules.load_config`）；
  交易飞书读 `config/trade.yaml` 的 `feishu.enabled`。
- 建议新增 `config/market_position.yaml`，含两个键：`morning_push`（默认 `true`）
  与 `daily_collect`（默认 `true`）。读不到配置 → 回落默认（老行为）。

**这条是"加一个可关的开关"，不是"改需求"** —— 用户拍板要做每日推送，只是让它可撤销。

## 6. 不做（划界）

- **不改推送器**：`tools/send_report_feishu.py` 是三个既有功能（研报/舆情/P1a 研究包）
  共用的组件，为大盘位置去改它有回归风险。要调整**只改体温表 Markdown 本身的形状**。
- **不做定时重试/补发**：调度器已有防重与补发机制（`VeraScheduler` 的 `state_path`），
  推送层不重复建设。
- **不接邮箱**：邮箱那两路属于复盘报告（另一份计划书），不混进来。

## 7. 验收标准

1. `python tools/market_position_collect.py --push` 返回 `ok: True`、`codes: [0]`。
2. 用户**亲眼**看到卡片，并确认 V2（表格没散）与 V5（照镜子警告在）这两条。
3. 若 V2 不过，按 §4 减列或拆卡后**重推一次**，直到看着舒服；把最终形态写回计划书与 CHANGELOG。
4. 把"手动验证通过 + 卡片长什么样"记进 `docs/plan/2026-09-17_大盘位置与趋势研判_计划书.md`
   的 §11 验收标准第 5 条（那条现在是「⚠️ 半验收：路由已确认挂载，但浏览器与飞书都没看过」）。

## 8. 依赖项：自动推送要生效必须先重启 scheduler

**这一点单列，因为非常容易漏**：`scheduler/__main__.py` 本次新增了两个 job
（`market_position_collect` 15:50 / `market_position_morning` 09:05），但**正在运行的
scheduler 进程是改动前启动的，不会自动加载新 job**。

而项目上下文里明确记着这条坑（2026-09-16 记录）："已运行进程继承旧环境变量，改完注册表
必须用带新 PATH 的环境重启 server/scheduler 才生效"。

所以顺序是：

1. 先手动推一次，验卡片（本计划 §3）
2. **再重启 scheduler**（否则 09:05 那个 job 根本不存在，第二天什么都不会发生）
3. 次日 09:05 收到卡片 = 自动链路验通

**重启是用户的动作，我不代做**——实盘服务不该被开发动作打断（同样适用于 PC 端页签：
需重启 server 后刷新 `http://127.0.0.1:8080/#market` 才看得到）。

## 9. 外部最佳实践对照与采纳（2026-09-17 联网检索后新增）

检索来源：[Webhook 最佳实践（Integrate.io）](https://www.integrate.io/blog/apply-webhook-best-practices/)、
[重试与重复投递处理（Nylas）](https://developer.nylas.com/docs/cookbook/use-cases/build/retry-failed-webhooks/)、
[Webhook 失败处理与重试（Mambu）](https://docs.mambu.com/docs/webhooks-best-practices/)、
[通知设计如何避免告警疲劳（Kissflow）](https://kissflow.com/workflow/bpm/how-to-design-workflow-notifications-without-causing-alert-fatigue/)、
[降低告警噪音（NinjaOne）](https://www.ninjaone.com/blog/reduce-alert-noise-using-client-facing-strategies/)。

### 9.1 逐条对照

| # | 外部实践 | 我们现状 | 采纳结论 |
|---|---|---|---|
| **W1** | **"告警疲劳"是通知系统的头号失败模式**——无差别的高频推送会导致收件人**集体忽略**，那时真出事的通知也看不见了 | 本计划是**每交易日 09:05 无条件推**，一周 5 张，**从来没问过"该不该每天都推"** | ⚠️ **部分采纳**（§9.2，这条是本次最有价值的外部输入） |
| **W2** | **重试会导致重复投递**，接收端必须做幂等/去重；反之亦然 | 我们**没有重试**（`VeraScheduler` 只在 job 层防重发），失败即丢 | ⚠️ **部分采纳**（§9.3）：**不加自动重试**（避免重复投递），但**失败必须留痕** |
| **W3** | **投递要可验证**，不能"发出去就当成功" | `push_thermometer` 已逐卡校验飞书返回 `code == 0` ✅ | ✅ 已具备 |
| **W4** | **消息格式要适配平台能力**；飞书卡片 JSON 有长度限制，需要稳健分片（社区实现里专门有"robust splitting"的改进） | `chunk_sections` 按 8000 字节拆卡 ✅，但**表格只能降级成文字行** | ✅ 已具备；§3 的 **V2 判据就是在验它** |
| **W5** | 通知应当**可订阅、可关闭** | §5 已建议加 `config/market_position.yaml` 开关 | ✅ 已具备，且与外部实践方向一致 |

### 9.2 采纳 W1：加"静默规则"（原计划最大的盲点）

原计划的设计假设是"每天推一张，用户每天看"。
**外部实践明确指出这会导致忽略**——尤其当市场没有变化时，连续几天推一模一样的
"宽度 21%、成交额一年 1.6% 分位"，用户第三天就不看了，**然后真出信号那天也看不见**。

**改法（可选，需用户点头）**：09:05 的推送加一道"值不值得推"的闸：

| 情况 | 推送策略 |
|---|---|
| 数据滞后（`stale`） | **必推**，且抬头醒目（这是要人处理的事） |
| 宽度 / 成交额分位**突破预设阈值** | **必推**（有变化） |
| 候选择时规则的**状态发生切换**（on↔off） | **必推**（信号变了） |
| 与昨日相比**无实质变化**且无异常 | 推**精简版一行**（或按配置跳过） |

**注意**：这条**不等于取消每日推送**——用户要的是"每天早上推一张"，
这里只是让**内容随信息量变化**，而不是让"推不推"随机化。
阈值与开关全部走 §5 的配置文件，默认行为**保持每天全量推**（零行为变化）。

### 9.3 采纳 W2：失败要留痕，但**不加重试**

外部实践在"重试"上给的是双向建议：要重试，但要防重复。
**我们选择不加重试**，理由：飞书自定义 bot 的 webhook **没有幂等键**，
我们无法保证"重试不产生第二张卡"；而一张重复的体温表比漏一张更烦人（见 W1）。

**但"失败即丢"不可接受**——现在的行为是：推失败只在调度器日志里留一行
（`大盘体温表未推送: ...`），**用户永远不会知道**。改法：

- 推送失败时写一条**持久化留痕**（`data/market_position/push_failures.jsonl`）；
- **下一次成功推送时，在卡片抬头加一行**「⚠ 上一张体温表（YYYY-MM-DD）推送失败，原因：…」；
- 这样**漏推是可发现的**，而且不引入重复投递风险。

### 9.4 §9 的验收标准

1. §9.2 的静默规则**默认关闭**（配置 `silent_when_unchanged: false`），
   打开后连续无变化日的卡片内容确实变精简（有测试）。
2. 推送失败必须落 `push_failures.jsonl`；下一次推送卡片抬头出现"上一张失败"提示（有测试）。
3. **不实现自动重试**——若将来有人提议，先回看 §9.3 的理由（无幂等键 → 会重复投递）。
4. 保持 §3 的 V2 判据（表格不被 lark_md 打散）不变。
