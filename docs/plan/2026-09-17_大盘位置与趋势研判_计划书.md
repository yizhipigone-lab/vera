> 入口: 用户 2026-09-17 在系统优化评估中点名「大盘所处位置 + 趋势研判（提升空间最大的方向）」
> 并拍板「这个可以做」。
> 一句话目标: 把研究大脑现在"每天一张大盘照片"升级成"连续录像 + 历史照镜子 + 每日体温表"。

## 1. 现状与缺口（先说人话）

现在大脑看大盘靠 `brain/market_panel.py` 的 `market_snapshot()`，它从 akshare 抓五个板块
（A股指数快照 / 港股指数 / 美股三大指数 / 南向资金 / 涨停池），再拼上一张
`market_health()` 体检表（4 指数 × 4 窗口收益 + 牛熊状态）。

这张表的三个缺口：

1. **没有"位置"概念**：只有"涨了多少"，没有"现在贵不贵"。
   指数 3891 点是高是低？要靠脑子里记住历史。
2. **没有连续序列**：`market_snapshot` 有 2 小时文件缓存（`data/brain_model_cache/`），
   但那是"当天快照"，隔天就被覆盖，攒不出时间序列。
3. **没有宽度**：指数是大市值股票的函数，指数涨不代表大多数股票在涨。
   实测 2026-09-16 就是一个活例子（见 §3 实测数据）。

## 2. 目标（可验收）

- **G1 连续录像**: 每个交易日盘后落盘一条结构化记录到
  `data/market_position/daily.jsonl`（一天一行 JSON），含位置/宽度/量能/波动四组指标。
- **G2 历史照镜子**: 给定今天的指标向量，自动找出历史上最像的若干天，
  并给出那几天之后 20 / 60 个交易日的实际走势（参照系，不是预测）。
- **G3 择时规则影子记录**: 三条候选择时规则每日记录状态，
  **只记录不交易**；并用历史序列回放算它们的假想成绩（T+1 口径）。
- **G4 每日体温表**: 每交易日盘后自动生成 Markdown 并推飞书
  （复用 `tools/send_report_feishu.py` 链路）。
- **G5 大盘位置页签**: PC 端新增独立页签，展示最新一条 + 近 250 日趋势 + 照镜子结果。

## 3. 实测数据（先把尺子摆出来）

**数据日期 = 2026年9月15日，不是 9月16日** —— 这是本子系统第一个实测发现（详见 §4.2）：
日线缓存里 9月16日那根是个股"空壳 bar"（文件写入时间 9月16日 09:16，开盘前抓的，
成交量 0），有效交易日判据把它挡掉了。下面全是最终交付版本（滚动 2430 个交易日窗口）
的实测值：

| 指标 | 实测值（数据日 2026年9月15日） | 读法 |
|---|---|---|
| 上证指数(代码 000001.SH) 十年百分位 | **90.9%** | 比过去十年 90.9% 的交易日都高 |
| 沪深300(代码 000300.SH) 十年百分位 | 73.0% | 偏高但没到极端 |
| 创业板指(代码 399006.SZ) 十年百分位 | 88.4% | 偏高 |
| 站上 20 日均线家数占比 | **21.2%** | 只有约五分之一的股票还在均线上方 |
| 创 60 日新高 / 新低家数 | 51 / **275** | 新低是新高的 5.4 倍（差 −224） |
| 全A成交额 | 16,037 亿元 | 处于过去一年的 **1.6% 分位**（一年中位数 23,581 亿元） |
| 涨停 / 跌停家数 | 32 / 33 | 本地日线推导，ST 股会漏计 |
| 上证指数近一年收益 | −0.2% | 一年白干 |
| 沪深300 近一年收益 | −1.6% | 一年小幅亏 |
| 沪深300 年化波动率（20 日） | 14.1% | 低波动 |

> **口径勘误（成文后修订）**：本节初稿写的是"2026年9月16日"，上证百分位 92.3%、
> 站上 20 日均线 19.7%、新高新低 52/299、成交额分位 62%。那组数字来自原型阶段，
> 有两处口径与最终交付不同：①日期用的是 9月16日（当时还不知道那根是空壳 bar）；
> ②百分位用「过去 3652 个自然日 + 严格小于」计算，最终交付改成「滚动 2430 个
> 交易日 + `rolling.rank(pct=True)`」，且历史不足十年时要求满 3 年才给数。
> 两套口径在数据日上也差一天，故不能逐项相减比较。**以本表为准。**

**这组数字本身就是最好的产品说明**：指数在十年 90% 分位的高位，
但个股层面八成已跌破 20 日均线、创新低家数是新高的 5.4 倍、成交额趴在一年最低的
1.6% 分位 —— 典型的"指数虚胖、个股挨打"。
只看指数会得出完全相反的结论。这就是本子系统的价值。

## 4. 数据源与口径（关键决策）

### 4.1 数据源 = 本地日线缓存，不用网络

`data/kline_cache/1d/` 已有 5761 个 parquet（5211 只沪深 A 股 + 指数 + ETF），
指数历史回溯到 2013-01-04。全量读取（只取 date/close/volume/amount 四列）
实测 **17~28 秒**，一次性放进内存后向量化计算 **3 秒**。

**决策**: 走本地缓存，不走 akshare。
理由：①复现性 —— 同样的输入永远得同样的数，方便测试与审计；
②离线可用 —— 不开 TDX / 断网也能算；③已有基础设施 —— 调度器每交易日 15:45
已经把这个缓存刷到最新（`core/kline_cache_maintenance.py`），不重复建设。

读取时置 `VERA_KLINE_READONLY=1`，让 `KlineCache._ensure` 直接返回，
**绝不触发任何网络补拉**（只读分析任务不该因为网络卡死）。

### 4.2 【踩坑实录】缓存最后一根可能是"空壳 bar"

实测发现：`000001.SZ`（平安银行）的日线最后一根是 2026-09-16，
但 `open=high=low=close=11.81、volume=0、amount=0`，文件写入时间是
**2026-09-16 09:16**（开盘前抓的）。

也就是说：盘前抓数会造出一根"有日期、无成交"的假 bar。如果直接拿它当收盘价算宽度，
会静默用盘前价冒充收盘价。

**对策（硬性）**: 定义"有效交易日"= 全市场成交量大于 0 的股票占比 ≥ 50% 的那一天。
快照的 `data_date` 取最后一个有效交易日，并在记录里写
`stale: true/false` 与 `expected_date`。数据滞后时照常落盘但打标 + 告警，
**绝不把滞后数据当新鲜数据推给用户**。

### 4.3 牛熊口径复用单一真相源

`core/index_regime.py::classify()`（价 > MA250 且 MA250 的 20 日斜率 > 0 为牛，
价 < MA250 且斜率 < 0 为熊，其余震荡）。**不写第二份**。

### 4.4 涨停家数：本地推导 + 已知偏差

用 `core/limit_ratio.py::limit_ratio()`（全项目唯一真相源）算每只票的涨跌停幅度，
再比对收盘价是否触及涨停价。**已知偏差**: 该函数需要 `st` 布尔标记，
而本地缓存里没有 ST 标记，故 ST 股（±5%）的涨停会被漏计 —— 这是**低估**，
方向安全（宁可少报不虚报）。记录里写 `limit_source: "kline_cache"` 标注来源。

### 4.5 不合成总分（沿用既有决策）

`docs/plan/2026-09-04_市场体检表与研究雷达_决策记录.md` 已拍板"四指数并行不合成"。
本子系统**沿用**：每个维度各给自己的百分位，**不给一个混合总分**，
避免用拍脑袋的权重掩盖分歧（指数高位 + 宽度崩塌这种分歧本身就是最有价值的信息）。

## 5. 指标定义

每条日记录（`data/market_position/daily.jsonl` 一行）：

```
{
  "date": "2026-09-15",              # 数据实际日期（最后一个有效交易日）
  "expected_date": "2026-09-16",     # 应有数据的交易日
  "stale": true,                     # date < expected_date 时为 true
  "indices": {                       # 三大指数，各 8 个字段
    "shanghai":    {"name":"上证指数","close":3864.30,"pct_10y":90.9,
                    "from_high_pct":-8.9,"vol_ann_20":12.2,"vol_ann_60":16.7,
                    "ret_1y_pct":-0.2,"ma250_dev_pct":-3.1,"regime":"range"},
    "hs300":       {...},
    "chuangyeban": {...}
  },
  "breadth": {                       # 市场宽度（战场上有多少士兵在冲）
    "traded": 5190,                  # 当日有成交的股票数（分母）
    "above_ma20_pct": 21.2,          # 站上 20 日均线占比
    "above_ma60_pct": 38.9,          # 站上 60 日均线占比
    "new_high_60": 51,               # 创 60 日新高家数
    "new_low_60": 275,               # 创 60 日新低家数
    "hl_spread": -224                # 新高 − 新低
  },
  "turnover": {
    "amount_yi": 16037.0,            # 全 A 股成交额（亿元）
    "amount_pct_1y": 1.6             # 成交额在过去一年的百分位
  },
  "limit": {"up": 32, "down": 33, "source": "kline_cache"},
  "shadow": {                        # 三条候选择时规则的当日状态（只记录不交易）
    "ma20": "off", "breadth50": "off", "regime": "off"
  }
}
```

> **本示例已按 §3 勘误表更新为最终交付口径的真值**（数据日 2026年9月15日、2430 个交易日
> 滚动窗口）。2026-09-17 深度审查 M2 发现：本节初版仍是原型阶段的作废数字
> （9月16日 / 92.3% / 19.7% / 52/299），与 §3 自己声明的"以本表为准"直接冲突。**现已修正。**

指标口径逐条：

| 指标 | 算法 | 白话解释 |
|---|---|---|
| `pct_10y` | **滚动 2430 个交易日**窗口内 `rolling.rank(pct=True) × 100`；**min_periods=750**（满 3 年才给数） | 现在的位置比过去十年百分之多少的日子高 |
| `from_high_pct` | 收盘 / 同窗口滚动最高 − 1 | 距十年最高点还差多少 |
| `vol_ann_20` | 近 20 个交易日对数收益标准差 × √252 | 年化波动率，越大越颠 |
| `ma250_dev_pct` | 收盘 / MA250 − 1 | 偏离年线多少 |
| `regime` | `core/index_regime.classify()` | 牛 / 熊 / 震荡 |
| `above_ma20_pct` | 当日有成交且收盘 > 自身 MA20 的股票占比 | 多少人还在均线上 |
| `new_high_60` | 当日收盘 ≥ 自身近 60 日最高收盘 | 创近三个月新高家数 |
| `hl_spread` | new_high − new_low | 正数=扩张，负数=收缩 |
| `amount_pct_1y` | 全 A 成交额在过去 250 个交易日的百分位 | 现在的量能算大还是小 |

## 6. 历史照镜子（G2）

> **口径提示（2026-09-17 深度审查 M3 补）**：本节描述的是 **v1 已交付口径**
> （`gap=20` / top-5 / 5 个样本的中位数）。**§14.1 已判定 `gap=20` 是数据窥探、
> §14.2 已判定"5 个样本的中位数不是统计量"**——**实际实施以 §14 为准**，
> 本节保留是为了记录 v1 的原貌与它错在哪。

**特征向量**（6 维，全部是"当日已知"的量，不含任何未来信息）：
`[上证十年百分位, 沪深300十年百分位, 站上MA20占比, (新高−新低)/有成交家数, 沪深300年化波动20日, 成交额一年百分位]`

**算法**:
1. 用历史全序列对每个特征做 z-score 标准化（减均值除标准差）；
2. 算今天向量与每个历史交易日的欧氏距离；
3. 排除最近 20 个交易日（否则照出来的镜子全是"昨天、前天"，没有信息量）；
4. 贪心去重：已选中的日子前后 20 个交易日内不再选（否则一次照出 20 个连续的同一天）；
5. 取距离最小的 5 天，各自给出其后 20 / 60 个交易日的指数实际涨跌；
6. 汇总给出"这 5 次之后 20 日的涨跌分布"。

**诚实声明（必须写进报告与页面）**: 样本只有 5 个，且 A 股三十年只经历过
屈指可数的几轮周期，"历史相似"**不是预测**，只是提供一个参照系。
报告里必须原样带上这句警告。

## 7. 择时规则影子记录（G3）

三条候选规则，每日记录 on/off，**只记录不交易**：

| 规则名 | 多头条件（on） | 参照 |
|---|---|---|
| `ma20` | 沪深300 收盘 > 自身 MA20 | 最经典的均线择时 |
| `breadth50` | 站上 MA20 家数占比 ≥ 50% | 用宽度而非指数 |
| `regime` | `core/index_regime.classify()` = bull | 项目既有牛熊口径，作对照组 |

**回放评估口径（照抄 2026-08-24 的教训）**: 信号在 T 日收盘产生，
**T+1 日生效**（`docs/plan/` 与 `trade/shadow.py` 的既定纪律）。
原口径"T 日当天生效"对高频规则系统性乐观，本项目已经因此得出过一次假结论，
不得重犯。回放输出年化 / 最大回撤 / 夏普 / 卡玛 + 买入持有对照。

**铁律提醒**: 本节的输出是**研究报告**，绝不接进 `trade/` 的任何闸门或仓位计算。
测试里用 AST 静态断言 `core/market_position*.py` 与 `market_position_api.py`
不含 `import trade`（照 `tests/brain/test_sentiment_acceptance.py` 的守护写法）。

## 9. 落盘与幂等

- 路径 `data/market_position/daily.jsonl`（一天一行，按日期排序）。
- **upsert 语义**: 同一天重跑覆盖该行，不追加重复行（照 `trade/shadow.py::append_shadow_log`
  的按日去重思路，但用"读全量 → 合并 → 原子重写"实现，因为要支持回填覆盖）。
- 原子写：临时文件 + `os.replace`（照 `VeraScheduler._save_state` 的写法）。
- 采集窗口默认最近 **300** 个交易日（**不是 90**——深度审查 M4 发现本文初版写的 90 与代码
  `core/market_position_runner.py:66 DEFAULT_BARS = 300` 不符；且 90 根不够算 `amount_pct_1y`
  的 250 根窗口，按 90 实现会静默算不出该字段）。为什么是 300：覆盖成交额一年分位（250 根）
  \+ 60 日新高低 + 缓冲，**一次算出窗口内所有有效日并全部 upsert** ——
  于是"停机三天后开机"会自动补上那三天，无需单独写补数逻辑。

## 12. 后续衔接：盘后复盘报告「合不合进大盘位置页签」的裁决（2026-09-17 用户提问）

用户问：盘后自动复盘报告（今日盘面 + 持仓表现 + 明日关注）是不是和大盘趋势的
TAB 合在一起比较好？

**裁决：用户看到的地方要「合」，代码里的模块要「分」，依赖单向朝下。**

三条理由：

1. **物理隔离不能破**。大盘位置模块的数据源是纯市场数据（本地日线缓存），
   本计划书 §7 给它立了 AST 守护「绝不 import trade」。复盘报告的「持仓表现」
   必须读 `data/trade/trade.db`（持仓/资产/成交），一旦塞进同一个模块，
   那条守护就废了 —— 而守护正是「大盘研判不会悄悄联进仓位」的**机械保证**
   （业务铁律 1 要求仓位由人工把关，机制比自觉可靠）。
2. **两者服务的使用场景不同**。复盘报告是「推」：早上在路上，飞书弹一张卡；
   大盘页签是「看」：坐到电脑前想往下钻（十年百分位 / 照镜子 / 趋势图）。
   硬合成一个页签会让「推」的文案变重、让「看」的页面变乱。
3. **但内容层次上确实是一家**。复盘的「今日盘面」直接复用
   `thermometer_md()`，**不写第二份盘面文案**。依赖方向：

   ```
   notes_gen/daily.py                复盘: 盘面 + 持仓 + 留意清单
        ├─ core.market_position_runner   ← 复用体温表(盘面段)
        └─ trade 域数据(trade.db)        ← 持仓段
   core/market_position_runner.py     大盘位置(绝不 import trade)
   ```

**页面落地**：大盘位置页签里加一个「今日复盘」折叠块，内容由复盘模块生成的
Markdown 全文注入，不由大盘模块生成。用户一个页签看全，代码边界干净。

**排期依赖（必须串成一条链，顺序不能错）**：

| 时刻 | 步骤 | 状态 |
|---|---|---|
| 15:05 | 交易端 EOD 归档 | 现有 |
| 15:45 | K 线缓存补尾段 | 现有 |
| 15:50 | 大盘位置采集 | **本次新建** |
| 09:05（次日） | 大盘体温表推飞书 | **本次新建** |
| 15:55 | 复盘报告生成 + 推送 | 待做 |

复盘必须排在大盘位置采集之后，否则会引用到昨天的大盘位置。

**「明日关注」的口径（待用户拍板）**：建议 v1 **只做规则事实，不做主观预测**，
并且把名字改成「需要你留意的清单」（原名承诺了预测，与铁律 1 冲突）：

- 持仓中当日触发或接近止损/止盈线的标的；
- ETF 轮动的当前目标腿与下一次锚定日；
- 当日公式出票（14:52 自动买入信号）；
- 大盘位置侧的状态提示（数据滞后 / 宽度跌破阈值）。

LLM 只允许做**一句话归纳**（可选开关，默认关）。理由：推到手机的报告一旦掺进
「我觉得明天会……」，就会被当成建议读，而铁律 1 要求仓位由人把关。

## 14. 邮件研究发现的改良项（2026-09-17 用 qqmail 技能读信后新增）

用户让我用 `qqmail` 技能收了收件箱最新 9 封。**其中一封直接暴露了我已交付实现里的
一个真实缺陷**，其余几条是有价值的缺口。本节是本子系统第二轮的开工依据。

### 14.1 【缺陷·高】`similar_days` 的 `gap=20` 是数据窥探

邮件《A股大盘研判：跌破年线3.49%还算牛吗？》（2026-09-13 17:11）用的方法与我的
「照镜子」**同源**（多特征 + Z-score 标准化 + 欧氏距离取最近邻），但它明确写了：

> 排除最后 252 天避免数据窥探

而 `core/market_position.py::similar_days(gap=20)` 只排除最近 **20 个交易日**。
后果：照出来的"历史相似日"可能就在一个月前——**等于拿昨天当历史参照，是数据窥探**。
已交付的那次实测最晚相似日是 2026-04-07（约 5 个月前），**这次侥幸没踩到，但门是开着的**。

**改法**：`gap` 默认 20 → **252**（一年），保留调用方可覆盖。
**2026-09-17 实施时按 §16.7「新增」一行拆成两个参数**（原 `gap` 同时承担
"排除最近 N 日"与"选中日之间间隔 N 日"两个语义，放大到 252 会把两个都放大）：
`exclude_recent`（默认 **252**）与 `min_gap`（默认 **20**），旧 `gap` 保留为
已废弃的兼容参数（传了就同时覆盖两者，老调用方零改动）。

**可行性已实测验证**：

| 量 | 计划期估计 | **实施后实测（2026-09-17）** |
|---|---|---|
| `daily.jsonl` 行数 | 5501 | 5501（2004-02-03 ~ 2026-09-15） |
| 六个相似度特征**全部非空**的记录 | 2579 | **2579**（一致） |
| 排除最近 252 天后可选作类比的历史日 | 约 2327 | **2328** |

**改 252 不会把照镜子废掉**，样本完全够（2328 天可比）。
（注：M2 自检时这里一度读到 2461 / 2210，**那是 §19.3 那个预热 bug 污染后的读数**，
bug 已修，以本表为准。）
**注意：不需要重跑 `--backfill`** —— `similar_days` 只在 `mirror()` 里被消费，
`daily.jsonl` 存的是原始指标、不存照镜子结果，所以这是**纯消费侧改动**。
（计划期写的"改完必须重跑 --backfill"是对依赖关系的误判，实施时已核实纠正。）

### 14.2 【缺陷·高】top-5 的中位数在统计上没有意义

现在的输出是"最近 5 个相似日之后 20 日中位数 +2.4%、上涨占比 80%"。
**5 个样本的中位数不是统计量**——这正是 `MIRROR_WARNING` 里道歉的那件事，
但道歉不能替代修正。邮件取的是**最小 5%（222 天）**，给的是分布
（中位/均值/25/75 分位/胜率），而不是 5 个点的中位数。**明显更对。**

**改法**：`similar_days` 增加"分位带"模式（取距离最小的前 N%，默认 5%，上限约 300 天），
结论句基于分位带；top-5 明细保留作为"最像的几天"展示，但**不再作为结论依据**。

**已落地（2026-09-17）**：`similar_days(..., quantile=0.05, max_band=300)` 返回 dict
（`picks` / `band` / `n_band` / `eligible` / `exclude_recent` / `min_gap` / `quantile`），
**不新增公开函数**（守住 §8.1 的接口预算）。实测分位带 = **116 天**，
`mirror()` 的结论句与体温表、页签、CLI 全部改成"基于 116 天的一档"，
top-5 明细降级为展示。**并同时报 `N_eff`**（§16.7 MED-3）：116 天 ÷ 20 日 ≈ **5.8 份**、
÷ 60 日 ≈ **1.9 份** —— 结论旁边必须写"真正独立的信息只有约 5.8 份"。

### 14.3 【缺陷·中】没有逐年拆解，发现不了"只反映某一次熊市"

邮件 §五有一张逐年拆解表（类比年份 2011/2013/2018/2020/2021 各自的 3 个月中位与胜率），
一下暴露关键事实——**5 个类比年份里 4 个继续跌，唯一例外 2020 是靠政策强刺激反转的**。
没有这张表，"6 个月后中位 −12.3%、胜率 21.2%"就只是一个没有出处的数字。

**改法**：照镜子输出增加"按年份拆解"（每个命中日归属年份 → 该年命中数、后续收益中位、胜率），
并加一条硬规则：**若结论由单一年份主导（占比 > 50%），输出里必须点名说出来。**

**已落地（2026-09-17）**：体温表新增"按年份拆开看"表 +
**单一年份 > 50% 时强制点名**（常量 `YEAR_DOMINANCE_WARNING`，文案含
"**本结论由 XXXX 年主导**"，有测试锁 `test_mirror_names_dominating_year`）。
**实测这条硬规则这次没有触发**（最大年份 2016 占 49/116 = 42.2%），
但表一摆出来就看见**真正的集中度**：2016 年 49 天 + 2017 年 35 天 = **72.4%**。
所以除硬规则外，另加一句**无阈值的描述**（"命中日最集中的两年是 2016 年和 2017 年，
合计占了 72.4%"）—— 硬规则负责"必须吭声"，这句话负责"让人自己看见"。

**实测年份拆解（2026-09-15 数据日、110 天分位带）**：

| 年份 | 命中天数 | 之后 20 日（沪深300）中位 | 上涨占比 |
|---|---|---|---|
| 2016 | 49 | +1.8% | 63% |
| 2017 | 35 | +3.6% | 94% |
| 2021 | 2 | +1.6% | 50% |
| 2022 | 25 | **−6.6%** | **0%** |
| 2023 | 5 | −0.8% | 40% |

**读法**：2022 年那 25 天之后**一个上涨的都没有**（中位 −6.6%），2017 年 35 天之后
94% 上涨 —— 同一批"位置很像"的日子，落在不同年份结果完全相反。
这就是为什么"总体中位 +1.5%"必须配这张表一起看。

### 14.4 【缺口·中】指标集里没有估值维度，而估值是唯一被验证过的长周期因子

邮件《单因子独立回测》（2026-09-13 09:38）结论：**ERP 股债性价比 rho=+0.481（p<0.001）、
五等分价差 +26.7pp，是最强单因子**；全A PE-TTM 分位 rho=+0.357 次之。

我现在的位置指标是**位置 / 宽度 / 量能 / 波动**四组，**没有估值**。而"大盘所处位置"
这个问题里，估值恰恰是最能回答"贵不贵"的那一维（体温表现有只有"指数在十年 90% 分位"
这种价格分位，**价格分位 ≠ 估值分位**——指数可以在价格高位而估值不高）。

**改法（**待核实数据可得性**）**：新增 ERP = 1/PE − 10 年期国债收益率。
需要全A PE 长序列（邮件用的是"万得全A口径"）+ 10Y 国债收益率序列。
**本地有没有、口径是否一致，我没把握**——列为待核实项；**没有就不做，绝不编数**。

### 14.5 【缺口·中】没有牛熊区间与时长统计

邮件《A股牛熊演变图（2005至今）》（2026-09-13 16:24）给了完整 13 段牛熊明细
（起止/月数/点位/涨跌幅），汇总：**牛市持续中位 27.2 个月、涨 57.0%；
熊市持续中位 12.0 个月、跌 34.4%**。

我目前只有 `core/index_regime.py::classify` 给的**单点状态**（牛/熊/震荡），
**答不了"这轮牛走了多久、超出历史中位多少"**——而这正是"位置"的一部分。

**改法**：新增牛熊区间统计（区间划分口径见 §14.6 的警示，两条并列），输出当前区间
已走月数、累计涨跌幅、与历史中位/区间的对比。

### 14.6 【口径警示·高】同一天两封邮件结论相反 —— 正面印证"不合成总分"是对的

同一条流水线在同一天发的两封邮件，结论**互相矛盾**：

| 邮件 | 时间 | 结论 |
|---|---|---|
| 《A股牛熊演变图》 | 2026-09-13 16:24 | **现在是牛市**，处在"牛市中的震荡" |
| 《A股大盘研判》 | 2026-09-13 17:11 | **牛市结束后的回落期**，"顶部已过、下跌中继"，**不算牛** |

相差 47 分钟、同一批数据，一个说牛一个说不算牛。根因是**判定口径不同**
（前者 20% 法则，后者 10 特征历史类比）。

这条实测证据正面支持本项目 2026-09-04 拍板的「**四指数并行不合成**」决策：
**多个口径并列摆出来，比合成一个总分诚实**。本子系统继续执行，并把这条实证写进
体温表的口径说明——它是"为什么不给总分"最有说服力的例证。

**同时**：§14.5 新增区间统计时，20% 法则与 MA250 斜率**两条口径都要给**，
不要挑一个。上面这张表就是挑一个口径的下场。

### 14.7 【方法论·最高优先】把「五维验证框架」纳入大盘评估

用户 2026-09-17 追问「邮箱语料的五维模型不纳入大盘的评估里面吗」——**应该纳入，
而且这是本子系统最缺的一块方法论**。

#### 他们做了什么

v5 面板（2026-09-13 13:42）把「大盘判断」拆成**五个维度，每一维单独做预测有效性检验**
（vs 未来 12 月收益的 Spearman rho + p 值 + 五等分价差），再按结论决定去留：

| 维度 | 检验结果 | 处置 |
|---|---|---|
| ① 牛熊**状态**判断 | ✅ 可用：与 20% 法则一致率 85.1%（基准 64.9%）；说熊 75% 真熊、说牛 93.5% 真牛 | 保留显示（去掉"建议动作"） |
| ② 趋势**方向预测** | ❌ 失效：rho=−0.048（p=0.59） | 权重 30% → **0，仅展示** |
| ③ 拐点**距离预测** | ❌ 无解：背离度 rho=+0.048（p=0.59），预警精确率 28% **低于**基础率 34% | **删除预测**，改客观事实 |
| ④ **ERP 估值**（长期） | ✅ 强有效：rho=**+0.481**（p<0.001），Q5−Q1 价差 **+26.7pp** | **新增**为战略仓位中枢 |
| ⑤ **资金层** | ❌ 证伪：三子指标 p=0.17/0.46/0.38，合成显著是"构造巧合" | 权重 30% → 建议移除 |

原话最扎心：「**该有效的没被重用，不该用的占了 85% 权重。**」

#### 我在做什么、差在哪（必须承认）

我的 `shadow_replay()` 是**规则级**回放（权益曲线 / 年化 / 回撤 / 夏普），回答的是
**"这条规则能不能赚钱"**。他们做的是**维度级**预测有效性检验，回答的是
**"这个指标跟未来收益有没有相关性"**。**这是两件事，而我只做了前者。**

不过我的实测**独立印证了他们的 ②③ 失效**：我跑的三条候选择时规则
（沪深300>MA20 / 宽度≥50% / 牛熊口径=牛）13.7 年**全部跑输买入持有**——
正对应他们说的"趋势层 rho=−0.048、广度动量 rho=−0.302（方向为负）"。

#### 最不舒服的一条：我的指标可能没有一维被验证过

我现在的位置指标是四组：**十年百分位 / 站上 MA20 占比 / 新高新低差 / 成交额分位 / 波动率**，
**全部是价格衍生量**。他们 v5 的批评是"不该用的占了 85% 权重"，
而在我这里是**接近 100%**——连唯一的"成交额"也仍是交易衍生量。

**结论：我现在这套指标里，可能没有一维被验证过能预测收益。** 这个可能性必须用数据确认，
不能靠"看起来有道理"。

#### 改法：新增「维度体检」

对现有每一个指标，算 **vs 未来 1/3/6/12 月收益的 Spearman rho + p 值 + 五等分价差**，
结果写进体温表；**没通过的指标在页面上标注「仅描述现状，不参与判断」**
（照他们 v5 的做法，把"描述"与"预测"在展示层就分开）。

这是决定"**该保留哪些指标、该补什么维度**"的唯一数据依据。做完之后，
§14.4 的 ERP 估值维度就从"可选项"变成"**必须补**"——因为它是唯一有强证据的外部候选。

**诚实提醒**：维度体检本身也可能过拟合（多重比较）。他们的做法是
**样本 129 个月 + 报告 p 值 + 承认样本局限**，我们照做，且结论要标注样本量。

### 15.2 措辞改口径（E4，这是一处真的过度解读）

我原来的写法：「三条候选规则 13.7 年**全部跑输买入持有**」。

**问题**：跑输 0.1 个百分点也叫"跑输"，但那就是噪声。按 E1 加上置信区间后，
正确表述是「**样本内、毛口径下无显著净边际**」。改法：

- 加显著性后才下结论；置信区间含 0 → 写「**无显著净边际**」，**不写"无效"、也不写"跑输"**；
- 只有置信区间**显著为负**时才写"显著劣于买入持有"；
- 这条同时要改**体温表与页签上已有的文案**（不只是计划书）——现在页面上写的是
  "候选规则 13 年全部跑输买入持有"，属于同一处过度解读。

### 15.3 【重要】一条与项目已拍板决定冲突的外部建议

外部技能明确建议用 **Deflated Sharpe Ratio（DSR）** 与 **CSCV/PBO** 做过拟合与多重检验校正。
但本项目 **2026-07-26 用户已拍板「多重检验校正（Deflated Sharpe 等）不做，勿再提」**，
该决定写在 `CLAUDE.md` 的战略方向一节。

**本计划遵守该决定，不引入 DSR/PBO。** 同时把两条边界写清楚，避免将来混淆：

1. **§15.1 采纳的 HAC t 值/置信区间，不是多重检验校正。** 它校正的是**同一条损益序列的
   自相关**（重叠窗口让有效样本量缩水），回答"**这一个**夏普与 0 的差别是否显著"；
   而 DSR 校正的是**"在 N 次尝试里取最大值"的挑选偏差**，回答"你试了这么多次，
   最好的那个是不是撞运气"。两者数学基础与用途都不同——**前者采纳，后者维持不做。**
2. **但多重比较的风险客观存在**，不能装作没有。本子系统的维度体检会测
   **5 个指标 × 4 个持有期 = 20 个组合**，与"公式农场 244 组网格挑冠军"是同一类问题。
   **处置：不引入 DSR，但输出里必须显式标注"共检验 N 个组合"**，让读者自己知道
   这是从 20 次里挑出来的——**诚实披露比添一套校正更符合本项目"先跑通再优化"的风格**，
   也是在不违反既有决定的前提下能做的最大让步。

### 15.4 §15 的验收标准

1. `shadow_replay` 的每一条规则都输出：夏普点估计 + **HAC t 值 + 95% 置信区间** + 有效样本量。
2. 输出**按持有段**的显著性（不只看日频）。
3. 每个结果**标注样本内 / 样本外两段**（前 70% / 后 30%）。
4. **毛口径**显式标注在报告抬头（与 T+1 口径并列）。
5. 文案改口径：置信区间含 0 → 「无显著净边际」；**体温表与前端页签的既有文案一并改**
   （不许只有计划书改、页面还留着旧说法）。
6. 维度体检输出标注"共检验 N 个组合"。
7. **不引入 DSR/PBO**——若将来有人提议，先回看 §15.3 与 `CLAUDE.md` 的既有决定。

## 16. 深度审查修订（2026-09-17 对抗式审查后，逐条必改）

审查发现 **3 条 HIGH**、5 条 MEDIUM、4 条 LOW 与本节相关。**本节是强制修订清单，
与前面各节冲突时以本节为准。** 另：§8 的「接口预算」也是本次审查的产物（HIGH-1）。

### 16.1 【HIGH-3】维度体检必须月频采样，否则 `N_eff≈9`，p 值是虚构精度

**问题**：§14.7 要对每个指标算 "vs 未来 1/3/6/12 月收益的 Spearman rho + p 值"，
数据源是**日频**（`_features_frame`）。而 **§15.1 E1 刚刚采纳了 `N_eff = T/factor` 作为"必须"**
——同一份计划书里 §14.7 用原始日频 p 值、§15 要求 N_eff，**自相矛盾**。

**实测**：`daily.jsonl` 5501 条 → 6 特征 `dropna()` 后 **2579 个日频观测**
（2016-02-03 ~ 2026-09-15；与计划期侦查一致。M2 期一度读到 2461 = §19.3 预热 bug 的污染）。
重叠前向收益下的**有效独立样本**：

| 持有期 | 重叠观测 | **有效独立样本** |
|---|---|---|
| 1 月（21 日） | 2558 | ≈122 |
| 3 月（63 日） | 2516 | ≈40 |
| 6 月（126 日） | 2453 | **≈19.5** |
| 12 月（252 日） | 2327 | **≈9.2** |

按 n=2327 报出的 `p<0.001` 是**虚构精度**。**对照**：借鉴的那封邮件用的是
**129 个月频观测**——抄方法时把采样频率丢了。

**修订**：§14.7 改为 **月度采样**（每月末取一个观测 → ≈129 个，**与邮件可比**），
并在输出里**同时报 N_eff**。验收加一条：**报告任何 p 值必须同时报 N_eff**。

### 16.2 【HIGH-4】成本不能省——`breadth50` 扣费后**转负**，"换手极低"是错的

**问题**：§15.1 E3 用"择时规则换手极低（13.7 年持仓占比 31.9%~100%）"当理由**拒绝成本分析**。
这个理由**与实测相反**，而且把两个不同的量当成了一个。

**实测（持有段统计，区间 2013-01-04 ~ 2026-09-16，3329 个交易日 / 13.2 年）**：

| 规则 | 持仓占比 | **建仓次数** | 持有段中位长度 |
|---|---|---|---|
| ma20 | 52.7% | **196 次** | **4 日** |
| breadth50 | 47.9% | **181 次** | **5 日** |
| regime | 43.6% | 15 次 | 28 日 |

196 次往返 / 13.2 年 ≈ **每年 15 次**，持有中位 4~5 天——**这是高换手翻仓，不是低换手**。
"持仓占比"是**暴露度**，不是换手率。

**按项目自己的成本参数**（`backtest/engine.py:133` `commission=0.0003`、
`:135` `stamp_tax=0.0005` 卖出单边）：单次往返 ≥ **0.11%**（尚未计滑点），
196 次 ≈ **21.6% 累计 ≈ 1.6pp/年**：

- `ma20` 年化 +2.6% → 扣费后 **≈ +1.0%**
- **`breadth50` 年化 +0.6% → 扣费后转负 ≈ −0.9%**

**后果正好打在 §15.2 想立的措辞纪律上**：毛口径写"无显著净边际"，扣费后 `breadth50`
是**显著劣于**买入持有。省略成本会把结论方向都改了。

**修订**：**撤销 E3 的"不做成本扫描"**，改为按项目默认成本做一次**净口径回放**，
毛/净并列。若坚持不做，理由必须改成"**未测**"，并**禁止任何基于毛口径的方向性结论**
（不能写"无显著净边际"，只能写"毛口径下 X，未计成本"）。
**并修正 §15.1 E3 与 §15.2 引用的 31.9%**（那是修 `regime` bug 之前的旧数，实测应为 52.7%）。

#### 16.2.1 已落地（2026-09-17）—— 交付后实测，与上面的"侦查数"略有出入，**以本表为准**

成本实现方式：**现读 `backtest/engine.py` 的默认值**（`BacktestEngine({})` 只取

|---|---|---|---|---|---|---|---|---|---|

| `breadth50`（宽度≥50%） | 48.0% | 181 | 5 日 | +0.5% | **−0.9%** | −8.2% ~ +7.9% | −56.3% | 0.0% | 37% |

（区间 2013-01-04 ~ 2026-09-16，3329 个交易日 / 13.7 年。计划期侦查表里的
"13.2 年"与"breadth50 181 次 / 47.9% / 毛 +0.6%"是另一次快速估算，

> **勘误（2026-09-17 M7，回应审计 F-03/F-04）**：本节 M2 期记的
> `breadth50` 是 **179 次 / 在场 47.1% / 毛 +0.3% / 净 −1.1%**，
> 而 2026-09-17 重跑 `shadow_replay()` 得到 **181 次 / 48.0% / +0.5% / −0.9%**
> （差 2 次建仓、0.9 个百分点 —— **不是四舍五入能解释的**）。

#### 16.2.2 实施中发现的一个新坑（计划书原来没有，**必须记录**）

§16.7 MED-4 曾建议把段长差异"归一化"掉——**段内日均收益**或**折算年化**。
按 `ma20` 的 196 段实测，这两种做法**会把结论的符号弄反**：

| 口径 | 结果 |
|---|---|
| **每笔平均盈亏（不归一化）** | **+0.28%（毛）/ +0.17%（净）** ✅ 与按天数加权的真实日均收益同号 |
| 段内日均收益（除以段长） | **−0.39%/天** ❌ 与真实日均收益**反号** |
| 按天数加权的真实日均收益 | +0.028%/天（在场日平均每天赚多少） |

**原因**：除以段长会给**长段**（趋势策略的赢家，最长 56 天）打折，却不给
**短段**（输家，最短 1 天）打折 —— 长赢家被稀释、短输家原样保留，均值必然被推成负数。
**处置**：段收益定义改为「**段内日收益复合后扣费，不做长度归一化**」，
检验的是"**每开一次仓，平均是赚还是亏**"；按天数加权的口径由主表的 HAC t 值承担。
这条已写进 `_segment_stats` 的 docstring，**并留证在体温表**（"按每一笔算（扣费后）：
平均 +0.2%、中位 −0.8%、赚钱的只占 22.0%"）。

## 17. 【设计纠错】推送时刻重定：体温表必须在当天盘后推，不在次日早上（2026-09-17 用户指出）

### 17.1 用户指出的问题（我错了）

用户原话：「大盘体温表都已经是15点50采集了，**干嘛要早上推送**，早上推送**要加上隔夜的新的信息**啊。」

我原来的设计是：15:50 只采集不推送，**次日 09:05 才推**。**这个设计是错的。**

### 17.2 实测证据（不是推理，是跑出来的）

跑 `core.kline_cache_maintenance.expected_last_trading_day()` 对照三个时刻：

| 什么时候跑 | 「应有数据的交易日」 | 说明 |
|---|---|---|
| 交易日 T 的 **15:50**（盘后采集） | **T** | 当天数据已入缓存（15:45 刚补过尾段） |
| 次日 T+1 的 **09:05**（原计划推送时刻） | **还是 T** | 因为没到 15:00，函数返回上一交易日 |
| 次日 T+1 的 15:50 | T+1 | 这才前进一天 |

**结论：15:50 与次日 09:05 算出来的记录逐字段相同**——早上那张卡，
**与前一天下午就能发的完全一样，一个新数字都没有**。

### 17.3 我设计错的根本原因

我把体温表当成了"每天早上看一眼的东西"。但**它是用当天收盘价算出来的**：
收盘价、多少股票在均线上方、成交额——**全是当天收盘才定下来的**。
它天生属于「**收盘后**」，**拖到第二天早上也不会变**。

硬拖到早上，等于**把昨天的作业今天早上再交一遍**。而早上真正值钱的东西我一个都没放进去：
**美股隔夜收盘、港股、隔夜消息与政策**——那些才是"过了一夜新发生的事"。

### 17.4 修正设计

**第一件（必做）：体温表挪到当天 15:55，与复盘报告合成一条消息**

| 时刻 | 推什么 | 用户看到的效果 |
|---|---|---|
| **当天 15:55** | 市场体温 + 我的账户 + 需要留意的清单 | **收盘后一条消息看完今天**，全部是当天数据 |
| ~~次日 09:05~~ | ~~同一张体温表~~ | **取消——与前一天盘后内容完全重复** |

实现上：把 `scheduler/__main__.py` 里已注册的
`market_position_morning`（09:05）**去掉**，
把体温表推送并入复盘报告的 job（见 `2026-09-17_盘后复盘报告_计划书.md`）。
**现在这两个 job 一次都没跑过**（用户尚未重启 scheduler），改动零风险。

**第二件（已拍板 2026-09-17：选 (b)）——早上改发「隔夜简报」**

用户 2026年9月17日拍板选 **(b)**。定案如下：

| 时刻 | 推什么 | 内容 |
|---|---|---|
| **当天 15:55** | **今日收盘体温表**（后续与复盘报告合成一条） | 位置 / 宽度 / 量能 / 照镜子 / 影子规则 —— 全部是**当天收盘**的数字 |
| **次日 09:05** | **隔夜简报** | **只放"过了一夜新发生的"**，见下表 |

**隔夜简报的内容清单**（原则：**只放新信息，体温表只作一句话背景**）：

| 板块 | 放什么 | 数据来源（都是现成的，不用新建） |
|---|---|---|
| 美股隔夜 | 道指 / 纳指 / 标普500 的隔夜收盘与涨跌幅 | **`brain/market_panel.py::overnight_facts()`**（结构化数字，见下方 M7 更正） |

## 18. 【上下游缺口】缓存新鲜度检查分辨不出"空壳 bar"，会一直误判"1d 新鲜"（2026-09-17 实测发现）

### 18.1 现象

2026年9月17日实测：体温表卡片上写着「数据滞后：最新有效交易日 2026-09-15，应有 2026-09-16」。
去查是不是误报：

| 检查项 | 结果 |
|---|---|
| 沪深个股 parquet 里的最后交易日 | 2026-09-16（5204 只票**都有这一行**） |
| 但这一行**有成交量的**只有 | **10 只（0.2%）** |
| 结论 | **9月16日那根真的是空壳，卡片没报错** |

### 18.2 真正的洞在**上游**

同一时刻跑 `core.kline_cache_maintenance.ensure_cache_fresh()`，它报的是：

```
缺 ['5m', '1m']，已后台启动补拉
```

——**1d 不在"缺"的名单里**，因为 `stale_periods()` 的判据是
`cached_last_date(period) < expected`，而它读的是 **manifest 表里的 `MAX(last_date)`**，
那格里明明白白写着 `20260916`。

**问题**：manifest 只记"这一行存在"，**记不了"这一行有没有成交"**。
于是**空壳 bar 会被当成正常数据，补拉永远不会被触发，它就永远卡在缓存里**。

这和本项目已有的一类坑同源：**判据只看"有没有"，不看"内容对不对"**
（类似 `CLAUDE.md` 里记的 QMT 日线"有数据但陈旧"事件——当时的修法也是把判据从"取空"
扩成"末根 < 应有一根"；**这次要在那个基础上再加一条"末根得有成交"**）。

### 18.3 好消息：本子系统自己**没有**被这个洞骗到

`core.market_position.last_valid_date()` 用的是**成交量 > 0 的股票占比 ≥50%** 这条判据，
所以它正确地把 9/16 判为无效、回退到 9/15。**洞只在上游缓存维护，不在大盘位置。**

### 18.4 修法（两条，建议一起做）

| # | 改哪 | 怎么改 |
|---|---|---|
| **①（治本）** | `core/kline_cache_maintenance.stale_periods()` | 对 **1d** 增加一条"末根有效性"检查：抽样或全量确认最后一根 bar 的成交量不为 0；不达标则**也算 stale**，触发补拉 |
| **②（兜底）** | 大盘位置采集 | 发现 `stale=true` 时**记一条警告**并（可选）**自动触发一次 1d 尾段补拉**；避免"知道数据旧但没人去修" |

**同时**：`data/kline_cache/manifest.db` 的 `MAX(last_date)` 语义要写进文档——
**它代表"有行"，不代表"有数据"**。任何拿它当新鲜度判据的地方都要知道这个区别。

### 18.5 验收标准

1. 构造"末根有行但无成交"的缓存，断言 `stale_periods()` **把该 period 报为 stale**（有测试）。
2. 体温表 `stale=true` 时，日志里出现一条明确的 WARNING 与"该跑哪条命令"的提示。
3. `CLAUDE.md` 的日线新鲜度条目补上"manifest 的 last_date 不代表有成交"这一条。

### 19.3 M2 自检时先抓到一个**静默数据劣化 bug**（这是本节最重要的一条）

**症状**：M2 实测"六特征全非空的日频观测"只有 **2461** 条，而计划期侦查是 **2579** 条；
跑一次 `collect(bars=300)` 之后又变回 **2579** —— 同一份数据，跑一次日常采集就少 118 天。

**根因（实测复现并定位）**：日常采集算 `DEFAULT_BARS = 300` 天，
但 `_load_matrices(300)` 把日线**截断成 300 根**，于是窗口头部的长回看指标算不出来 ——
`amount_pct_1y` 用的是 `rolling(250, min_periods=120)`，**头 120 天必然是 NaN**
（新高新低是 60 日窗，同理）。而日常采集会把这 300 条**全部 upsert 覆盖**回录像
（自愈设计的代价），于是**历史上本来是好的记录被改成了缺值**。

**实测证据（逐字段对比跑前/跑后）**：

| 项 | 结果 |
|---|---|
| 跑前六特征齐全 | 2579 条 |
| 跑后六特征齐全 | **2461 条（−118）** |
| 被劣化的记录 | **118 条**，日期 2025-04-17 ~ 2025-10-13 |
| 少掉的字段 | **全部是 `amount_pct_1y`** |
| 被"修好"的记录 | **0 条**（单向变坏） |

> **勘误（2026-09-17 M7，回应审计 F-04）**：上面的 118 条 / 2025-04-17 是 M2 期的读数。
> 用录像重放这条"无预热"路径，实测劣化条数**取决于重放了几天日常采集**：
> - **单次** `collect(bars=300)`（无预热）：**72 条**，2025-06-26 ~ 2025-10-13
>   （M7 复现，2026-09-17）；
> - **连续多天**滑窗重放：审计报告复现为 **119 条 / 起点 2025-04-16**；
> - M2 当时记的是 **118 条 / 起点 2025-04-17**。
>
> 三者**都真**，差的是"重放的窗口长度"与边界那一天。结论方向不变（单向变坏、只伤
> `amount_pct_1y`），但**引用条数时必须说明口径**，不能拿一个数当普适事实。

**为什么这条比"缺行"更严重**：记录**看起来是完整的**（有日期、有价格、有宽度），
只有成交额那一格悄悄变 null。任何按 `dropna()` 取样本的下游
（照镜子、维度体检）都会**静默丢掉那 118 天**，而且不知道丢了。

**修法（已落地 + 有回归测试）**：新增常量 `WARMUP_BARS = 300` ——
日常采集**多读 300 根做预热**，但**只输出窗口内最后 `bars` 天**，
预热段不算正式记录。修完复测：**差值 0、被劣化 0 条**。

**回归测试**：`tests/test_market_position_runner.py::TestWarmup::test_daily_collect_does_not_degrade_history`
—— 先全量回填，再跑日常采集，**逐条断言"跑之前有值的字段跑之后不许变 null"**。

**顺带纠正 19.3 的旧结论**：我在 M2 里曾把"2461/2210/110"当成"实测值"写进本节，
**那是被这个 bug 污染后的读数**。修完之后以本表为准：

| 项 | 计划期侦查 | M2 期（被 bug 污染） | **修正后（交付值）** |
|---|---|---|---|
| 六特征全非空的日频观测 | 2579 | 2461 | **2579**（计划期是对的） |
| 排除 252 天后的可选历史日 | ≈2327 | 2210 | **2328** |

| `breadth50` 建仓次数 / 在场占比 / 毛年化 | 181 次 / 47.9% / +0.6% | 179 次 / 47.1% / +0.3% | **181 次 / 48.0% / +0.5%**（2026-09-17 重读，见下方勘误） |

`breadth50` 那一行与计划期侦查的差（181 vs 179）与预热 bug **无关**

#### 19.6.1 【重要·可复现性】影子回放的数字**会随本地日线缓存漂移**

M7 逐行验证时实测到：M2 记的 `breadth50`「179 次 / 在场 47.1% / 毛 +0.3% / 净 −1.1%」，
到 M7 复现成「**181 次 / 48.0% / +0.5% / −0.9%**」（`ma20` 的 196 次与 `regime` 的 15 次没变）。
**先排除了"我们自己的 bug"**：

| 检查 | 结果 |
|---|---|
| 全量回填后测一次 | 181 / 48.0% / +0.5% / −0.9% |
| 再跑一次日常采集（bars=300）后测 | **完全一样**（无差异） |
| 结论 | **不是** §19.3 那类"日常采集覆盖历史"的病 —— `collect` 本身是可复现的 |

那差异只能来自**输入**：影子状态是每次 `collect` 从本地日线缓存**现算**的
（`above_ma20_pct` 来自全市场宽度），而这个仓库**同时有别的会话在跑**，
日线缓存会被别的进程刷新（本项目 2026-09-17 已在 RAG 计划书 §3.3 记录过这个并发事实）。
缓存一变，宽度序列就变，`breadth50` 这种**贴着 50% 阈值的规则**就会多/少几次翻仓。

**处置（不是修 bug，是改引用方式）**：
1. 引用影子回放数字时**必须带数据日期**（本文所有数字的数据日是 **2026-09-15**）；
2. 把它当**活读数**而不是冻结快照 —— 换个数据日，±2 次建仓 / ±0.2 个百分点是正常的；
3. `ma20` 的 196 次与 `regime` 的 15 次两个数据点**前后一致**，说明漂移不是全局的，
   而是集中在贴阈值的规则上（这本身也说明 `breadth50` 的信号是"擦边"的，更不该信它）。

### 19.7 M7 逐行验证：自己抓到的那个真 bug（`regime_20` 被静默丢掉）

**症状**：`regime_20`（20% 法则牛熊口径）在**全部 5501 条记录里 0 条非空** —— 实测确认。

**根因**：`_build_record` 写记录时按列名判断该不该转 float，写的是
`_f(r[col]) if col != "regime" else str(...)`。M3 新增的 `regime_20` **也是文本列**，
却落进了 `_f()` 分支 → `float("bull")` 抛 `TypeError` → **被 `_f` 的 `except` 吞掉并返回 None**。
于是：
- 记录里的 `regime_20` 永远是 None（静默丢一维）；
- 页签上「按 20% 法则给时间轴涂底色」这条**什么也画不出来**（`regimeBands` 读不到值）；
- 体温表那一段不受影响（它是从指数序列现算的，不走记录）。

**这正是本项目最痛的一类 bug**：不报错、不崩、记录看起来完整，只是**某一维悄悄空了**。

**修法**：把文本列**显式列成常量** `TEXT_COLS = ("regime", "regime_20")`，
并按 `col in TEXT_COLS` 判断 —— 以后再加文本列必须一并登记，不会再靠"记得改那个 if"。

**回归锁**：`tests/test_market_position_runner.py::TestCollect::test_text_columns_survive_the_record_writer`
断言三条指数记录的 `regime_20` 必须是 `bull/bear/range` 之一（不是 None）。

**修完实测**：`regime_20` 非空 **3328/5501** 条（其余 2173 条是 2013 年以前、本来就没有指数数据），
最新一条沪深300 = `regime: range` / `regime_20: bull`（正是"两条口径分歧"那个真实例子）。
