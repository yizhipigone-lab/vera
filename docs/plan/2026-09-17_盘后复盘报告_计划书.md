**所以：账户那一半（持仓表现/盈亏/成交）不需要新建，重复造就是「第三份」。**
本计划的任务是**补缺口**，不是重写日报。

## 3. 用户已拍板的架构裁决（沿用计划书 §12，不重议）

**页面上合，代码上分，依赖单向朝下。**

```
notes_gen/daily.py（新增：复盘编排器）
      ├─→ core.market_position_runner.thermometer_md()   ← 盘面段（复用，不写第二份）
      └─→ trade 域数据（daily_report 表 + 持仓 + 止损线）  ← 持仓段 + 留意清单
```

**为什么编排器放在 `notes_gen/`**：那里已有 `notes_gen/monthly.py`（月度笔记），
语义完全一致（生成笔记/报告），**不新增顶层包**（铁律 8「如无必要勿增实体」）。
不放进 `trade/`：`trade/` 有严格的模块纪律（文档记的是 9 模块），且复盘是"报告"
不是"交易"，放进交易域会让交易包继续膨胀。

**注意**：`core/market_position_runner.py` 绝不 import trade 这条守护**必须保持不变**
（`tests/test_market_position.py::test_ast_no_trade_import`）。隔离是靠**编排器在更外层
同时 import 两边**实现的，不是靠放松里层的守护。

## 4. 触发方式：独立 job，15:55（不碰实盘进程）

> **先把"谁在什么时候到"说清楚（2026年9月17日用户抓到我把它讲错了，特此钉死）**：
> 会有**两份**东西、**两个时刻**，不要混：
>
> | 报告 | 生成/推送时刻 | 用户什么时候看到 |
> |---|---|---|
> | **大盘体温表**（本计划之外，已建） | 15:50 采集，**次日 09:05** 补采并推送 | **早上、开盘前** |
> | **盘后复盘报告**（本计划） | **当日 15:55** 生成并推送 | **当天下午、收盘后** |
>
> 为什么会容易混：代码里两个都是 `hhmm` 字符串（`"09:05"` / `"15:55"`），
> 不写清"这个时刻是白天还是晚上、用户当时在干什么"就会说错。

有两个选项，我推荐第二个：

| 选项 | 做法 | 评价 |
|---|---|---|
| A | 接在 `_notify_daily` 里一起发 | **顺序冲突**：EOD 在 15:05，而大盘位置 15:50 才采集完，15:05 取不到当天盘面。且要改 `trade_main.py` 实盘代码——**脆弱期少动为妙** |
| **B（推荐）** | **新增独立 scheduler job，每交易日 15:55**，纯读 | ①顺序天然正确；②`trade_main.py` 一行不改；③报告生成失败绝不影响交易链 |

时间链（顺序不能错）：

| 时刻 | 步骤 | 状态 |
|---|---|---|
| 15:05 | 交易端 EOD 归档（含 `daily_report` 落库） | 现有 |
| 15:45 | K 线缓存补尾段 | 现有 |
| 15:50 | 大盘位置采集 | 2026-09-17 已建 |
| **15:55** | **复盘报告生成 + 推送** | **本计划新增** |
| 09:05（次日） | 大盘体温表推飞书 | 2026-09-17 已建 |

**代价（如实说）**：15:55 读到的账户数据是 15:05 落的快照。但那时已收盘，
资产数字不会再变，可接受。**唯一的坏情况**是 15:05 那次 EOD 因关机没跑——
此时 `daily_report` 表缺当日行，复盘报告的持仓段要**明确写"当日无交易归档"**，
**不能用昨天的数字冒充今天**。

## 5. 「需要你留意的清单」（原「明日关注」改名）

**改名理由**：「明日关注」承诺了预测，与业务铁律 1（宏观/研判只报告、仓位人工把关）
冲突——推到手机上的报告一旦像建议，就会被当建议读。改叫「需要你留意的清单」，
只陈述事实。

**v1 只做规则事实，不做主观预测，不调 LLM。**

| 条目 | 数据来源 | 把握度 |
|---|---|---|
| ① 持仓中距止损线最近的 N 只 | 持仓 `avg_cost` + 当日收盘价（本地日线缓存，离线可得）+ `trade/config.py::StopConfig` 的硬止损阈值 | **待核实**：止损阈值在多条件（硬止损/移动止盈/阶梯止盈/时间止损）下"当前生效的那条"如何判定，需先读透 `StopConfig` 语义再定 |
| ② ETF 轮动当前目标腿 + 下次锚定日 | payload 里已有 `rotation`（`trade_main.py:1042~1057`） | 高（现成字段） |
| ③ 大盘位置侧状态提示 | `market_position_runner.latest()` 的 `stale` / 宽度阈值 | 高（现成字段） |
| ④ 当日公式出票 | **待核实**：`trade/store.py` 里只有 `RotationSignalStore`，没找到 auto_buy 信号的专用表（可能在 audit 事件里） | **待核实**，查清后决定是否纳入 v1 |

**LLM 只允许做一句话归纳，且默认关闭**（选项同 `trade/config.py::FeishuConfig.ai_review`
的既有惯例：默认 `False`）。

## 8. 不做（划界）

- **不重写已有的盘后日报**（总资产/盈亏/成交/卖飞/仓位变动全部保留原样）。
- **不给"明日关注"做预测**：只陈述规则事实，不改铁律 1。
- **不做盘中实时版**：只在盘后生成。盘中提醒属于另一个失败域（应该是 `brain/alert_rules.py`）。
- **不合并舆情日报**：见 §7 最后一行。
- **不自动联动任何仓位**：报告里出现的"距止损线还有 2%"只是提示，
  **绝不触发减仓**——止损由 `trade/` 既有的自动规则独立负责，报告线不介入。

## 9. 验收标准

1. `python -m notes_gen.daily`（或等价 CLI）能生成一份含**三段**的 Markdown：
   市场盘面 / 我的账户 / 需要你留意的清单。
2. 账户段的数字与同日飞书日报**逐项一致**（因为复用同一份 payload，不一致即为 bug）。
3. 停机场景单测：`daily_report` 表无当日行时，持仓段写明"当日无交易归档"，
   且**不出现**任何昨日数字冒充今日。
4. AST 守护仍然通过：`core/market_position*.py` 无 `import trade`。
5. 投递：飞书卡片 + 邮件两路各实测成功一次（邮件用 `tools/send_email.py` 的既有能力）。
6. 页签：大盘位置页签出现「今日复盘」折叠块，内容与推送一致。
7. `pytest tests/` 全绿。

## 11. 邮件研究带来的修订（2026-09-17 用 qqmail 技能读信后新增）

用户让我用 `qqmail` 技能收了收件箱最新 9 封。对本计划有四点影响，其中两点**改了原判断**。

### 11.1 邮箱投递的必要性被实证（原判断加强）

收件箱里有一个**独立的「研究产物自动分发」流水线**（发件人 `研究产物自动分发 <dcliuzh@qq.com>`），
最近 9 封全是 A 股研究产物包，**附件是 6.2MB / 82 个文件的 zip**。

含义：`tools/send_email.py` 那条路**不是"锦上添花"，而是这台机器上已经在用的主力分发方式**。
§10 第 3 条我倾向"v1 只接 `send_email.py`"——**结论不变，但理由从"够用"升级为"与既有实践一致"**。

同时补一条原计划漏掉的：**邮件可以带附件**。复盘报告若做成 HTML + 附件包，
比飞书卡片（不支持表格/图片）更能承载明细。v1 仍是纯文本/Markdown 正文，
**附件包列为可选项**，不做进 v1。

### 11.2 【改判断】「留意清单」不要掺外部研报结论（原计划没说清）

那批邮件里有大量**外部研报的研判结论**（例如《A股大盘研判》给出"还要再跌约 22%、
2027 年 2~3 月见底、三种情景概率 50/25/25"）。这些结论**看起来非常适合放进"留意清单"**，
但**不能放**：

- 业务铁律 1：宏观/研判类内容**只生成报告提示，绝不联入仓位调度**。
- 更要紧的是：§14.6（见 `2026-09-17_大盘位置与趋势研判_计划书.md`）实测发现
  **同一批数据、同一天，那套流水线自己就给了两个相反结论**（16:24 说"现在是牛市"、
  17:11 说"不算牛、下跌中继"）。把这种自带矛盾的外部观点塞进复盘报告的"留意清单"，
  等于把矛盾传染给用户。

**结论**：留意清单**只用本系统自己算出来的、口径写明的数字**（大盘位置的 `daily.jsonl`、
payload 里的轮动信号、持仓止损距离）。外部研报**最多在报告末尾加一行"邮箱有 N 封新研报"**
（纯事实、不给结论），且这一行**默认关闭**。

### 11.3 值得抄的做法：那批邮件每份都带「方法局限」和「自查发现的错误」

那 9 封邮件的共同特征：每份都有独立的「方法局限」章节，多份还主动用红字标出
**自己上一轮算错的地方**（例如"月末推算用了 `DateOffset(months=1)` 落到周六，
静默取到陈旧价格，买入持有年化被低估"、"用月度网格算回撤导致 2015 股灾回撤只显示 -17%
（真实 -57.9%）"）。

**抄法**：复盘报告的「需要你留意的清单」后面加一段**固定的口径局限说明**，
至少写清：①账户数字来自 15:05 的 EOD 快照；②盘面数字来自 15:50 的采集，
数据日期可能滞后；③三条已知偏差（ST 涨停漏计 / 生存者偏差 / 百分位窗口不足十年，
已在 `CALIBER_FOOTER` 常量里）。**不写局限的报告会被当结论用。**

### 11.4 【改判断】止损线那条，找到了可参照的算法口径

那批邮件算"距年线多少"用的是 `core/index_regime.py` 同一族的 MA250 口径，
而我们的止损线是 `trade/config.py::StopConfig`。**邮件没直接给答案**，
但它示范了一种做法值得抄：**把"当前生效的那一条"明确写出来，而不是把五段配置都摊开**。

故 §10 第 1 条的处理方式修订为：**先读透 `StopConfig` 的优先级语义，
在报告里点名"当前生效的是哪条规则、阈值多少、以什么价为准"**；
读不透就不做这一条（原判断"宁可 v1 少一条也不出错数"不变）。

## 12. 外部最佳实践对照与采纳（2026-09-17 联网检索后新增）

检索来源：[SMB Training 盘后复盘指南](https://www.smbtraining.com/blog/how-to-review-your-trading-after-the-market-closes)
（职业交易员训练机构的盘后复盘清单）。这份清单暴露了本计划一个**结构性偏向**。

### 12.1 逐条对照

| # | 外部实践 | 我们现状 | 采纳结论 |
|---|---|---|---|
| **D1** | **好日子也要复盘，不能只在亏钱时复盘**——"赚了就没必要看"是最常见的错误 | 现有飞书日报 + 我的计划都是**中性陈列数字**，没有"今天做对了什么"这一视角 | ✅ **采纳**（§12.2） |
| **D2** | 复盘要看**过程与心态**，不只看盈亏：是否追高、是否过度交易（`overtrading`/`churning`）、最好的与最差的 `setup` | 我的留意清单只有"距止损线/轮动腿/公式出票"——**全是持仓与市场，没有一条关于"我的交易行为"** | ✅ **采纳可自动计算的部分**（§12.3） |
| **D3** | **持续统计**（keep stats），并**从小处开始、逐项增加** | 无跨日累计；我的 v1 只做规则事实（与"从小处开始"一致 ✅） | ✅ 采纳（§12.4） |
| **D4** | 需自述的项（心态是否失衡 `on tilt`、精力水平、是否做好准备） | 系统观测不到 | ❌ **不采纳**：系统无法观测自述状态；**编一个"心态分"就是编数**，违反项目"不拍脑袋" |

### 12.2 采纳 D1：报告要有"做对了什么"

现有日报与我的计划都偏向"哪里出问题"。加一小段**「今天做对的」**，规则事实、不吹捧：

- 当日**盈利贡献最大的 1~2 只**（按已实现盈亏排序）及其原因（止盈落袋 / 持有上涨）；
- **卖在相对高点**的（现成的卖飞信号反过来用：卖出价接近当日最高价）；
- **按规则止损且事后证明是对的**（卖出后该票继续跌）——这条能强化"守纪律"的正反馈。

注意：这**不是自我表扬**，而是**防止形成"只有坏消息"的复盘偏差**——
只报问题会让人回避看报告，这是 SMB 那篇文章的核心论点。

### 12.3 采纳 D2：加一条"我的交易行为"维度（可自动计算的部分）

从现有数据能算出来的三项（**都只陈述、不评判**）：

| 条目 | 怎么算 | 数据源 |
|---|---|---|
| **换手是否异常** | 当日成交额 / 总资产，与过去 60 个交易日的分位对比 | `daily_report` 表的 `turnover` + `total_asset` |
| **笔数是否异常** | 当日成交笔数（买+卖）与过去 60 个交易日的分位对比 | 同上 `buy_count`/`sell_count` |
| **是否在追高** | 买入价在当日**振幅中的位置**（`(买价 − 当日最低) / (当日最高 − 当日最低)`），>70% 记为"买在当日偏高位置" | 成交记录 + 当日 OHLC（本地日线缓存可得） |

**这三项必须只陈述事实、不写评价词**（不写"你今天操作太频繁了"），
只用"当日换手处于过去 60 日的第 87 分位"这种客观句。评判留给用户——
这与铁律 1（仓位由人把关）同源：**系统描述，人判断**。

### 12.4 采纳 D3：加一小段「累计统计」

单日数字看不出趋势，复盘的真正价值在累计。在报告末尾加 3~5 行滚动统计：

- 近 20 个交易日：胜率、已实现盈亏合计、最大单笔亏损；
- 连续触发止损的次数（若有）；
- 本月至今 vs 上月同期（`daily_asset` 表已有月度口径，参考 `trade/analysis_api.py` 的月度端点）。

**只做已有数据的聚合，不新增取数**。

### 12.5 §12 的验收标准

1. 报告含「今天做对的」段（≥1 条，无内容时明写"无特别亮点"而不是略过）。
2. 报告含「我的交易行为」段三条（换手分位 / 笔数分位 / 买价位置），**全部为客观陈述，
   全文不得出现评价性措辞**（加一条测试：断言这段文案里不出现"过于/太/应该"等词）。
3. 报告含「累计统计」段（近 20 日与本月至今）。
4. **不引入任何需要用户自述的字段**（心态/精力/准备度）——系统观测不到的就不编。
5. §10 的"止损线"条目仍受"读不透就不做"约束，**不因为多了这几项而放松**。
6. **【大白话·硬条款】** 报告全部文案必须符合 `AGENTS.md` 沟通风格第 7 条
   （用户 2026年9月17日明确要求"所有给我的数据、表述都要用大白话，可以打比方，我是小白"）。
   **可机器检查的判据**：
   - 正文**不得出现未解释的英文缩写**（首次出现必须跟一句白话）；
   - **每个数字后面必须跟一句白话说明它意味着什么**（如"成交额 16,037 亿元，是过去一年里最低的
     1.6% 那几天之一"），不许只甩数字；
   - "需要你留意的清单"里**不得出现评价性措辞**（不许写"你今天交易太频繁了"），
     只陈述事实（测试断言不出现"过于/太/应该"）；
   - 落地靠模板：文案与 `trade/llm_review.py::_PROMPT` **必须把这条写进去**，不靠每次自觉。

### 12.6 实测核对（2026-09-17 只读查 trade.db，看到的数据事实）

写 §12.2~§12.4 时我实际只读查了一次生产库（`mode=ro` + `PRAGMA query_only=1`，

## 13. 深度审查修订（2026-09-17 对抗式审查后）

审查结论：**本计划整体可批准**，只有 1 条实质问题（除零）与 4 条需补，成本都低。

### 13.1 【MED-2·实质】"买价在当日振幅中的位置"会**除零**

**问题**：§12.3 写「买价在当日**振幅中的位置** = `(买价 − 当日最低) / (当日最高 − 当日最低)`」，
数据源"**本地日线缓存可得**"——**但没有任何有效性判据**。

而本地日线缓存**盘前抓数会造出"有日期、无成交"的空壳 bar**（本项目 2026-09-16 刚实测过：
`open=high=low=close=11.81` 且 `volume=0`）→ 空壳 bar 的 `high − low = 0` →
**`ZeroDivisionError` 或 `inf`**。这个坑本项目刚踩过（大盘位置 §4.2），这里又踩一次。

**修订**：
- 复用 `core.market_position.last_valid_date` 同款的「**成交量 > 0**」判据；
- `high == low` 时该条写成「**当日无有效振幅**」，**不算出一个数**；
- **明写"仅限当日成交"**——`KlineCache.get()` 只支持前复权
  （`core/kline_cache.py:207-209` 对非 `front` 直接 `raise ValueError`）；
  当日成交价与前复权当日 OHLC 同日可比，**但扩展到历史成交日就会口径错配**。

### 13.2 【M7】§12.4 的"参考"必须改成"**复用**"

§12.4 原写「本月至今 vs 上月同期（`daily_asset` 表已有月度口径，**参考**
`trade/analysis_api.py` 的月度端点）」。**"参考"在实施时几乎必然变成"照着写一遍"** ——
月度盈亏聚合就会出现两份实现（`trade/analysis.py` 一份、`notes_gen/daily.py` 一份），
而项目对这一类零容忍。

**既有实现（机器核验）**：真正的**纯函数**在
**`trade/analysis.py::build_summary_view`** 与 **`trade/analysis.py::build_daily_pnl_view`**
（`trade/analysis_api.py` 里的 `@router` 只是薄层，含 `year/month` 参数与
`load_prev(f"{prefix}-01")` 上月对比）。

**修订**：§12.4 改成「**复用** `trade.analysis.build_summary_view` /
`build_daily_pnl_view` 的既有口径（**同一函数、不重算**）」；
并在 §6「有没有第三份?」那一行**点名这两个函数**。

### 13.3 【M8】缺**反向** AST 守护——铁律 1 的守护是双向的

**核验**：项目对铁律 1 的守护是**双向**的——
`tests/brain/test_sentiment_acceptance.py` 的**证据 1** = 报告模块不得 `import trade`（AST 正向）；
**证据 2** = **`trade_main.py`（实盘入口）不得引用任何舆情模块**（反向）。

而本计划 §9 验收第 4 条只写了「AST 守护仍然通过：`core/market_position*.py` 无 `import trade`」
——**只守住了旧边，新边没有任何断言**。`notes_gen/daily.py` 必然 `import trade.config`
（取 `StopConfig`），一旦它被 `trade/` 某处 import，"报告 → 交易"的反馈环就通了。

**修订**：§9 验收加一条**镜像断言**：
「AST 断言 **`trade_main.py` 与 `trade/` 下模块不 import `notes_gen.daily`**」，
照 `test_sentiment_acceptance.py` 证据 2 的写法；并在 §3 的依赖图旁写明
"**这条新边靠反向 AST 断言守住**"。

（附注：`notes_gen/monthly.py` 读 trade 数据的方式是**按 sqlite 路径直读**
`data/trade/trade.db`，**不 import `trade`**——所以"放 `notes_gen/`"这个选择本身有先例、站得住。
`trade/__init__.py` 刻意零 eager import，故 `import trade.config` 不会连带引入整个交易栈。）

### 13.4 【M6】落盘路径必须钉死，且**不能落进 RAG 的语料根**

**问题**：本计划 §9 验收只说"能生成一份含三段的 Markdown"，**通篇没写落盘路径**。
而项目惯例（`brain/prompts.py:104`）是「简报/研究报告默认落 `docs/brief/` 或 `docs/report/`」。
**一旦复盘报告按惯例落进 `docs/`，它就会被 RAG 索引进去**——系统每天生成一份报告，
日积月累**污染自己的检索库**。这正是 RAG 计划书 §11.2 要防的"索引漂移"，
但两份计划书各写各的，**没人画这条连线**。

**修订**：**钉死落盘路径为 `data/daily_review/<日期>.md`**：
`data/` 已被 RAG 的 `exclude_dirs` 排除，**天然不会自我污染**；且与
`data/market_position/daily.jsonl` 同族（运行时产物，gitignore）。
**不用 `docs/`。** 并在本计划加一行交叉引用：
「本目录不是 RAG 语料源；改动前先看 `docs/plan/2026-09-17_研究库检索增强RAG_计划书.md` §12.6」。

### 13.5 【L3】术语中文化：§10 的五个配置类名要配中文

§10 把 `CostStopConfig` / `TrailingStopConfig` / `LadderTpConfig` / `TimeStopConfig` /
`CondTimeStopConfig` 五个类名并排罗列，**无中文对照**，而同一份计划书 §5 已用了
"硬止损 / 移动止盈 / 阶梯止盈 / 时间止损"。规则虽豁免"代码标识符"，
但这是给量化入门者看的计划书。

**修订**：照 §5 的写法**先中文再附类名**——「硬止损（`CostStopConfig`）/
移动止损止盈（`TrailingStopConfig`）/ 阶梯止盈（`LadderTpConfig`）/
时间止损（`TimeStopConfig`）/ 条件时间止盈（`CondTimeStopConfig`）」。

### 13.6 §13 的验收标准

1. 「买价位置」条在 `high == low` 或空壳 bar 时输出「当日无有效振幅」，**不产生 inf/异常**（有测试）。
2. §12.4 复用 `trade.analysis.build_summary_view` / `build_daily_pnl_view`，**不新写月度聚合**。
3. 反向 AST 断言存在且绿：`trade_main.py` 与 `trade/` 不 import `notes_gen.daily`。
4. 复盘报告落 `data/daily_review/`，**索引里不得出现该路径的 source**（与 RAG §12.6 联验）。
5. §10 的五个类名已配中文。

### 14.2 实施中发现并修掉的一个**单位错**

payload 里的 **`turnover` 是「成交额（元）」，不是百分比**。

- 证据（对着**写方**核，不是猜）：`trade/daily_report.py:68` 存的是 `round(turnover, 2)`，
  而 `turnover` 是 `Σ abs(amount)`；`trade/notifier.py:282` 也按「成交额 {x:,.2f}」打印。
- 后果：第一版按百分比打印，**空成交时显示的 0.0 看不出错**，一旦有成交额就会把
  「12 万元」印成「+0.00%」。
- 处置：改成「当日成交额 X 元」，并加测试断言「成交额 120,000 元」。
- **附带的单位对照表**（同一份 payload 里三种单位混着）：
  `day_pnl_pct` = **百分数**（0.5 表示 +0.5%）；`win_rate` = **比率**（0.5 表示 50%）；
  `turnover` = **金额（元）**。三个都要乘/不乘不同的系数，混一个就是错的。
