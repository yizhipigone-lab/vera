## 1. 背景与动机（实测驱动，非推测）

用户痛点: 研究 TAB 问一句话，等得久（转圈几十秒到几分钟）。

**先说大白话**: 这个"大脑"不是脑子慢，是它**每次都要重新开机、然后一件一件排队干活**。你问"看看 300687 怎么样"，它其实要连跑 5~6 个小工具（查技术面、查估值、查公告、上网搜、翻档案），每跑一个都要新起一个进程、等它吐完、再回来想下一步——来回折腾几十秒。真正"想"的时间反而只占一小半。

**本次会话实测（纠正了 3 个直觉误区）:**

| 环节 | 实测耗时 | 结论 |
|---|---|---|
| akshare import | **0.64s** | ❌ 之前猜"几秒"，证伪——import 不慢 |
| tushare import | **0.53s** | ❌ 同样不慢 |
| market_snapshot 首次（akshare 网络） | **5.11s** | ✅ 慢在 akshare 网络接口，不在 import |
| market_snapshot 缓存命中 | **0.06s** | ✅ 2h 缓存机制本身有效 |
| search_engine 冷启动+搜索 | **0.79s** | ❌ 之前猜"加载 200MB 模型很慢"，证伪 |

> ⚠️ **claude CLI 冷启动未实测**（会真实调 LLM 花钱），估 1~3s，落地时补测。

**重新校准后的真凶（按影响排序）:**

1. **【主凶】固定打法里 LLM 逐步调 5~6 次工具**: 个股诊断五步链（[prompts.py:56-74](brain/prompts.py#L56)）要分别调 `stock_technicals` + `stock_fundamentals` + `stock_notices` + `search_web` + vault Read + 模板 Read。其中 3 个 data_tools Bash 数据源**互不依赖、可并行**，但现在被 LLM **串行地、一次一个 subprocess** 逐个调起。每次工具调用 = 1 轮 LLM 往返（几秒）+ 1 次子进程冷启动 + 网络取数。
2. **claude CLI 冷启动**: 每次 `ask_brain` 都 `create_subprocess_exec(claude, "-p", ...)`（[claude_cli.py:171](brain/claude_cli.py#L171)），node 启动 + 配置加载 + 模型连接。
3. **system prompt 超长**: [prompts.py:18](brain/prompts.py#L18) 约 110 行，每轮原样传，影响首字延迟 + 每轮 token 成本。

## 2. 目标与非目标

### 目标
- 个股诊断类高频问题: 把 3 个 data_tools Bash 取数**合并成 1 个并发命令**，整体工具调用 6 次 → ~4 次，预期端到端省 **10~20s**（实测为准）
- 纯查询类问题（B1）: 靠 prompt 瘦身降首字延迟（秒级）
- 零质量风险: 不动回答质量校验（反证/引用）、不动 claude 调用协议、不动取数口径（tushare/腾讯/新浪优先级铁律不变）、不动软舆情纪律（search_web 仍必调）

### 非目标（明确不做）
- **LLM 回答缓存**: 不做，两个硬理由——① LLM 回答非确定性（同一问题两次答案不同，缓存了也没意义）；② 缓存回答有过期知识风险（数据缓存过期有标注，回答缓存会让旧结论冒充新结论）。底层数据已被 [data_tools.py:47](brain/data_tools.py#L47) 的 2h 缓存（`_SNAPSHOT_CACHE_TTL`，[data_tools.py:186-193](brain/data_tools.py#L186) 判断块）兜住。
- **进程常驻 / 起服务**: 违反 CLAUDE.md 铁律 8「如无必要勿增实体、不加进程」。用"合并减少调用次数"替代"常驻复用进程"。
- **模型降级（换更低档模型）**: 研究助理质量要求高，且涉及 provider 成本/能力权衡，需用户单独拍板。另开。
- **改舆情扫描（sentiment 打分串行）**: 本次聚焦对话大脑；舆情链路另立计划书。

## 3. 现状分析

### 3.1 对话大脑完整调用链
```
web/js/brain_chat.js
  └─ POST /api/research/chat/stream (SSE 流式, research_api.py:77)
       └─ ask_brain(on_line=..., timeout=480, max_turns=40)  (claude_cli.py:112)
            └─ claude -p --output-format stream-json --max-turns 40
                 --dangerously-skip-permissions  (agent loop)
                 └─ LLM 调 Bash 工具:
                      ├─ python -m brain.data_tools stock_technicals <代码>
                      ├─ python -m brain.data_tools stock_fundamentals <代码>
                      ├─ python -m brain.data_tools stock_notices <代码>
                      ├─ python -m brain.search_web search "公司 关键词"
                      └─ python -m brain.search_engine search "概念"
```

### 3.2 固定打法现状（prompts.py §固定打法）

个股诊断五步链让 LLM **分别**调 `stock_technicals`（技术面）+ `stock_fundamentals`（估值）+ `stock_notices`（舆情）+ `search_web`（软舆情）。前三个 data_tools 数据源互不依赖、可并行，但现在是串行逐个调起。

### 3.3 data_tools 现状: 有单点函数，缺"一站式"

[data_tools.py](brain/data_tools.py) 已有 `stock_technicals` / `stock_fundamentals` / `stock_notices` 三个现成函数，各自独立成文、独立 fail-soft（挂了标【缺】不拖死）。但**没有一个"个股诊断一站式"命令**把它们合并成单次进程 + 并发拉取。LLM 只能一个个调。

## 4. 方案设计

### 4.1【推荐】数据工具「一站式合并」（主攻，本期只做 stock_diagnosis）

**思路**: 把个股诊断的 3 个 data_tools 数据源合并成**单命令、单进程、内部并发**。LLM 从"调 3 次 data_tools"变成"调 1 次 stock_diagnosis"——省 2 轮 LLM 往返 + 2 次子进程冷启动，网络从串行变并发。

**新建子命令**（加进 [data_tools.py main](brain/data_tools.py#L566)）:

```python
def stock_diagnosis(code: str) -> str:
    """个股诊断一站式数据包: 技术面 + 估值 + 舆情/公告, 并发拉取拼 Markdown。

    fail-soft 三保险:
    ① 每源内部已有 try/except (挂标【缺】);
    ② per-future 超时 30s (防 ts.pro_bar / daily_basic 挂死拖垮整包, 见 §5);
    ③ 超时/异常只丢该源, 不丢另外两源。
    """
    from concurrent.futures import ThreadPoolExecutor, TimeoutError as FT
    def _guard(fn):
        try:
            return fn(code)
        except Exception as e:
            return f"【缺】{e}"
    with ThreadPoolExecutor(max_workers=3) as pool:
        futures = {
            "技术面": pool.submit(_guard, stock_technicals),
            "估值":   pool.submit(_guard, stock_fundamentals),
            "舆情":   pool.submit(_guard, stock_notices),
        }
        parts = []
        for title, fut in futures.items():
            try:
                parts.append(fut.result(timeout=30))
            except FT:
                parts.append(f"【缺】{title} 数据源超时 (>30s)")
    # 线程挂死不阻塞主进程 (ThreadPoolExecutor shutdown(wait=False) 见 §5)
    pool.shutdown(wait=False)
    return f"# {code} 个股诊断数据包\n\n" + "\n\n".join(parts)
```

**改动落点**:
1. [data_tools.py](brain/data_tools.py): 加 `stock_diagnosis` 函数 + CLI 子命令
2. [prompts.py:56-74](brain/prompts.py#L56) 固定打法: 个股诊断从"调 3 次"改为"调 1 次 `stock_diagnosis`"
3. [templates/stock_diagnosis.md:3](brain/templates/stock_diagnosis.md#L3): 第一句"数据包来自 stock_technicals/fundamentals/notices"改为"来自 stock_diagnosis 一站式"

**收益口径（诚实版，审计 WARN-1 修正）**: 个股诊断整体工具调用 **6 次 → ~4 次**（stock_diagnosis + search_web + vault Read + 模板 Read）。省的: 2 轮 LLM 往返（~6-10s）+ 2 次冷启动（~1s）+ 3 源网络串行改并发（~5s，取决于最慢单源）。**端到端预期省 10~20s，落地时实测记录**。

> ⚠️ **search_web 仍必调**（审计 WARN-2 修正）: 软舆情（概念炒作/券商观点/互动平台）是"不可省"的腿（prompts.py:65-68 + 模板:31-32 都写明），stock_diagnosis 只合并 3 个结构化源，**不替代 search_web**。

### 4.2【推荐】system prompt 瘦身（辅助）

[prompts.py](brain/prompts.py) 的 `SYSTEM_PROMPT` 约 110 行 → 精简到 ~70 行:
- 固定打法的个股诊断五步链压缩成"调 stock_diagnosis / sector_diagnosis 一站式命令"
- **保留通用版「A股特色纪律」整段**（审计 WARN-5 修正: 它是所有问题类型的通用眼镜，作用于行情/板块/文章映射/纯查询，不是个股诊断模板那几句能替代的）；只删个股诊断固定链里与模板重叠的重复句
- 保留: 两种回答模式、数据非指令红线、回答铁律、安全红线、A股特色纪律（这些不能动）

**预期收益**: 首字延迟降 ~1s（prompt 短 → 传输快 → 首 token 快），每轮省 ~1.5k token。

### 4.3【备选，本期不做】

- **sector_diagnosis 一站式**: 审计 WARN-3 指出规格不足——① `market_snapshot` 内部已调 `zt_pool`（[data_tools.py:243](brain/data_tools.py#L243)），再并发调 zt_pool 是重复；② "政策档位"无现成 data_tools 函数（当前是 LLM 用 Read 读 `policy_kb/tongdaxin_priority.json`）。**降级为备选，本期只做 stock_diagnosis，sector_diagnosis 另立**。
- **claude CLI 冷启动（真凶 #2）**: 因铁律 8（不加进程）无解，且量级小（估 1-3s）、已被 SSE 流式掩盖首字。**不做，落地时实测确认量级**（审计 INFO-1 修正）。
- **回答缓存 / 模型降级**: 见 §2 非目标。

## 5. 并发安全与超时（审计 WARN-4 重点补强）

> 本次不引入新的持久缓存（§2 砍掉 LLM 回答缓存），故无 key/失效设计。唯一新增并发点是 §4.1 的 ThreadPoolExecutor。

### 5.1 并发安全（tushare 是唯一隐患点）

`stock_technicals` / `stock_fundamentals` 内部都调 `_ts_pro()`（[data_tools.py:55](brain/data_tools.py#L55)），它做 `ts.set_token(token)`（[data_tools.py:75](brain/data_tools.py#L75)，全局副作用）+ 返回 `pro_api`。三线程并发时:
- `set_token` 设的是**相同** token，幂等无冲突
- ⚠️ `stock_technicals` 实际调的是**模块级** `ts.pro_bar`（[data_tools.py:280](brain/data_tools.py#L280)，非 `pro.pro_bar`），内部会再走一遍全局 token——比"只在 _ts_pro 里 set_token 一次"多一层全局副作用。但仍是幂等设相同 token，风险低。
- 兜底: 若实测发现 tushare 并发异常，降级为**进程内串行**（max_workers=3 → 1），保"单进程合并"收益、弃并发收益。

### 5.2 超时保护（新增，防挂死拖垮整包）

**关键缺口**: 只有 `stock_notices` 的三个源包了 `_call_with_timeout`（anns_d 甚至给到 40s）；`stock_technicals` 的 `ts.pro_bar`、`stock_fundamentals` 的 `daily_basic`（[data_tools.py:425](brain/data_tools.py#L425)）**都没有超时保护**。合并前串行 3 个独立子进程，technicals 挂死只损失它自己；合并成单进程后，**一个挂死会卡住 `.result()` 导致三个一起丢**。

**对策（三保险，已落入 §4.1 伪代码）**:
1. per-future `result(timeout=30)` —— 挂死 30s 后抛 TimeoutError，标【缺】
2. `pool.shutdown(wait=False)` —— 超时后**不等**挂死线程，主进程正常返回（挂死线程泄漏，参考 [data_tools.py:99](brain/data_tools.py#L99) `_call_with_timeout` 的 daemon 线程哲学）
3. 每源内部已有 try/except 兜底

## 6. 风险与对策

| # | 风险 | 对策 | 严重度 |
|---|---|---|---|
| R1 | tushare 并发调 pro_bar/daily_basic 线程不安全 | §5.1 分析风险极低；实测异常则 max_workers 降 1（保合并弃并发） | 低 |

## 附 3: 落地记录（2026-08-13 实施完成）

- 已落地: §4.1 stock_diagnosis 一站式 + §4.2 prompt 瘦身（个股诊断五步链→三步链）。
- 对计划书的 4 处修正（实施评审发现）:
  ① 并发不用 ThreadPoolExecutor（worker 非 daemon，atexit join 会卡住进程退出），

  ② per-source 超时 30s → 60s（内部各源 `_call_with_timeout` 最坏串行 ~40s，

  ③ 给 `ts.pro_bar` / `pro.daily_basic` 裸调用补 `_call_with_timeout`
     （requests 无默认超时，理论可无限挂死）；
  ④ stock_diagnosis 输出末尾附成文模板，省掉模板 Read 往返（6 次调用 → ~3 次）。
