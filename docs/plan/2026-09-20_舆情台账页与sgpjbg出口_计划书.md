## 二、批次 0：调度器看护 —— **⚠️ 本节已于 2026-09-20 凌晨被推翻重做**

### 2.0 先说结论：原方案（Windows 计划任务）已废弃

**原方案**：注册 `VERA-Scheduler-Guard` 计划任务（登录时 + 每 15 分钟），
配套 `tools/scheduler_guard.py`（幂等拉起）+ `tools/register_scheduler_guard.ps1`。
**当时的实施与验证都通过**（强杀 → 14 分钟内拉起；幂等；`LastTaskResult=0`）。

**用户当场质疑**：「还要用 WINDOWS 计划任务，岂非换了台机器就跑不起来了调度？」

**质疑成立，而且比表面更严重 —— 三个问题**：

1. **重新制造了本轮要修的 bug**。计划任务是**机器本地状态**，不在仓库里。
   换机器/重装后 `start_vera.bat` 照跑，但看护**静默消失** —— 无报错、无提示、
   没人知道。这正是"静默停机"换个层级重演（又一次「看得见 ≠ 生效」）。

2. **忽略了项目已有的决策**。`research/2026-08-24_VERA全面调研_优化方向报告.md` §5
   明确给过方案：**"先做最便宜的 —— bat 里 `:loop` + `goto loop`；进阶方案是写一个
   极简 watchdog 进程"**。计划任务**两者都不是**，是凭空发明的第三种。

3. **会和 `stop_vera.bat` 打架（最严重）**。`stop_vera.bat` 明确要停
   `VERA-Scheduler`，而 guard **15 分钟后又把它拉起来** —— **停止脚本失效**。
   `stop` 必须意味着 stop。

**另有一条事实削弱了原方案的卖点**：实测启动项里 **QMT(`XtMiniQmt`) 与 VERA 三进程
都不在**，关机后要手工起。所以"登录时自动拉起"给的**不是**自愈的 VERA，
而是"调度器在跑、交易与网页都没起"的半截状态 —— **重启自愈在本机价值接近于零**。

### 2.1 重新推导：防的到底是什么

关键事实：**死因无法区分**。证据只到"被外部强制终止"（无崩溃事件、无优雅退出日志、
无重启）。而两种可能死因的**正确反应是相反的**：

| 若是 | 正确反应 |
|---|---|
| 用户跑了 `stop_vera.bat` | **绝不能自愈**，该做的是"停机可见" |
| 窗口被误关 / 被误杀 | 自愈才是对的 |

原方案直接赌了第二种，且赌错了就会与 `stop_vera.bat` 对抗。

→ **采用用户既有报告里的原则**（同报告 §4）：

> 失败记录落盘并告警，**不自动重试但「可见」**

**可见优先于自愈**：不赌死因，两种情况下都不会做错事，且不再有"静默"。

### 2.2 落地实现（最终）

**① 心跳（`scheduler/vera_scheduler.py`）**

`VeraScheduler` 新增可选 `heartbeat_path`；`_loop` 每轮询周期覆写
`data/scheduler_heartbeat.json`（`{ts, iso, pid, jobs, tick_s}`），
**节流 30s**（默认 tick=1s，不节流是一天 8.6 万次写盘），tmp + replace 原子替换。
**不传参 = 不写**（旧行为与既有测试零影响）。

> **为什么不拿 `scheduler_state.json` 的 mtime 当心跳**：那个只在 job 真触发时才写，
> daily job 一天可能只触发一两次 —— 拿它当心跳会把"正常空闲"误报成"已停机"。

**② 存活判读（新增 `scheduler/health.py`，deep module）**

三态，**少任何一态都会误报**：

| 状态 | 判据 | 含义 |
|---|---|---|
| `running` | 心跳新鲜（≤ `STALE_AFTER_S`=300s） | 正常 |
| `stopped` | 存在人工停止标记 | 你主动停的，**不报警** |
| `down` | 无标记 且 心跳过期/缺失 | **这才是要你看一眼的** |

**③ 停止标记（跨语言契约）**

- `stop_vera.bat` 写 `data/.vera_stopped`（GBK + CRLF，用字节级 GBK 读写改的）
- `start_vera.bat` 删它
- 路径在 `.bat`(GBK) 与 `health.STOP_MARKER_PATH` 两处 —— **有测试直接读 .bat 源文件比对**，
  因为写错一个的症状是"静默不生效"（永远显示 running）

**④ 可见（`server.py` + `web/index.html` + `web/js/vera-ui.js`）**

`/api/status` 增 additive 字段 `scheduler`（旧前端不读不受影响）；首页状态栏常驻
`#schedStatus`，三态上色（绿/灰/**红加粗**），每 60s 刷新。

> **为什么单开一个轮询**：原有的 `/api/status` 轮询只在**回测运行时**存在，
> 空闲时页面什么都不显示 —— 而停机恰恰发生在空闲时。

**⑤ 移除**：计划任务已卸载；`tools/scheduler_guard.py` 与
`tools/register_scheduler_guard.ps1` 失去消费者，**已删除**（守铁律 8）。

### 4.2 存储层：给 `NewsDedup` 补一个区间查询

```python
def alerts_between(self, start_ts: float, end_ts: float, *,
                   rule: str | None = None, code: str | None = None,
                   limit: int = 500) -> list[dict]:
    """区间内异动台账（台账页用）。返 [{ts, date, code, name, polarity,
    strength, rule, evidence}]，按 ts 倒序。fail-soft 返 []。"""
```

> **铁律 8 说明**：`news_dedup.py` 是**持久化契约**（store），按 2026-09-19 架构审查
> 批次 5.3 的豁免口径（`gateway`/`store`/`config`/`book` 同属"契约面即接口面"），
> 在 store 内按表域加查询方法不构成"转发层"。**但新代码不得再增公开方法**这一条仍适用，

### 4.3 路由层：`sentiment_api.py`（薄层）

按 `market_position_api.py` 的既有范式（`APIRouter` + 在 `server.py` 注册）：

| 端点 | 用途 |
|---|---|
| `GET /api/sentiment/alerts?start=&end=&rule=&code=&limit=` | 台账列表（区间 + 筛选） |
| `GET /api/sentiment/daily?date=` | 某日汇总（bullish/bearish/total + 当日列表） |
| `GET /api/sentiment/summary?days=30` | 近 N 天分布（按日计数 / 按规则计数 / 按标的 Top） |

### 4.4 前端：`web/js/sentiment.js` + 页签

## 九、实施中新发现（批次 2 验收时顺带查出）—— **形状已修（§9.5）；阈值待定（§9.6）；尚未生效（§9.7）**

> 2026-09-20 凌晨，用新建的舆情台账页查真实数据时发现。
> **这不是本计划的一部分**，是台账页第一次把历史摊开看才暴露出来的。

### 9.1 现象

全量历史（2026-08-17 ~ 09-18）`alert_log` 共 **179 条异动，100% 是 `index_move`**：

| 规则 | 触发次数 |
|---|---|
| `index_move` 大盘指数异动 | **179** |
| `stock_sentiment` 个股情绪突变 | **0** |
| `sector_cluster` 板块新闻密集 | **0** |
| `volume_anomaly` 量能异常 | 0（v1 默认关，预期） |

即：**规则 1/2 自系统上线以来从未触发过一次**。舆情系统实际退化成了"指数涨跌播报器"。

### 9.2 根因（证据链完整）

**形状不匹配**：`judge_batch` 返回**嵌套**结构，消费方按**扁平**读。

```
brain/sentiment_judge.py::judge_batch   →  [{"id":…, "sentiment":{polarity,strength,…}}]
brain/sentiment_pipeline.py:145         →  pol = r.get("polarity")        ← 读顶层, 恒为 None
brain/alert_rules.py::rule_stock_sentiment →  news.get("polarity", 0.0)   ← 读顶层, 恒为 0.0
```

`judge_batch` 的 docstring 明写返回 `[{"id":…, "sentiment":{…}}]` —— 契约在 judge 侧，
**是消费方没拆包**。

**旁证（独立于代码）**：

- `news_seen` 表 **360 条全部 `polarity = NULL`**（`mark_news_seen` 确实被调用过，
  所以不是"没落库"，是落了个 None）；
- 规则 1 判据 `abs(pol) < pol_min` → `abs(0.0) < 0.6` → **必然 continue**；
- 规则 2 判据 `avg_pol < pol_min` → `0.0 < 0.4` → **必然 continue**。

### 9.3 为什么测试没抓到（**教训**）

`tests/brain/test_sentiment_acceptance.py::test_full_tick_fires_all_enabled_rules`
把 `judge_batch` **mock 成了扁平字典**：

```python
monkeypatch.setattr(sp, "judge_batch", lambda items: [
    {"polarity": 0.8, "strength": 2, ...},   # ← 真实 judge_batch 不长这样
])
```

→ 测试锁的是**假设**，不是**契约**；端到端那条腿被 mock 短路，真实形状差异永远走不到。
测试绿灯，生产静默失效 5 周。

### 9.4 附带发现：新闻源那条腿也是瘸的

- `search_web` 三个 backend **全失效**（baidu 无摘要 / bing 超时 / ddg 无结果），
  日志里 **46 次「全部 backend 均无可用结果」**、698 条 backend 失败告警；
- `_fetch_watch_news` 的源1（财新要闻，akshare）从未失败，是唯一在供货的；
- 153 次 tick 里 **`new = 0` 占 130 次（85%）** —— 去重后大多没有新新闻。

即使修好 §9.2，源2 不恢复仍会压制规则 1/2 的样本量。

### 9.5 已实施（2026-09-20，用户拍板方案 A）

**方案 A**：先写失败测试 → 拆包 → 干跑看真实触发量 → 再定阈值 → 才放开推送。

**① 先写复现用的失败测试（TDD 红）** —— 新增
`tests/brain/test_sentiment_shape_contract.py`（7 条）。

关键纪律（TDD 技能）：**"用真实路径，不要把 mock 断言当测试 —— mock 只能用来隔离
外部 IO"**。所以本文件**刻意不 patch `judge_batch`**，只桩掉最内层的 LLM 调用
（`judge_sentiment`），让**真实的包装函数**参与 —— 形状一变这里必红。

实测红灯，失败原因即诊断的那个：
```
{'scanned': 1, 'new': 1, 'scored': 1, 'alerts_fired': 0}
```
分数"算进去了"、规则一条没触发；另有一条 `scored == 0` 断言失败（证明顶层
`"error" not in r` 同样错一层，失败项被当成打分成功）。

**② 绿：最小实现** —— `brain/sentiment_pipeline.py` 拆包 + 补 `text`/`ts`：

```python
sent = r.get("sentiment") if isinstance(r, dict) else None
ok   = isinstance(sent, dict) and "error" not in sent
...
if ok:
    sent.setdefault("text", b.get("text", ""))
    sent.setdefault("ts", b.get("ts") or now)   # 缺 ts → Alert 带 epoch 0
    scored.append(sent)
```

**③ 同一批修掉 4 处说谎的 mock**（否则修了也没人守）：
`test_sentiment_acceptance.py` 1 处、`test_sentiment_pipeline.py` 3 处，全部从手写
扁平改为真实嵌套形状。**改之前先跑、看到它们变红** —— 证明它们此前锁的是形状假设。

**④ 全量 `pytest tests/` 通过**（回归无破坏）。

**未做（明确记录）**：`mark_news_seen` 仍不传 `code` —— 一条新闻的 `hit_pool` 可能含
多个标的，而 `news_seen.code` 是单值列，本就放不下；且**无任何消费者**
（舆情页读的是 `alert_log`）。故不动。

### 9.6 干跑读数（`tools/sentiment_dry_run.py`）

新增 `tools/sentiment_dry_run.py`：拉真实新闻 → 真实 LLM 打分 → 过真实规则 →
**只统计不推送**。三条零副作用保证：去重库用**临时库**标记（生产库只读，仅用来数
"真正新的有几条"）—— 否则干跑会把新闻标记成"已见"，真实 tick 就再也看不到它们；
notifier 用计数桩；不写任何持久状态。

**读数（2026-09-20 02:12，抓 15 条 / 打分 10 条）**：

```
抓到 15 条，其中生产去重库没见过的 8 条；打分成功 10 条
逐条分数：
  |p|=0.50 s=1  hit=[玻璃]
  |p|=0.30 s=1  hit=[油气开采,天然气,石油化工,油服]
  |p|=0.20 s=1  hit=[巨灾债券,881319.SH,保险]
  |p|=0.20 s=0  hit=[出海]
  |p|=0.00 s=0  hit=[人工智能,大模型]
  …其余 5 条全 0

阈值敏感性（规则1 需 |p|≥阈值 且 s≥强度 且 hit_pool 非空）：
  |p|≥0.6 → s≥2: 0 条   s≥1: 0 条
  |p|≥0.5 → s≥2: 0 条   s≥1: 1 条
  |p|≥0.4 → s≥2: 0 条   s≥1: 1 条
  |p|≥0.3 → s≥2: 0 条   s≥1: 2 条
```

**两条结论**：

1. **形状 bug 是真的，但光修形状不够** —— 修好后规则 1/2 在本采样上**仍是 0 条**。
2. **`strength ≥ 2` 在 10 条里一次都没出现**（最高 s=1），`|p|` 最高 0.50 ——
   当前阈值 `(0.6, 2)` 在这批真实新闻上**两个条件同时不可达**。
   2026-08-13 拍这个"中等档"时，手上**没有** LLM 实际输出分布的数据。

**但**这是**凌晨 02:12 的单次采样**，新闻强度低，**不能代表盘中**。
故**本次不动阈值** —— 用该工具盘中多次采样后再定。

### 9.7 上线状态（**重要**）

**必须重启调度器**新代码才会跑。按方案 A 第 5 条「确认后再放开推送」，
**重启这一步待用户确认** —— 重启即意味着两条规则在生产上首次真正开始工作。
