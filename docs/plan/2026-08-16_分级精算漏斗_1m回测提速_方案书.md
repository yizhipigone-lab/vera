# 2026-08-16 分级精算漏斗（1m 回测提速）方案书

> 成文日期 2026-08-16 · 回测研究侧 · 复用现有 `research/auto_strategy_optimizer.py` 与 `BacktestEngine`

## 一、目标（大白话）

批量选策略时，**不要对所有候选都用 1m 精算**，而是三级漏斗：

**日线（1d）粗筛 → 5m 复筛 → 1m 只给决赛圈定稿。**

一句话：1m 的"精确"只值钱在"最后几个要拿去实盘的策略"上；海选阶段 1d/5m
的"大概排序"足够把明显差的刷掉，省下 90%+ 的无谓精算时间。

## 二、核心原理：粗筛靠"排序"，不靠"精确"

5m 相对 1m 确实"不准"，但它的误差只影响**最终收益算到小数点后两位**；
而粗筛要回答的是另一个问题——**这堆候选里谁一眼就是废物**。回答这个问题，
5m 绰绰有余。

**为什么本项目安全**：我们的策略是**日线选股 → 尾盘买 → 持有几天到几周 →
止盈止损**。入场信号是日线级的，1m 只是把"止损到底盘中几点几分触发、卖在
哪个价"算得更细。这种出场时点的 ±0.1~0.2% 误差，在单笔几个点到几十个点
的收益面前是毛毛雨 → **5m 排出的名次和 1m 基本一致**。

> 失效边界（诚实）：只有 1m 级剥头皮/高频策略（利润藏在几分钟微观波动里）
> 才会被 5m 筛错。当前无此类策略；将来上高频再改回"全程 1m"。

## 三、三级漏斗流程

关键约束：**信号（日线选股）全程不变**，只有回测引擎的 `period` 在变——
漏斗只细化"出场时点"，不动入场逻辑（避免再踩"审错路径"的坑）。

```
第 0 级 (1d)  网格全量跑一遍        → results_1d.csv    （现状已做）
第 1 级 (5m)  取 top N 复跑          → results_5m.csv
第 2 级 (1m)  取 5m 结果 top K 复跑  → results_1m.csv     （定稿）
```

| 级别 | period | 跑多少候选 | 用途 |
|---|---|---|---|
| 0 | `1d` | 全量网格 | 粗筛，刷掉明显差的 |
| 1 | `5m` | top N（默认 10） | 复筛，精化出场时点 |
| 2 | `1m` | top K（默认 3） | 定稿，实盘决策的数字 |

N、K 做成 CLI 参数（`--refine-top 10 --final-top 3`），默认 10/3，可调。

## 四、排名分与筛选门槛

排名用**夏普（Sharpe）降序**（项目铁律"评价同时给夏普/Calmar/回撤/胜率"，
海选以夏普为第一排序键，最省事且稳定）；同分用 `ann/dd`（Calmar）拆解。

**进下一级前先过滤**，防把噪声候选送进更贵的精算：

| 门槛 | 条件 | 理由 |
|---|---|---|
| 达标 | `ok == True`（`judge` 判定） | 沿用现有"达标"口径 |
| 样本量 | `trades >= 30` | 少数交易的高夏普是过拟合，不配进决赛 |
| 正夏普 | `sharpe > 0` | 夏普为负的直接淘汰 |

## 五、代码改动（文件清单）

全部落在 `research/auto_strategy_optimizer.py` 内，**不新增独立脚本**
（遵守"如无必要勿增实体"铁律）。

| 位置 | 改动 |
|---|---|
| `make_bt_cfg(...)` | 加 `period` 参数（默认 `PERIOD`），透传进 `bt_cfg["period"]` |
| `run_backtest(...)` | 已吃 `bt_cfg["period"]`，确认数据拉取按 `period` 走（5m/1m 引擎已支持） |
| `evaluate(...)` | 加 `period` 透传（信号仍用日线 `close/high/low/vol` 算，只回测期变） |
| 新增 `refine_pass(...)` | 读上一级 CSV → 过滤（§四）→ 夏普排序 → 取 top N/K → 用对应 period 复跑 → 写 `results_5m.csv` / `results_1m.csv` |
| `main()` / CLI | 加 `--refine` 开关（默认开）与 `--refine-top` / `--final-top` |

**数据成本提示**：1m 取数本身慢（TDX 单次 ~24000 根、`_fetch_and_store` 按
≤80 交易日分段）。所以 top K 必须小（默认 3），否则漏斗白搭。

## 六、已知边界与风险

- **单次回测不适用**：漏斗只对"批量候选"提速。单个 1m 回测要快，靠的是
  药2（float32）/药3（numba），本方案不覆盖。
- **5m→1m 名次相关性**：对日线级策略成立（§二），上高频策略前需重验。
- **1m 数据可得性**：1m 深度覆盖的区间/池子有限（引擎对 1m 有区间硬限 +
  告警），决赛圈跑 1m 前先确认候选池在该区间有 1m 数据，缺则回退 5m 定稿。
- **口径一致性**：三级都用同一份 `make_stop` 止损止盈参数，只换 period，
  保证名次差异**只来自出场时点精度**，不掺其他变量。

## 七、验收标准

1. **冒烟**：拿现有 `results_1d.csv` 跑 `refine_pass`，确认 `results_5m.csv`
   落盘、top 排序正确、过滤门槛生效（trades<30 的被剔除）。
2. **parity**：同一候选在 1d / 5m / 1m 的**入场信号与笔数一致**（只出场价
   与出场时点不同），证明漏斗没改入场口径。
3. **端到端耗时**：网格 N 个候选，记录 `1d 全量 + 5m×10 + 1m×3` 总耗时，
   与"全量 1m"估算对比，确认降一个数量级。

## 八、分阶段实施

1. `make_bt_cfg` / `evaluate` 加 `period` 透传（地基，零行为变化）
2. 写 `refine_pass` 纯函数（读 CSV → 过滤排序 → 复跑 → 落盘）
3. CLI 开关 + 端到端串起来
4. 冒烟 + parity + 耗时对照，跑通一个真实网格
