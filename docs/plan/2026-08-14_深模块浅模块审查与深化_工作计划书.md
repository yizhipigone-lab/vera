## 1. 背景与动机

用户要求从「深模块 / 浅模块」角度审视系统。结论先行：**骨架已经深**（真接缝、快路径、三层缓存、调度器、进度上报都是教科书级深模块），**浅处集中在回测入口一处历史包袱 + 两处接口重复**。

本计划书把「深化」落成可执行、可验证的工作项。本期只做风险最低、收益最清晰的一项（notifier 消重），其余记录触发条件、不抢跑。

## 2. 目标与非目标

### 目标（本期）
- **推荐① notifier 消重**：`trade/notifier.py` 与 `research/sentiment_notifier.py` 两份 ~150 行的重复实现，抽成一份共享轮子 + 两个薄适配器。

### 非目标（本期不做，记录触发条件）
- **推荐②** stop_config 无类型 dict → 带类型 dataclass（中风险，40 调用方，触发条件：新增止损字段时）。
- **推荐③** `run_cached` 18 参数收拢（高风险，触发条件：新增能力数据、接口腐化继续加重时）。
- **推荐④** data_tools 三子命令收口（需先确认无「只看技术面」类分头调用方）。

## 4. 方案设计

### 4.1 推荐①（本期）：notifier 消重

**现状重复点（已逐行比对 trade/notifier.py 与 research/sentiment_notifier.py 确认）**：

`_run`（[trade/notifier.py:114](trade/notifier.py#L114)、[research/sentiment_notifier.py:117](research/sentiment_notifier.py#L117)）、`_post`（[trade/notifier.py:141](trade/notifier.py#L141)、[research/sentiment_notifier.py:145](research/sentiment_notifier.py#L145)）、`_warn_no_url_once`、`start`、`stop` 五处**逐字级重复**（仅日志文案「交易不受影响」vs「舆情」、线程名不同）。`_handle` 分派不同（fill/daily vs alert/summary），**不该共享**。

**方案（拆两档，本档只做 ①a）**：

- **①a（必做，本档）**：抽 `utils/feishu_webhook.py::post_webhook(webhook, body, context="") -> bool`。只抽 `_post` 这一段——它编码了 2026-08-07「HTTP 200 ≠ 真送达、读业务 code」的坑 + fail-soft 超时，是重复里最危险、最值得「修一次管两处」的叶子。`context` 参数化日志前缀，保留「交易不受影响」vs「舆情」的语义。
- **①b（备选，本档不做）**：再抽 `QueuedWebhookNotifier` 基类（`__init__`/`start`/`stop`/`_run`/`_warn_no_url_once` 模板方法，子类实现 `_handle`）。约 68 行重复 → 一处。**判断**：worker 循环只有 ~15 行且极稳定，抽基类会加一层「子类→基类→_handle→_post」的间接层，收益 vs 间接层成本不成比例。等第三处 notifier 出现（真接缝变三适配器）再抽。

**隔离铁律不破**：`utils/` 是中立层，`post_webhook` 只 import stdlib，不 import trade/ 或 research/。两个 notifier 仍不互相 import；共享的是「发 webhook」这个纯基础设施，不含业务语义。

### 4.2 备选②③④（本期不做，仅记录触发条件）

- ② stop_config → dataclass：`Dict[str, Any]` → 带类型 dataclass + from_dict/to_dict 兼容层。触发条件 = 新增止损字段、schema 继续膨胀。
- ③ run_cached 收拢：18 参数 → 「能力上下文」dataclass。触发条件 = 新增能力数据、或调用方继续传错位（[backtest/engine.py:710](backtest/engine.py#L710) 的 unpack 兜底已复核实属）。
- ④ data_tools 收口：先 grep 确认无「只看技术面」分头调用方，再删 CLI 子命令。
