## 3. 逐项方案

### 3.1 item 1 —— raw 日志不再记 tick

**现状与位置**
- `trade_main.py:256-266` `_wire(sink, event_type)` 是网关回调的唯一接线器，**先 `append_raw` 再 `sink.put`**。
- 调用点：`trade_main.py:317` `tick_wire = _wire(self._engine, EVENT_TICK)`；`:321` `on_quote=lambda code, q: tick_wire({"code": code, **q})`。

**改法（最小）**
- `_wire` 增 keyword-only 参数 `raw: bool = True`；`raw=False` 时跳过 `append_raw`。
- tick 接线改为 `_wire(self._engine, EVENT_TICK, raw=False)`。
- **硬要求**：`sink.put(...)` 一行不动 —— tick 仍必须进引擎（monitor 心跳、止损判定全靠它），本次只砍"落 JSONL"这一段。

**为什么安全（已核实，非推测）**
- 生产侧**无任何消费者**读 raw 里的 tick：`tools/gapfill_daily_asset.py:114` 用的是自己的 `gapfill_raw.jsonl`；`trade/raw_log.py` 只写不读（除轮转按 `ts` 分月）。
- `tests/trade/test_e2e_trade.py:128-130` 只断言 `trade_fill` 与 `order_update` **存在**，不要求 tick。
- 历史文件不删（留痕），只是**新增不再记**；按月轮转逻辑完全不用改。

**先失败的测试**：`tests/trade/test_raw_log_no_tick.py`
- 推一个 tick + 一笔成交 → `flush_raw()` → 断言 raw 文件里**没有** `kind=="tick"`、**有** `kind=="trade_fill"`；
- 并断言 tick **仍然到达引擎**（monitor 侧 tick 计数 / `last` 前进），防"顺手把 tick 也掐了"。

**预计收益**：约 700MB/月 → 约 100KB/月；启动期 700MB 级内存扫描与"底账不能删"的保留难题一并消失。

**生效**：重启 `trade_main`。

### 3.2 item 4 —— 交易进程看门狗（复用 scheduler，不新增进程）

**4a 看门狗 job**
- 用**现成** API：`scheduler/vera_scheduler.py:243` `add_interval(name, func, interval_min, trading_hours=...)` —— 自带"仅交易日 + 仅交易时段"，且首次启动立即触发（`:90-107`）。

- 判定逻辑抽成**纯函数** `evaluate_watchdog(...)` 放进 `scheduler/health.py`（该模块已声明"不 import trade、不碰 data/trade"，符合业务铁律 1；也便于单测）。

  - 连续 **2** 次失败才告警（首次失败只记日志）；

### 3.5 item 9 —— 部署快照 + tag

**新增** `tools/deploy_snapshot.py`（`tools/` 按 TDD 技能不强制测试，但**结论必须可复现**）。回答的问题是：**出事时，"当时跑的是哪一版代码"**。

产出目录 `output/deploy_snapshots/<YYYYmmdd-HHMMSS>/`（`output/` 已被 `.gitignore` 整体忽略，不污染仓库）：

| 文件 | 内容 |
|---|---|
| `changes.patch` | `git diff HEAD` —— 已跟踪文件的全部未提交改动，可 `git apply` |
| `new_files/` | 未跟踪文件（`git status --porcelain` 的 `??` 项）按相对路径原样拷贝。**注意 git 对全未跟踪目录只报 `dir/`**（2026-09-20 逐行审查 P2-3）：拷贝前须递归展开目录；单文件 >10MB 不拷内容、只在 manifest 记路径+sha256（防把数据/图片拷爆） |

2. `changes.patch` 非空且含 `diff --git` 头，行数与 `git diff --stat` 汇总一致；
3. `new_files/` 文件数 == `git status --porcelain` 里 `??` 的条数；

### 3.6 item 6 —— 复核后被推翻，**不做**

原建议：把 `_on_trade` 里 `book.apply_trade`（`trade_main.py:760`）与 `store.save_trade`（`:787`）的**顺序倒过来**，理由是"先改内存后落库 → 落库失败后 `reconciler` 的 `known` 判重让它永不自愈"。

**复核结论：该理由不成立，且倒过来会开一个更差的洞。**

1. **A3 补写分支就是为此而建**（`trade/reconciler.py:255-257`、`:320-329`）：
   - `known = self._store.load_today_trade_ids(today)`（`:259`）**只装 DB 里已有的 traded_id**；
   - 因此"book 有账、trades 表缺行"时 `tid not in known` → 走到 `apply_trade` → 返回 `False`（book 幂等命中）→ **主动补写 trades 行闭环**；
   - 代码注释已写明这正是"首次 save_trade 失败（WAL busy 重试仍败）"的遗留态，且说明**为什么只补 trades 行**（`update_order_filled` 是累加语义、不可重放；飞书通知不重复打扰）。
   - 该分支由 2026-08-01 计划书批次1 引入，`sync_reports` 在每个对账时点（09:35 / 11:30 / 14:55 / 15:05）与 EOD 都会跑 → **暴露窗口是有界的、且会自愈**。

2. **倒过来会制造一个不自愈的洞**：DB 先写成功后若在 `apply_trade` 前崩溃/失败 → DB 有行、book 没有。而此后 `sync_reports` 的 `known` 过滤会把该 `tid` 直接 `continue`（`:265-266`）→ **不会补回 book**；内存账本会整场少一笔，直接影响卖出可用量、止损判定与资金口径，**要等重启由 QMT 持仓重建才恢复**。这是"系统性地错一整天"，比"几分钟内自愈的行缺失"更差。

3. 现有顺序还有一处更细的考量：`book.apply_trade` 是**廉价的幂等闸**，放在前面可以避免重复回报去碰 DB 唯一约束（现状下重复回报根本不会走到 `save_trade`）。

**因此：保持现状，不改。** 本条从本次范围移除。

**留给后续观察（不在本次范围）**：A3 的自愈依赖"进程活到下一个对账时点"。若在窗口内崩溃，重启后 `apply_trade` 会在 QMT 重建的持仓上再记一次（代码注释 `:324-325` 自己写了"重启后会成双扣洞"）。真要加固，方向是**启动时先跑一次 `sync_reports` 再接受任何交易动作**，而不是倒置落库顺序。此事另立计划。
