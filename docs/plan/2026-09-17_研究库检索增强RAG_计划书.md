## 3. 关键设计：`source` 路径约定必须统一（本计划最大的技术风险）

现状有一处会造成**同一文件被索引两遍**的隐患：

- `build_index` 第 325 行：`source = str(md_file.relative_to(VAULT_ROOT).as_posix())`
  → 产出形如 `company/company_002390.md`（**vault 相对**）
- `update_file` 第 342 行：
  ```python
  source = str(filepath.relative_to(VAULT_ROOT).as_posix()) \
           if filepath.is_absolute() and VAULT_ROOT in filepath.parents \
           else filepath.as_posix()
  ```
  → 文件**不在** `vera_obs_vault/` 下时，`source` 退化成**绝对路径**

加了 `research/`、`docs/` 两个新根之后，这个分叉会立刻爆炸：
全量构建产出 `research/xxx.md`，而归档增量更新产出 `E:/1target/VERA/research/xxx.md`，
两个 key 指向同一个文件 → 索引里出现重复块，检索结果里同一篇文章挤占多个 top-k 名额。

**决策：`source` 统一为「项目根相对 posix 路径」**（如 `vera_obs_vault/company/company_002390.md`、
`research/2026-09-16_ETF轮动基线诊断与改良迭代_研究报告.md`）。

这带来三个必须一起做的连带动作：

1. **全量重建索引**（`build --force`）。旧索引的 `company/xxx.md` 形态与新形态不兼容。
2. **迁移评测集**。`brain/search_evalset.json` 现有 62 行全部形如
   `"expect_path": "company/company_002390.md"`，必须整体加上 `vera_obs_vault/` 前缀，
   否则 `eval_search` 的命中判定（第 410 行精确等值比较）会**全部判失败**。
3. **顺带修一个老毛病（净改善）**：现在 `_cmd_search` 打印的 `path` 是
   `company/company_002390.md`——**这不是一个从项目根可读的路径**，大脑拿到后要自己猜
   前面还得补 `vera_obs_vault/`。统一成项目根相对路径后，大脑可以直接把这个路径丢给
   `Read`。这一条属于本计划的附带修复，要写进 CHANGELOG。

## 4. 要改什么（逐条）

### 4.1 索引范围改成配置驱动

新增 `config/brain_index.json`（`.gitignore` 已忽略 `*.json`，天然不入库）或直接在
`brain/search_engine.py` 里定义一个可被环境变量覆盖的常量。内容形如：

```json
{
  "roots": ["vera_obs_vault", "research", "docs"],
  "exclude_dirs": [".git", "__pycache__", "node_modules", "data", "output",
                   "logs", ".agent-teams", "vera_obs_vault/对话沉淀/_tmp"],
  "min_chars": 50
}
```

选择顺序：**先读 `config/brain_index.json`，读不到回落内置默认（= 现有 vault 两目录，
零行为变化）**。这样"没配置 = 老行为"，符合项目对默认值的纪律。

### 4.2 遍历改递归

`d.glob("*.md")` → `d.rglob("*.md")`，并在遍历时按 `exclude_dirs` 剪枝
（`docs/` 是嵌套的：`docs/audit/`、`docs/plan/` 都在子目录里，不递归等于没加）。

### 4.3 `source` 统一（见 §3）

`build_index` 与 `update_file` 共用同一个 `_to_source(path) -> str` 私有函数，
按项目根算相对路径。**两处必须引同一个函数**——这正是项目反复踩的"同一条规则
手写 N 份必然漂移"（买卖口径×2、行情陈旧判定×3、AI 设置三档）。测试里加一条：
同一个文件经 `build_index` 与 `update_file` 得到的 `source` 必须相等。

### 4.4 提示词更新

`brain/prompts.py` 第 28~31 行现在写的是"语义搜索 vault（概念类查找）"。改成分辨率更高的说明：

- 资料库 = vault 公司档案 + `research/` 研究报告 + `docs/` 审计与计划与方法论；
- 明确"问'我们以前研究过什么/某结论怎么来的/某个参数为什么这么定'时，**先搜资料库再答**"；
- 保留"引用具体文件路径"的既有铁律（第 132 行）。

注意：`SLIM_SYSTEM_PROMPT`（快路径瘦身版，第 159~194 行）**不含**模式 A/B 与固定打法段，
快路径本来就不调工具，故**不改**。`tests/test_brain_prompts.py` 第 11~13 行断言
`SYSTEM_PROMPT` 含 `python -m brain.search_engine search` 字符串——改提示词时**必须保留
这个字符串原样**，否则测试红。

### 4.5 评测闭环：先测基线，再改，再测

这是本计划唯一能量化"有没有变好"的动作，不能省：

1. **改动前先跑基线**：把新加的研究/文档类问题写进评测集，此时命中的是旧索引
   （新语料还没进去），`python -m brain.search_engine eval` 记下命中率。
2. 改代码 → `build --force` → **再跑一次**。
3. 验收判据：**整体命中率不低于改动前**（老的公司类问题必须仍然命中），
   且新增的研究类问题命中率有明确提升。

新增评测题建议 15~20 道，覆盖三类：

- 研究报告类：「ETF 轮动 20 日动量窗口是怎么定下来的」→ 期望命中
  `research/2026-09-16_ETF轮动基线诊断与改良迭代_研究报告.md`
- 审计/事故类：「缓存投毒事件是怎么发生的」→ 期望命中对应的审计或计划文档
- 方法论类：「公式因子体检的五条纪律是什么」→ 期望命中 `docs/公式因子体检方法论.md`

## 5. 规模与耗时估算

| 项 | 估算 | 依据 |
|---|---|---|
| 新增语料 | 268 篇 / 3.2 MB | 实测（`research/` 55 篇 0.6 MB + `docs/` 213 篇 2.6 MB） |

**结论：这是一件"一次性几分钟、之后边际成本为零"的事。**

## 7. 风险与边界

| 风险 | 处置 |
|---|---|
| `source` 分叉导致同一文件重复入库 | 收口 `_to_source` + 单测断言两侧一致（本计划最重要的一条） |
| 评测集没迁移 → eval 全判失败 → 误判"改了以后变差了" | 迁移评测集是 §3 的强制连带动作，写进验收标准 |
| 提示词改动踩掉 `tests/test_brain_prompts.py` 的断言 | 必须原样保留 `python -m brain.search_engine search` 字符串 |
| 索引变大后内存 | 512 维 × 约 8000 块 ≈ 16 MB float32，忽略不计 |
| `docs/` 里有生成物混进来 | `exclude_dirs` 剪枝 + `min_chars=50` 丢弃碎块；首次构建后抽查 `meta.jsonl` 的 source 分布 |
| 机密随检索片段外发 | **用户已选 C 并知悉**（§2），保留可逆开关 |

## 8. 不做（明确划界，防范围蔓延）

- **不做重排序模型**（rerank）：检索 top-k 后不再用交叉编码器精排。理由：要再下一个模型
  + 显著加延迟，而现在的瓶颈是"语料没进去"，不是"排序不精"。
- **不做混合检索**（关键词 BM25 + 向量）：大脑已有 `Grep` 做关键词精确匹配
  （`brain/prompts.py` 第 28 行明确二者互补），不需要在引擎里再实现一份。
- **不换 embedding 模型**：保持 bge-small-zh-v1.5。换模型要重下模型 + 全量重建，
  且向量维度变了旧索引直接作废，收益不确定。
- **不改 `SLIM_SYSTEM_PROMPT`**：快路径不调工具。
