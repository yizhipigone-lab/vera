## 3. 关键设计：`source` 路径约定必须统一（本计划最大的技术风险）

现状有一处会造成**同一文件被索引两遍**的隐患：

- `build_index` 第 325 行：`source = str(md_file.relative_to(VAULT_ROOT).as_posix())`
  → 产出形如 `company/company_002390.md`（**vault 相对**）
- `update_file` 第 342 行：
  ```python
  source = str(filepath.relative_to(VAULT_ROOT).as_posix()) \
           if filepath.is_absolute() and VAULT_ROOT in filepath.parents \
           else filepath.as_posix()
  ```
  → 文件**不在** `vera_obs_vault/` 下时，`source` 退化成**绝对路径**

加了 `research/`、`docs/` 两个新根之后，这个分叉会立刻爆炸：
全量构建产出 `research/xxx.md`，而归档增量更新产出 `E:/1target/VERA/research/xxx.md`，
两个 key 指向同一个文件 → 索引里出现重复块，检索结果里同一篇文章挤占多个 top-k 名额。

**决策：`source` 统一为「项目根相对 posix 路径」**（如 `vera_obs_vault/company/company_002390.md`、
`research/2026-09-16_ETF轮动基线诊断与改良迭代_研究报告.md`）。

这带来三个必须一起做的连带动作：

1. **全量重建索引**（`build --force`）。旧索引的 `company/xxx.md` 形态与新形态不兼容。
2. **迁移评测集**。`brain/search_evalset.json` 现有 62 行全部形如
   `"expect_path": "company/company_002390.md"`，必须整体加上 `vera_obs_vault/` 前缀，
   否则 `eval_search` 的命中判定（第 410 行精确等值比较）会**全部判失败**。
3. **顺带修一个老毛病（净改善）**：现在 `_cmd_search` 打印的 `path` 是
   `company/company_002390.md`——**这不是一个从项目根可读的路径**，大脑拿到后要自己猜
   前面还得补 `vera_obs_vault/`。统一成项目根相对路径后，大脑可以直接把这个路径丢给
   `Read`。这一条属于本计划的附带修复，要写进 CHANGELOG。

### 3.1 【铁律】先收口，再扩范围 —— 顺序不能颠倒

用户 2026-09-17 明确要求「**这个技术风险要重视，要避免**」。据此把执行顺序定死：

| 步骤 | 做什么 | 做完的判据 |
|---|---|---|
| **第一步**（唯一允许先做的改动） | 把 `source` 计算收口成唯一函数 `_to_source(path)`，`build_index` 与 `update_file` 都改引它。**此时索引范围一个字都不改** | `build --force` 重建 + 跑评测，**命中率与改动前完全一致**（范围没变，结果就不该变） |
| **第二步** | 才去加 `research/` 与 `docs/` 两个新根 | 评测整体命中率 ≥ 第一步基线，新增研究类问题命中率明显上升 |

**为什么必须分开**：如果两件事一起做，一旦检索结果变差，**无法区分是「source 口径变了」
还是「新语料稀释了 top-k」**——两处变量同时动，出了事查不出来。分开做，每步都有干净对照。

### 3.2 三重防线（缺一不可，每条都要有测试锁）

| # | 防线 | 机制 | 防的是什么 |
|---|---|---|---|
| **①** | **唯一出口** | 全项目只有 `_to_source(path)` 一处算 source；加一条 grep 断言：`relative_to(VAULT_ROOT)` 在 `brain/search_engine.py` 里**只允许出现一次** | 再分叉出第二个路径口径（项目反复踩的"同一条规则手写 N 份必然漂移"） |
| **②** | **拒绝绝对路径** | `_to_source` 出口处断言结果**不是绝对路径**（`is_absolute()` 为真、或以盘符开头 → 抛错），不允许静默退化 | 现状第 342 行的行为：VAULT_ROOT 外的文件会退化成绝对路径，与新根的相对路径撞成两个 key |
| **③** | **构建后自检** | `build_index` 收尾断言 `len({m['source'] for m in meta})` == 本次处理的文件数；不等即有文件被记成两个 key，**直接失败、不落盘** | 同一文件重复入库、一篇报告挤占多个 top-k 名额 |

**三条测试**（新增到 `tests/test_brain_search_engine.py`）：

1. 同一文件分别经 `build_index` 与 `update_file`，`source` **字符串必须相等**（回归锁，防未来又分叉）
2. 传一个 `vera_obs_vault/` **之外**的临时文件给 `update_file`，`source` 必须是项目根相对路径，
   且**等于** `build_index` 对同一文件会给出的值
3. 人为构造 source 冲突（两个文件映射到同一 source），`build_index` 必须**报错**而不是静默写重

#### 4.6.1 落盘设计

```
qqmail 技能收信  →  docs/research_inbox/<日期>_<主题>/   ← 只落 .md，且保留原始相对路径
                              ↓
                    加进 brain/search_engine 的 roots
```

- **只索引 `.md`**。实测那批产物包里：`.md` 21 篇 / 237 KB、`.html` 20 篇 / **8 MB**、
  `.py` 78 个 / 1 MB、`.json` 24 个 / 2.3 MB。HTML 体积是 Markdown 的 34 倍且满是标签噪音，
  `.py`/`.json` 是源码与数据不是报告——**一概不收**。
- **落盘目录与用户自己的研究物理分开**：用户手写的在 `research/`，这批外部产物在
  `docs/research_inbox/`。好处有两个：①`source` 路径天然带上来源，检索结果一眼能区分
  "这是我们自己研究过的" 还是 "这是别人发来的"；②将来想整批清掉只需删一个目录。
- **同名去重**：实测同一篇 `A股牛熊面板-资金层升级与指标验证.md` 在 9 个包里出现了 2 次。
  落盘时按内容哈希去重（同内容只留一份），否则同一篇文章会挤占多个 top-k 名额
  ——这与 §3 要防的是同一类病。
- **每篇顶部注入来源元信息**（照 `_extract_file_prefix` 对 company 文件的既有做法）：
  `来源：邮箱 dcliuzh@qq.com ｜ 收到：2026-09-13 ｜ 原始附件：xxx.zip`。
  检索片段自带出处，大脑引用时能写清"这是外部研报说的"，**不会与用户自己的结论混淆**。
- **`.gitignore` 要加 `docs/research_inbox/`**：这是外部第三方产物，且体积随收信增长，
  不适合入库。它是可重建的（重跑收信脚本即可）。

#### 4.6.2 收信→落盘要单独写一个脚本，且**不并入索引器**

新增 `tools/mail_to_corpus.py`：调 `qqmail` 技能 → 解出 `.md` → 去重 → 落
`docs/research_inbox/`。理由：

- **索引器只管"读仓库里的文件"，不碰网络/邮箱**。这条边界必须守住，
  否则 §3 的 `source` 唯一口径会被"从邮件来的语料"搅浑（那正是选项 C 被否掉的原因）。
- 收信是"拉外部数据"，落盘后就是普通仓库文件，索引器视角完全统一。

#### 4.6.3 必须带的质量警告（这批语料不是权威）

实测证据（详见大盘位置计划书 §14.6）：**同一批产物、同一天，两封邮件给出相反结论**
（16:24 那封说"现在是牛市"，17:11 那封说"不算牛、下跌中继"）。所以：

- 检索结果里**必须**能看出这是外部产物（靠 §4.6.1 的来源前缀与目录名）；
- 提示词里要加一句：**引用外部研究库内容时，必须说明来源并提示"该结论未经本系统复核"**；
- 评测集里**不放**外部语料的问题（评测集只考"能不能找到用户自己的报告"），
  避免用外部内容拉高命中率掩盖真实问题。

#### 4.6.4 一个意外收获：这批语料里有 ETF 轮动的现成研究

82 文件那个大包里有一整个 `02_ETF策略研究/` 目录，含 6 份 ETF 报告
（动量轮动、高抛低吸遍历、外部专家报告验证、尾盘成交时点验证、双周 vs 每周复核）。
本项目的 ETF 轮动已做过三轮 244 组研究，**这 6 份是可交叉验证的外部参照**。
这属于 ETF 轮动的研究范畴，**不在本计划范围内**——此处只登记线索，
另立研究任务时再取用（语料已在索引里，届时大脑可直接检索到）。

### 4.7 读信读出来的一个改良项（转交大盘位置计划书）

## 7. 风险与边界

| 风险 | 处置 |
|---|---|
| `source` 分叉导致同一文件重复入库 | 收口 `_to_source` + 单测断言两侧一致（本计划最重要的一条） |
| 评测集没迁移 → eval 全判失败 → 误判"改了以后变差了" | 迁移评测集是 §3 的强制连带动作，写进验收标准 |

| 机密随检索片段外发 | **用户已选 C 并知悉**（§2），保留可逆开关 |

## 8. 不做（明确划界，防范围蔓延）

- **不做重排序模型**（rerank）：检索 top-k 后不再用交叉编码器精排。理由：要再下一个模型
  + 显著加延迟，而现在的瓶颈是"语料没进去"，不是"排序不精"。
- **不做混合检索**（关键词 BM25 + 向量）：大脑已有 `Grep` 做关键词精确匹配
  （`brain/prompts.py` 第 28 行明确二者互补），不需要在引擎里再实现一份。
- **不换 embedding 模型**：保持 bge-small-zh-v1.5。换模型要重下模型 + 全量重建，
  且向量维度变了旧索引直接作废，收益不确定。
- **不改 `SLIM_SYSTEM_PROMPT`**：快路径不调工具。

## 11. 外部最佳实践对照与采纳（2026-09-17 联网检索后新增）

检索来源：[RAG 分块策略指南（Atlan）](https://atlan.com/know/chunking-strategies-rag/)、
[RAG 索引漂移检测（Oracle）](https://blogs.oracle.com/developers/how-to-detect-rag-index-drift-deleted-docs-stale-chunks-and-duplicate-embeddings)。

### 11.1 逐条对照

| # | 外部实践 | 我们现状 | 采纳结论 |
|---|---|---|---|
| **R1** | **RAG 最难的失败来自「陈旧、失管的源数据」，而不是分块大小没调好**（Atlan 指南的核心结论） | §3.2 有构建后自检、§3.3 有并发快照，但**没有"索引新鲜度"这个概念** | ✅ **采纳**（§11.2） |
| **R2** | 索引漂移的三种命名病：**已删除文档仍在索引 / 陈旧块 / 重复嵌入** | 重复嵌入：§4.6.1 有哈希去重 ✅；陈旧块与已删除：**全量重建天然解决**，但**没有断言兜底** | ✅ 采纳（§11.2 的"双向集合相等"断言） |
| **R3** | **元数据增强检索，准确率最高可比纯内容检索高 5 倍** | §4.6.1 已对邮箱语料注入来源前缀 ✅，但**只做了那一类** | ✅ **采纳并推广**（§11.3） |
| **R4** | 固定大小分块会切断语义；**层级 / 父子分块**能提升质量 | `_chunk` 是按段落递归合并 + 硬切（比固定大小好），无父子结构 | ❌ **不采纳**：Atlan 自己说最难的失败不是分块大小；改分块要全量重建且收益不确定，**违反"先跑通再优化"** |
| **R5** | 评测不能只看命中率，要看 **MRR / nDCG / recall@k** | `eval_search` 只算"`expect_path` 是否在前 5"（= recall@5），**排名质量完全没测** | ✅ **采纳 MRR**（§11.4），nDCG 不做（无相关性分级，用不上） |
| **R6** | 索引健康度要有独立监控 | 无 | ⚠️ 部分采纳：不引入 `raghealth` 之类外部工具，但 §11.2 的自检 + §4.5 的 eval 已覆盖核心 |

### 11.2 采纳 R1+R2：加「索引新鲜度」

外部结论很直接：**索引最怕的是"源文件变了而索引没跟上"**。我们的 `build_index` 有
`skipped` 早退逻辑（第 305~306 行：meta 存在就直接 `return {"skipped": True}`）——
**这正是"陈旧索引"的入口**：只要有人忘了加 `--force`，语料更新了索引也不动，
而**大脑看不出区别**。

**改法**：`build_index` 计算并落盘一个**新鲜度指纹** `index_stamp.json`，含：

- 构建时间；
- 本次纳入的**文件清单 + 各自 mtime**（或整体哈希）；
- 各 `root` 的文件数。

`search` 与 CLI 在检索前**比对当前磁盘清单与指纹**：不一致就打印一行醒目的
「**索引陈旧：自 YYYY-MM-DD 起有 N 个文件变动，请重跑 build**」。
**只告警不自动重建**（自动重建会让检索变成分钟级，破坏"毫秒级"这个核心体验）。

配套把 §3.2 的防线③从单向升级为**双向集合相等**：

```
索引里的 source 集合  ==  磁盘上扫描到的文件集合（相对路径）
```

少了 → 有文件没进索引；多了 → **有已删除文件仍留在索引里**（R2 的第一种病）。
两个方向都要断言，不等就失败、不落盘。

### 11.3 采纳 R3：元数据前缀推广到全部语料

§4.6.1 已经给邮箱语料注入来源前缀，实测这个做法有效，**推广到所有根**：

| 语料 | 注入的前缀 |
|---|---|
| `vera_obs_vault/company/*` | 已有：`公司：X。股票代码：Y。所属行业：Z。`（`_extract_file_prefix`，第 231 行） |
| `research/*` | `研究报告：<文件名主题>。日期：YYYY-MM-DD。` |
| `docs/audit/*` | `审计报告。日期：YYYY-MM-DD。` |
| `docs/plan/*` | `实施计划。日期：YYYY-MM-DD。` |
| `docs/research_inbox/*` | `外部研究产物（邮箱）。来源：X。收到：YYYY-MM-DD。` |

日期从文件名前缀 `YYYY-MM-DD_` 正则提取，提不到就不写（**不编日期**）。
好处：检索片段自带出处与类型，大脑引用时能分清"我自己写的计划"和"外部发来的研报"。

### 11.4 采纳 R5：评测加 MRR（这条是刚需）

现在 `eval_search` 只判"在前 5 吗"。**语料扩大 3 倍后，最典型的退化不是"找不到"，
而是"找到了但排到第 4 第 5"**——现指标对此**完全瞎**。

**改法**：在 `eval_search` 返回值里加：

- `mrr`：命中文档排名倒数的平均（排第 1 得 1.0，排第 5 得 0.2，没命中得 0）；
- 命中但排名 > 1 的题目清单（`ranked_low`），便于逐题排查。

这条直接服务 §3.1 的两步走：**第一步**（只收口 source 口径）要求
**hit_rate 与 MRR 双双不变**；**第二步**（扩语料）要求 hit_rate 不降、
**MRR 不显著下降**（新语料会稀释排名，降一点是正常的，但要看得见）。

### 11.5 §11 的验收标准

1. `build_index` 落盘 `index_stamp.json`；`search` 检测到陈旧时打印醒目告警（有测试锁）。
2. 构建后断言**双向集合相等**（索引 source 集合 == 磁盘文件集合），不等则失败不落盘。
3. 五类语料都有对应元数据前缀；日期提不到时不写（有测试锁）。
4. `eval_search` 返回 `mrr` 与 `ranked_low`；§3.1 两步走的判据改为 hit_rate + MRR 双指标。
5. **不引入父子分块、不引入外部 RAG 健康度工具**（§11.1 的 R4/R6）。

## 12. 深度审查修订（2026-09-17 两轮对抗式审查后，逐条必改）

审查发现 **5 条 HIGH**（其中 HIGH-1 已单列为 §0）、4 条 MEDIUM、4 条 LOW。
**本节是实施时的强制修订清单**，与前面各节冲突时**以本节为准**。

### 12.1 【HIGH-2】`失败不落盘` 把软降级改成硬失败，与 §3.3 自相矛盾

**问题**：`brain/search_engine.py:317-324` 是**刻意的逐文件 fail-soft**
（`_read_chunks` 返空 → `continue`；`_embed` 抛异常 → `logger.warning` + `continue`）。
而 §11.2 要求"双向集合相等，**不等就失败、不落盘**"——任何一个文件读取/嵌入失败，
**整次构建失败、索引停在旧状态**（比现在更糟：现在是少一个文件，改后是一个都没有）。
且 §3.3 自己承认"仓库同时有别的会话在写"，并发增删会让断言**频繁**失败，
而 §3.3 给的解药"再跑一轮"下一轮大概率同样失败。两个机制在同一份计划书里互相打架。

**修订（覆盖 §3.2 防线③ 与 §11.2）**：

| 情况 | 处置 |
|---|---|
| 文件**没进索引，但在 skipped 清单里**（读取失败/嵌入失败/块数 0） | **不算失败**，记入 `skipped: [{path, reason}]`，随构建结果返回 |
| 文件**没进索引，也不在 skipped 里** | **失败**（这是真漏） |
| 索引里有、磁盘上没有（**旧文件残留**） | **失败**（这是真病：已删除文件还在索引里，占检索名额） |
| 并发导致磁盘清单在构建期间变动 | **告警 + 保留上一份可用索引**，**绝不让构建把已有索引清空** |

断言改为：`索引 source 集合 == 磁盘文件集合 − skipped 集合`。
另把 `_embed` 失败从直接 `continue` 改成**重试一次再跳过**，减少 skipped 来源。

### 12.2 【HIGH-5】三重防线漏了 `update_file` —— 迁移窗口内会产生"双 key"

**问题**：防线③**只在 `build_index` 里**。但 `update_file` 是**运行时常规路径**
（`brain/archive.py:167` 每次对话归档都调，另有 `claude_cli.py:242`、`dsh_channel.py:349`、
`quick_chat.py:106`）。`brain/search_engine.py:361-368` 按 **source 字符串精确匹配**去重
（`m["source"] != source`）。

**收口 source 口径后、在下一次 `build --force` 之前**，任何一次归档都会算出**新形态** key
（`vera_obs_vault/对话沉淀/xxx.md`），而它**匹配不到索引里旧形态的 key**（`对话沉淀/xxx.md`）
→ **旧块保留 + 新块追加 = 同一文件两个 key 并存**。三道防线一条都拦不住
（①满足②满足③不执行）。

**修订**：

1. 索引里落一个 **`source_format` 版本号**（写进 `meta.jsonl` 首行或 `index_stamp.json`）；
   `update_file` **入口先校验版本**，不匹配就 **拒绝写入并提示先 `build --force`**（fail-closed，
   而不是静默追加）。`brain/search_engine.py` 现在 `SCHEMA|VERSION|stamp` 零命中，没有任何版本闸门。
2. **§3.1 补一条顺序铁律**：`build --force` **必须**在 source 收口提交后的
   **第一次 `update_file` 之前**完成；brain 服务在跑就先停，或先设 `BRAIN_NO_INDEX_SYNC=1`。
3. **加测试**：往一个"旧形态索引"上调 `update_file`，**必须报错**而不是产生双 key。

### 12.3 【L1】删掉 `index_stamp.json` —— `meta.jsonl` 已经逐块存了 mtime

**问题**：§11.2 要新建 `index_stamp.json`。但 `meta.jsonl` 里每块已经有
`{"id","source","chunk_idx","mtime","snippet"}`（`_meta_entries`）——**磁盘清单与 mtime 现算即可，
不需要新文件**。深模块检查单第 2 问就是"能不能更小"。

**修订**：**不新建 `index_stamp.json`**；新鲜度改为**从 `meta.jsonl` 现算**：
比对「磁盘上各文件的 (相对路径, mtime)」与「meta 里各 source 的最大 mtime」。
唯一需要新落盘的是 §12.2 的 **`source_format` 版本号**（可以放在 meta 首行，或一个极小的
`index_stamp.json` 只装版本号——两者选一，不装文件清单）。

**并明写 LOW-4 的仲裁**（否则会出现"告警永不消除"或"假清除"）：
**只在真正执行构建时写版本号；遇到 `skipped` 早退时，重算磁盘清单与 meta 比对，
不一致就返回 `stale: True` 并提示 `--force`，绝不静默更新版本号。**

### 12.4 【L2】`tools/mail_to_corpus.py` 的外部依赖必须显式声明

**问题**：§4.6.2 说它"调 `qqmail` 技能"，而该技能在
`C:\Users\<用户名>\.dsh\skills\qqmail`——**仓库之外、绑定当前 Windows 用户**，换机器/换用户即失效。
另经核验：该技能的 `Receive-QQMail.ps1` **只产出 `.eml` / `.txt` / `_summary.txt`，
不解析 zip 附件**——所以"解出 `.md`"这一步**确实得自己写**。

**修订**：
- §4.6.2 的表述改成「**调技能收信 + 自己解 zip 取 `.md`**」，两件事分开写清；
- 显式声明这是**机器专属外部依赖**；
- **技能缺失时脚本必须报错退出，不许静默产出空语料**（否则会把"收不到信"伪装成"没有新语料"，
  下一次 `build` 就把索引里那部分清空——这正是 §12.1 要防的那类静默失败）。

### 12.5 【M5】§6 说"不新建模块"与 §4.6.2 新增 `tools/mail_to_corpus.py` 打架

**修订**：§6 那句改成——「**索引器本身不新建模块**（改动全在 `brain/search_engine.py` 内）；
另新增 **1 个**收信落盘工具 `tools/mail_to_corpus.py`（理由见 §4.6.2，删除测试：删掉它，
"收信→落盘"这件事只能散回调度器与手工步骤，故该留）」。
把 §6「删除测试」一行补上这个工具的论证。

### 12.6 【M6】`docs` 根会收进机器生成物 —— 且与复盘报告形成"自我污染"环

**问题**：`docs/brief/`（`tools/daily_brief.py` 每天生成）、`docs/report/`（回测排名产物）、
`docs/audit/`（`formula_lab` S5 自动落盘，108 篇）**都是机器生成物**，而 §4.1 的
`exclude_dirs` **一个都没排**。

**更严重的连线**：复盘报告计划书**通篇没定落盘路径**，而项目惯例（`brain/prompts.py:104`）
是"简报/研究报告默认落 `docs/brief/` 或 `docs/report/`"。**一旦复盘报告按惯例落进 `docs/`，
它就会被自己的 RAG 索引进去**——系统每天生成一份报告，日积月累污染检索库。
这正是 §11.2 想防的"索引漂移"，但两份计划书各写各的，没人画这条线。

**修订（两份计划书同改）**：

| 改哪 | 怎么改 |
|---|---|
| RAG §4.1 `exclude_dirs` | 显式加 `docs/brief`、`docs/report`、`docs/audit`（**确认是机器生成物**；`docs/audit` 若想保留就单独讨论，默认排） |
| 复盘计划书 | **钉死落盘路径：`data/daily_review/<日期>.md`**（`data/` 已被 RAG 排除，天然不会自我污染），**不用 `docs/`** |
| 两份计划书 | 各加一行交叉引用：「本目录是/不是 RAG 的语料源，改动前先看对方计划书」 |

### 12.7 【L6】如实修正机密暴露面：根 `research/` **早已在 git 里**

**问题**：§2 把 `.gitignore` 第 58~59 行当 `research/` 的机密依据。**实测：那两行排除的是
`docs/research/`，与根目录 `research/` 不是同一个路径**。而根 `research/` **已被 git 跟踪
308 个文件**，其中就包括 §2 点名的那份含止盈止损参数的报告。

**修订**：§2 改成如实描述——「`.gitignore` 只把 `docs/research/` 排除在外；
**根 `research/` 及其中的参数类报告已经在 git 里**（`git ls-files` 实测 308 个文件）」。
**这不改变"选 C"的结论**（用户已知悉并拍板），但影响对暴露面的判断：
**参数早就在版本库里了**，RAG 把它发到模型厂商是"多一条外发通道"，不是"首次泄露"。
把这一点写进 §2 的风险认知，避免将来误判。

### 12.8 §12 的验收标准（追加到 §9 之后）

1. **索引内不得出现以盘符开头的 source**（断言，防 §0 事故复发）。

8. `eval_search` 返回 `mrr` 与 `ranked_low`（§11.4）。

### 13.4 索引新鲜度（§11.2 R1+R2，**不新建 stamp 文件** §12.3）

新增 `index_freshness()` + CLI `fresh`：从 `meta.jsonl` **现算**，比对
「磁盘各文件的 (相对路径, mtime)」与「索引各 source 的最大 mtime」，给出
`missing_from_index` / `changed` / `orphan_in_index` / 版本是否匹配（mtime 留 1 秒容差）。
**实测**：重建后 `python -m brain.search_engine fresh` = **「索引与磁盘一致」**。

**为什么必须有它**：检索库最容易出的不是"搜不准"，而是"搜到的是上一版内容"
或"删掉的文件还在被引用" —— 这两种都不会报错。
