# VERA 前端模块化 — 项目计划书

> 日期: 2026-07-23
> 范围: `web/vera-ui.js` (1711 行) → 4 文件
> 目标: 给前端 JS 建立内部接缝，每个模块一个小接口，行为零改动

---

## 0. 背景与目标

### 现状

`web/vera-ui.js` 是一个 1711 行的单体 JS 文件：
- 69 个函数声明，全部挂全局作用域
- 30+ 个全局 `let`/`const` 变量散落文件各处
- 20 个 `fetch()` 调用点，每个自己处理错误
- 3 种状态存储（DOM、localStorage、全局变量）各自独立管理
- 无模块边界，改图表逻辑可能碰坏 API 调用，改表单校验可能影响回测提交

### 目标

将单体文件拆成 5 个模块，每个通过 ES modules (`<script type="module">`) 加载：

| 文件 | 职责 | 估算行数 | 对外接口 |
|---|---|---|---|
| `web/js/api.js` | API 客户端 | ~120 行 | 15 个 fetch 函数 |
| `web/js/config.js` | 配置表单适配器 | ~250 行 | `collect()` / `apply()` / 校验函数 |
| `web/js/charts.js` | 图表渲染 + 视觉 | ~550 行 | `render(result)` / `toast(msg)` / `log(msg)` |
| `web/js/recover.js` | 断网恢复逻辑 | ~100 行 | `tryRecover()` / `resetUI()` / `RECOVER` |
| `web/js/vera-ui.js` | 应用壳体（协调 + 初始化） | ~550 行 | 导出共享状态访问器 + 入口 |

> recover.js 是计划自检后新增的第 5 个模块，原因见 §5。

### 设计原则

1. **行为零改动** — 用户看到的界面、交互、数据流完全不变
2. **每个模块只做一件事** — API 模块不碰 DOM，图表模块不发请求，配置模块不管渲染
3. **接口即测试面** — 每个模块的导出函数就是它的测试合同
4. **先拆后优** — 本次只做结构重组，不趁机重构函数内部实现

## 1. 模块设计

### 1.1 API 客户端 (`web/js/api.js`)

**职责**: 所有后端 HTTP 请求的单一入口。

**接口**（15 个导出函数）:

```
fetchStatus()              → GET  /api/status
submitBacktest(config)     → POST /api/run
stopBacktest()             → POST /api/stop
fetchLastResult()          → GET  /api/last_result
fetchResults()             → GET  /api/results
fetchResult(id)            → GET  /api/results/{id}
fetchConfigDefaults()      → GET  /api/config/defaults
saveConfig(config)         → POST /api/config/save
fetchSavedConfig()         → GET  /api/config/saved
deleteSavedConfig()        → DELETE /api/config/saved
fetchSectors()             → GET  /api/sectors
fetchFactorRules(formula)  → GET  /api/factor-rules
submitLabJob(body)         → POST /api/lab/run
fetchLabStatus()           → GET  /api/lab/status
fetchLabHistory()          → GET  /api/lab/history
fetchLabReport(formula)    → GET  /api/lab/report
```

**设计约束**:
- 每个函数只做 fetch + JSON 解析，不处理业务逻辑
- 统一返回 `{success, data/error}` 形状（当前后端约定）
- 不引入 axios 等外部依赖 — 保持零构建工具
- 不做错误重试、不做超时控制 — 这些属于调用方职责

**从哪里搬**:
- `loadSectors()` 里的 fetch → `fetchSectors()`
- `saveConfigToFile()` / `loadConfigFromFile()` / `deleteSavedConfig()` 里的 fetch → 各自对应
- `resetDefaults()` 里的 fetch → `fetchConfigDefaults()`
- `runPipeline()` 里的 `/api/run` + `/api/status` 轮询 fetch → `submitBacktest()` + `fetchStatus()`
- `stopPipeline()` 里的 `/api/stop` → `stopBacktest()`
- `tryRecoverAbortedResult()` 里的 `/api/status` + `/api/last_result` + `/api/results` → 各自对应
- `loadFactorRules()` 里的 fetch → `fetchFactorRules()`
- `labSubmit()` / `refreshLabStatus()` / `loadLabHistory()` / `viewLabReport()` 里的 fetch → 各自对应
- `loadHistory()` 里的 fetch → `fetchResult()`
- 初始化时的 `/api/config/saved` / `/api/results` → 各自对应

### 1.2 配置表单适配器 (`web/js/config.js`)

**职责**: 前端表单 ↔ 后端配置 dict ↔ localStorage 的翻译层。

**接口**（~12 个导出）:

```
collectConfigFromForm() → payload        // 读 DOM 表单 → 后端 JSON
applyConfigDict(cfg)    → void           // 后端 dict → 写 DOM 表单
loadConfig()            → void           // localStorage → DOM
saveAllConfig()         → void           // DOM → localStorage
refreshAllSummaries()   → void           // 更新侧栏摘要文本
toggleEdit(blockId)     → void
cancelEdit(blockId)     → void
saveBlock(blockId)      → void
validateDate(el)        → void
validatePositive(el)    → void
validateNonNeg(el)      → void
validateLadder(el)      → void
cleanNum(x)             → number
```

**常量导出**: `CONFIG_IDS`, `RADIO_CONFIGS`, `STORAGE_KEY`

**设计约束**:
- `collectConfigFromForm()` 和 `applyConfigDict()` 必须互为逆操作（往返测试可验证）
- 对 DOM 的读写是模块的副作用，但接口本身是纯数据 in/out
- 不发起任何网络请求

**从哪里搬**: 整段 config persistence 区域（行 125-198）+ 表单校验（行 57-83）+ `collectConfigFromForm`（行 448-494）+ `applyConfigDict`（行 499-572）+ `refreshAllSummaries`（行 360-393）+ block edit（行 396-443）

### 1.3 图表渲染 (`web/js/charts.js`)

**职责**: 所有可视化渲染。接收数据，产出 DOM/ECharts。

**接口**（~12 个导出）:

```
renderAllCharts(data)     → void    // 主渲染入口：KPI + 权益图 + 月度 + 交易分析 + 降级卡 + 未平仓
renderTradeTable(trades)  → void    // 交易明细表
filterTrades()            → void    // 交易筛选逻辑
fillHeroSub(m, data, c)   → void    // hero 子行指标
revealResults()           → void    // 卡片入场动画
showToast(msg, type)      → void    // Toast 通知
addLog(msg, type)         → void    // 系统日志
checkEngineVersion(data)  → void    // 引擎版本警告
getColors()               → colors  // 主题色
toggleTheme()             → void    // 切换主题
toggleSidebar()           → void    // 切换侧栏
hexToRgba(color, alpha)   → string  // 颜色工具
esc(s) / escAttr(s)       → string  // XSS 防御
tweenNumber(el, v, fmt)   → void    // KPI 数字动画
sparkline(vals, c, a)     → string  // SVG 迷你图
echartsInit(id)            → chart   // ECharts 实例管理
```

**设计约束**:
- 不发起网络请求 — 只接收数据、产出 DOM
- 不读写**业务配置**的 localStorage（theme/sidebar 偏好是纯 UI 行为，保留在 charts.js 内）

- `renderAllCharts(data)` 是唯一的"大入口"，内部调用所有子渲染函数
- `addLog` 的 `logLines` 数组作为模块内部变量（不在模块间共享）；调用方统一通过 `import { addLog } from './charts.js'` 使用
- theme toggle 和 sidebar toggle 是纯 UI 行为，归此类（含其 localStorage 读写）

**从哪里搬**: 行 1-23（hexToRgba, esc）+ 行 85-123（theme, sidebar, getColors）+ 行 656-670（addLog）+ 行 672-684（lastResult, charts, echartsInit）+ 行 917-1355（tweenNumber, sparkline, fillHeroSub, revealResults, renderAllCharts）+ 行 1357-1459（reasonDetail, renderTradeTable, filterTrades）+ 行 25-33（showToast）+ 行 44-55（checkEngineVersion）+ 行 1685-1699（loadHistory — 但这个调 API，应该留在 app.js...让我重新考虑）

实际上 `loadHistory` 既有 API 调用又有渲染，应该在 app.js（协调层）。图表模块只负责"给我数据，我渲染"。

## 5. 关键发现：现有测试兼容性

### 问题：`test_recover_integration.js` 用 `vm.runInContext` 加载源码

`tests/js/test_recover_integration.js` (209 行) 的核心加载机制是：

```js
const src = fs.readFileSync(path.join(__dirname, '..', '..', 'web', 'vera-ui.js'), 'utf8');
vm.runInContext(src, ctx);
```

它依赖：
1. **源码是纯脚本**（无 `import`/`export`）—— ES module 语法在 `vm.runInContext` 里是语法错误
2. **源码末尾的 CommonJS 导出块**：`module.exports = { tryRecoverAbortedResult, resetRunUI, RECOVER }`
3. **全局函数被 mock 钉死**：`addLog`, `showToast`, `renderAllCharts` 等在 vm context 里被 `Object.defineProperty(writable:false)` 覆盖

切换到 ES modules 后，`vm.runInContext` 无法解析 `import` 语句。

### 解决方案：提取 recover 模块

把 `tryRecoverAbortedResult` / `resetRunUI` / `RECOVER` 提取到 `web/js/recover.js`：

- **无 `import` 依赖** — 所有外部依赖通过函数参数传入（`showToast`, `addLog`, `renderAllCharts` 等）
- **浏览器端**：`vera-ui.js` 用 `import { ... } from './recover.js'` 导入
- **测试端**：Node.js 用 `require('./recover.js')` 或动态 `import()` 加载

修改点：
1. 原 `tryRecoverAbortedResult(cfg, originalErr)` 签名不变，内部调用的 `showToast`/`addLog`/`renderAllCharts`/`checkEngineVersion`/`resetRunUI`/`lastResult` 改为模块顶层可替换引用（类似 connector seam 模式）
2. `resetRunUI` 拆出 — 它是纯 UI 函数，操作 `document.getElementById`，测试 mock 已覆盖
3. 测试文件更新路径：`web/vera-ui.js` → `web/js/recover.js`

### 成本

- 新增 1 个模块文件（`web/js/recover.js`，~100 行），总数从 4 变 5
- 测试文件路径更新 + `vm.runInContext` → 直接 `require()`

## 6. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| ES module 在旧浏览器不兼容 | 低 | 低 | VERA 是个人本地工具，用户用最新 Chrome/Edge |
| `import` 导致 CORS 问题（file:// 协议） | 低 | 中 | VERA 走 FastAPI `StaticFiles` 托管，走 http://localhost:8080，无 CORS |
| ECharts 全局变量在 ES module 中不可见 | 中 | 中 | `echarts.min.js` 挂 `window.echarts`，模块内用 `globalThis.echarts` 或 `const echarts = window.echarts` |
| 函数搬移时遗漏调用点 | 中 | 高 | Step 1-3 每一步搬完后，用 Grep 在原文件搜索函数名确认无残留调用 |
| 往返测试发现 `collect≠apply` 漂移 | 低 | 中 | 重构前先跑一次现有往返基准，记录 baseline |
